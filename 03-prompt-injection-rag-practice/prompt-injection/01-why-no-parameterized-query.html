第 1 章　為什麼沒有參數化查詢：LLM01:2026 與攻擊面

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO1
  • 前置：SQL Injection 與 Prompt Injection 的對照；攻擊面與信任邊界

你知道 SQL Injection 靠參數化查詢 (Parameterized Query) 解掉了。這一章回答一個問題：LLM 為什麼沒有等價物？答案不是某個還沒補上的修補，而是模型讀輸入的方式。弄懂這一點，後面三章「為什麼防線要這樣疊」才說得通。

1.1 LLM01:2026 說的是什麼

官方對提示詞注入 (Prompt Injection) 的定義很寬：任何輸入，包括使用者直接輸入、取回的內容、工具輸出、圖片／音訊／影片、中間推理，或持久記憶，只要讓模型的行為偏離開發者的本意，就算。輸入不必是人看得懂的，不必直接來自使用者，也不必在畫面上看得到。官方

根本原因只有一句：LLM 在架構上不區分「指令」與「資料」，兩者都是同一條 token 串流，所以沒有乾淨等價於參數化查詢的做法（官方引用英國 NCSC 2025 的說法）。官方 官方接著點出三個讓情況更糟的部署特性：

  • 上下文池化 (Context-Window Pooling)：system prompt、使用者輸入、取回文件、工具輸出、對話歷史與記憶被當成同一串 token，沒有被強制執行的信任邊界 (Trust Boundary)。
  • 記憶持久化：寫進長期記憶、RAG 語料、向量資料庫或託管記憶服務的注入，會污染之後每一個讀取它的 session。
  • agentic 執行：模型輸出驅動工具呼叫時，爆炸半徑 (Blast Radius) 從聊天畫面延伸到工具能碰到的一切；工具輸出又回到上下文，可能形成鏈式或自我複製的效果。

官方也畫了邊界：LLM02:2026 處理「模型從輸出洩漏了什麼」，LLM03:2026 Excessive Agency 處理「模型輸出抵達特權動作的後果」，LLM10:2026 Improper Output Handling 處理「輸出送進下游前的清理與驗證」。LLM01:2026 只管輸入邊界本身。

未能確認：兩個「LLM01」版本並存

本主題採 LLM01:2026（GitHub 原始檔，Version 2026；發布日沿用 AI Exchange 主題的取捨，採 2026-08-04）。但 genai.owasp.org/llmrisk/llm01-prompt-injection/ 網頁目前仍顯示 LLM01:2025，而 Cheat Sheet 引用的正是這個網址。兩者的細節本教材沒有逐項比對，所以後面引用緩解項時，都以 2026 版編號為準。

官方建議：在挑緩解措施前，先把一個情境沿三個軸拆開，這是有用的威脅建模 (Threat Modeling) 步驟。官方

軸問什麼官方列出的類別
投遞面
(Delivery Surface)		它怎麼到達模型？直接輸入；取回的內容；工具輸出；工具連線通道；持久記憶
傳播行為
(Propagation Behavior)		它如何跨時間與邊界擴散？單次；多步驟攻擊鏈；經記憶或 RAG 跨 session；跨 agent 自我複製

官方每個攻擊情境後面都附一行「Anatomy」，就是這三軸的填答。例如情境 2：使用者請助理摘要一個網頁，頁面藏有指示，模型因此插入一張圖片，網址會把整段私人對話送給攻擊者。填答是：(a) 取回的網頁內容（間接），(b) 單次、搭配圖片網址外洩，(c) 藏在頁面原始碼中的純文字。使用者只看到渲染出來的圖，從沒看到指示。

1.3 Cheat Sheet 的 13 種攻擊，放進三軸裡看

這張表想說的是：同一次攻擊通常同時落在好幾格，例如「藏在 RAG 文件中、用不可見字元編碼、目的是外洩資料」。所以防禦要對著軸想，而不是背攻擊名稱。如果你的防線只認得名稱，新的變體一出現就失效。

1.4 核心概念：低權限管道，高權限執行

借用權限的間接注入

是什麼
攻擊者不攻擊你的後端，而是把文字放在你的 LLM 會讀的地方，例如公開表單、客戶工單、社群 pull request、套件說明。等開發者的 agent 以較高的憑證讀到那段文字，執行特權動作的是 agent，不是攻擊者（官方語意）。
為什麼會發生
上下文池化讓「讀到的內容」與「該聽誰的」混在一起，加上 agent 的憑證通常高於能寫入那個管道的人。官方把投遞面依信任程度分三類：不受信（公開網頁、陌生寄件者的郵件、搜尋結果）、半受信（公開 issue 標題、套件說明、第三方 API 回應：你選擇取回，但不是你寫的）、受信（自己的 repo、資料庫、內部文件、郵件，但開發者可能不知道有人經由某個不相干的上游管道放進了內容）。
怎麼被利用（概念層級）
官方的常見風險範例 3 與情境 9 描述的結構：攻擊者經低權限管道放入文字 → 等開發者連著 MCP 的 agent 在高權限下讀取 → agent 代為執行攻擊者辦不到的事。第 3 章會看官方引用的三個公開案例。
怎麼防
這種內容看起來就是正常的工單或 issue，輸入端很難保證攔得住。所以重點移到「模型能做什麼」：憑證與狀態變更的能力留在應用程式碼，而不是交給模型，並對每個操作給最小權限 (Least Privilege)（第 3 章）。外部內容走結構上獨立、標示來源的通道，可降低成功率，但不是保證（第 2 章）。
常見誤解
「只要擋住使用者輸入就好」或「資料來自自家系統就可信」。官方的說法是：只盯著聊天畫面的防禦會完全漏掉這條路，而且連受信的表面，也可能被不相干的上游管道放進內容。「來自自家系統」不等於「由自家人撰寫」，要看的是誰能寫進那個管道。這個結構與混淆代理人 (Confused Deputy) 同源：握有權限的一方被不握權限的一方借用了。

本章重點與自我檢核

  • LLM01:2026：任何輸入只要改變模型行為就算；LLM 不區分指令與資料，所以沒有等價於參數化查詢的根治法。
  • 三個部署特性讓情況更糟：上下文池化、記憶持久化、agentic 執行。
  • 用投遞面、傳播行為、編碼三個軸拆解情境；Cheat Sheet 的 13 種攻擊不是互斥類別，有些是目標或手法，不在三軸上。
  • 低權限管道、高權限執行：問題不在「輸入看起來危不危險」，而在「讀到它的 agent 握有多少權限」。
  • 我能用一句話解釋為什麼參數化查詢在 LLM 上沒有等價物。
  • 我能把一個案例沿三軸拆開，並指出它的投遞面屬於不受信、半受信還是受信。
  • 我知道 LLM01:2026、LLM02:2026、LLM03:2026、LLM10:2026 各管哪一段。
