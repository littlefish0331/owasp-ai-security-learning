第 3 章　架構式防禦：工具邊界與限縮後果

  • 預估閱讀：約 9 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章；AI Exchange：最小模型權限；致命三要素 (Lethal Trifecta)

前面兩章的結論是：攔截會被繞過。這一章回答「那要把關在哪裡」。答案是工具邊界 (Tool Boundary)：模型提出動作，但由應用程式碼決定能不能執行。你會看到官方給的控制有哪些、各自是在降低成功率還是限縮後果，以及怎麼依你的架構挑選。

3.1 把關在哪裡：工具邊界

LLM01:2026 的緩解 #4 是官方在 agentic 部署中標為「承重」（load-bearing）的兩條之一（另一條是 #8）：憑證與狀態變更的能力要握在應用程式碼，而不是模型手上，並對每個操作給最小權限 (Least Privilege)；特權呼叫走一個確定性的政策引擎，在執行當下重新驗證意圖與參數。官方 Cheat Sheet 的安全實作管線也是同樣的順序：

  1. 辨識每個通道的不可信內容（取回文件、工具結果、對話歷史），與可信指令分開，但標籤不構成邊界；
  2. 在模型之外的執行程式碼裡，驗證工具參數並強制呼叫者的權限；
  3. 高風險操作先取得「針對該動作」的核准；
  4. 把模型輸出在每個下游用途都當成不可信，套用該目的地需要的控制（安全渲染 HTML、參數化資料庫查詢）；
  5. 用無害資料與可觀察的測試替身，測試上述邊界。

LLM01:2026 還給了一個為什麼必須如此的觀察：事件紀錄上多數高衝擊的提示詞注入 (Prompt Injection)，之所以嚴重，是因為注入落在一個工具、權限範圍或輸出渲染能力讓被攻陷的模型可以代表攻擊者、用使用者的權限行動的系統裡。

3.2 控制清單：降低成功率，還是限縮後果？

官方的說法是：有些控制降低注入成功率，預期會對適應性攻擊者 (Adaptive Attacker) 退化；有些控制限縮成功後的爆炸半徑 (Blast Radius)，能撐得住會探測系統的攻擊者。agentic 部署中，最小權限與能力預算是承重控制。下面把 LLM01:2026 的 11 項緩解放進這個框架。

3.3 核心概念：Rule of Two 與致命三要素

以能力預算檢查系統設計

是什麼
Rule of Two（出處標為 Meta AI, 2025）把一個 agent 的能力分成三項：(A) 處理不可信輸入、(B) 存取敏感資料或系統、(C) 變更狀態或對外通訊。官方建議把「三項同時具備」視為高風險：[A,B,C] 的 agent 每個動作都要人工核准；[A,B] 或 [A,C] 要有明確的殘餘風險評估。官方 官方同時引用 Simon Willison 的「致命三要素」(Lethal Trifecta, 2025) 作為同一結構診斷的另一種說法：能同時存取私人資料、讀入不可信內容、又能對外溝通，具備高衝擊外洩的條件，拿掉任何一項就拿掉條件。
為什麼有用
注入可以視為會發生。與其問「能不能擋住」，不如問「就算發生，這個 agent 同時握有幾項」。它把抽象的權限討論變成一張三格檢查表，容易在設計審查時使用。
怎麼被利用（概念層級）
官方情境 9 轉述三個公開事件（出處為 Invariant Labs、General Analysis、Koi Security 等 2025 年的報告），結構相同：攻擊者在低權限管道（公開 GitHub issue、客服工單、惡意 npm 套件）放文字，開發者的 agent 在較高憑證下讀到並代為行動。其中一例是以 service_role 執行、繞過列級安全 (row-level security) 的資料庫 MCP；另一例是一個惡意的郵件相關 MCP 套件，被估計影響約 300 個組織。這些細節是官方轉述的第三方報告，本教材沒有獨立查證。
怎麼防
拆掉其中一項（例如處理不可信輸入的 agent 看不到敏感資料；能存取敏感資料的步驟拿不到不可信內容；能對外通訊的步驟必須經過核准）；或讓三項分屬不同的隔離元件，元件間只傳遞受限的結構化結果。
常見誤解
「Rule of Two 保證安全」。官方明說它是下限(floor)，而且對自主程度（agent 能連續自己做多少步）沒有規定；[A,B] 或 [A,C] 並不代表沒風險，只是要有明確的殘餘風險評估。另外「核准」本身會疲勞：官方要求呈現實際動作而非摘要，因為不可見字元可以讓顯示的動作與實際執行的不同。

3.4 進階：把「讀」與「做」分開 —— 雙 LLM 與 CaMeL

如果拆掉一項能力做不到，還有一類架構是讓讀過不可信內容的模型，根本沒有能力呼叫工具。Cheat Sheet 介紹了兩個脈絡：

  • 雙 LLM 模式 (Dual-LLM Pattern)：Simon Willison 提出，把一個有工具權限的「特權」模型和一個讀不可信資料但沒有工具的「隔離」模型分開。Cheat Sheet 說它有已知缺陷，CaMeL 改進了這個提案（防止被注入的資料操縱工具參數）。
  • CaMeL (CApabilities for MachinE Learning)：Google DeepMind 提出。特權規劃：一個從不看不可信文件的規劃模型，把使用者請求寫成逐步計畫（程式碼形式）；隔離解析：一個零工具權限的隔離模型負責讀不可信內容並擷取資訊，即使讀到攻擊指示也無從行動；能力追蹤：一個自訂直譯器執行計畫，追蹤資料流圖，用中繼資料標籤(capabilities)強制安全政策。

Cheat Sheet 對 CaMeL 的警語（2026-10 修訂後）

  • CaMeL 擋下違反「已設定的能力政策」的工具呼叫；保護力取決於政策與相依性追蹤，論文也討論旁路通道風險。
  • 它的威脅模型假設使用者提示可信、記憶未被攻陷；它不防止誤導性的摘要或釣魚文字，只要受保護的資料流沒有被改變。
  • 釋出的程式碼是研究成果，不是受支援的安全元件：作者警告實作可能有安全錯誤，且不打算維護。

所以對一般團隊，CaMeL 比較像「看懂方向」：資料流與能力標籤，而不是直接拿來上線。你立刻能用的是它的精神：碰過不可信內容的元件，不要同時握有工具。

本章重點與自我檢核

  • 真正把關的是工具邊界：模型提出動作，由應用程式碼依呼叫者權限驗證參數、決定能不能做。
  • LLM01:2026 的 11 項緩解中，#4、#7、#8、#9、#10 是限縮後果，其餘多半降低成功率；agentic 部署以 #4 與 #8 為承重。
  • Rule of Two：不可信輸入、敏感資料、狀態變更或對外通訊，三項同時具備要每個動作人工核准；它是下限，不是保證。
  • 人工核准要顯示實際動作，量大時會疲勞。
  • CaMeL 的精神是「讀過不可信內容的元件不握有工具」；但其程式碼是研究產物，政策與威脅模型有限制。
  • 我能把一個 agent 的能力放進 A／B／C 三格，並說出該採哪種處理。
  • 我能說出為什麼「在 system prompt 寫規則」和「在程式碼授權」不是同一種控制。
  • 我知道 CaMeL 的三個角色，以及為什麼不能直接當作現成的安全元件。
