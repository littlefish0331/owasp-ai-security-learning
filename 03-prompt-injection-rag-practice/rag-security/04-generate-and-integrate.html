第 4 章　生成端、失效安全與整合

  • 前置：第 3 章；縱深防禦與失效安全 (Fail Securely)

內容已經通過寫入端與讀取端，進到提示詞了。最後一段要處理的是：模型怎麼用這些內容、它的輸出會去哪裡、以及任何一站壞掉時系統怎麼辦。這一章把 Cheat Sheet 的 Section 3、5、9、10、12、14 串起來，最後把整個主題接回 LLM09:2026、AISVS 與 AI Exchange。

4.1 上下文視窗與輸出驗證

上下文視窗 (Context Window)：Cheat Sheet Section 3 列出的風險是：取回的文件含有看起來像系統指令的文字；多個本身無害的區塊合起來構成對抗性提示；一份很長的文件把系統提示擠出模型的有效注意力範圍。它建議：

  • 用分隔符號標示「以下是不可信的檢索內容，只當資料」，並在檢索內容之後再次強調原本的系統指令（位置要逐模型測試，因為不同模型的注意力模式不同）；
  • 限制區塊數量與總大小；Cheat Sheet 建議的預設是 3–5 個區塊、總計 2,000–4,000 個 token（它自稱是合理預設，不是標準）；
  • 取回的區塊先掃描明顯的指令樣式；
  • 明確的原則：檢索內容是資料，不是命令。官方

作者整理，非官方：分隔符號只是降低機率，邊界在別處

同一系列的 Prompt Injection Cheat Sheet（2026-10 修訂版）明確寫道，文字標籤與提示措辭不是強制邊界，輸入篩選也不是安全邊界。這與 RAG Cheat Sheet Section 3 的建議並不衝突，但要讀得精確：分隔符號與掃描是降低機率的措施；真正的邊界是 Section 4（存取控制）、Section 9（輸出驗證）與 Section 10（工具授權）這類在模型之外、由執行層強制的控制。這是作者的讀法，兩份 Cheat Sheet 並沒有互相引用。詳細討論見提示詞注入主題的第 2 章。

輸出驗證 (Output Validation)：Section 9 稱它是「最後一道防線」：驗證所有模型輸出再交給使用者或下游；用政策過濾器遮蔽個資與憑證；工具呼叫用允許清單與結構化輸出（如 JSON schema）驗證；依提問者的存取層級遮蔽欄位。要避免的是：直接執行模型輸出、信任模型去落實政策（模型產生文字，不執行政策），以及因為取回的內容安全就假設產出也安全。官方

4.2 工具呼叫與失效即拒絕

RAG 很少獨立存在：取回的內容影響模型的決定，模型的決定觸發工具，工具執行不可逆的動作。Cheat Sheet Section 10 說，這是「理論風險變成實際傷害」的地方。它的控制有五項：

  1. 高風險動作（付款、刪除資料、對外 API 呼叫）要使用者明確確認；
  2. 工具層的授權檢查要獨立於模型的決定：「模型決定呼叫工具」不等於「使用者有權使用該工具」；
  3. 每個情境維護工具允許清單（客服 RAG 不該有付款工具）；
  4. 完整記錄：哪個查詢觸發哪次檢索、哪次檢索影響哪個輸出、哪個輸出觸發哪次工具呼叫；
  5. 熔斷器 (circuit breaker)：發現異常（工具呼叫量突增、呼叫從未用過的端點）就中止執行。官方

要避免的是：檢索內容未經驗證就影響工具執行、任意串接工具，以及假設「檢索被授權」就代表「後續的工具呼叫也被授權」。這與最小模型權限、提示詞注入的架構式防禦是同一種思路（作者整理，非官方）。

失效即拒絕 (Fail-Closed)：Section 14 的規則一句話就說完：管線任何元件失敗時，系統要拒絕請求，而不是退回到可能不安全的行為。它還有一個容易被忽略的觀點：失敗本身是資安事件，不是效能問題；攻擊者可能刻意製造失敗，迫使模型靠記憶回答。

4.3 來源歸屬、可觀測性與最低 CI 測試

來源歸屬 (Source Attribution)：Section 5 要求每個回應附上用了哪些文件與區塊、出處資料與文件雜湊，歸屬資料要簽章，並提供驗證端點。沒有出處，就無法事後偵測投毒文件是否影響了答案。官方

可觀測性：Section 12 要求不要把 RAG 當黑盒：用關聯 ID、文件 ID、授權決策、模型版本與工具呼叫結果追蹤每個請求。2026-10-04 的修訂加上：預設不要記錄原始查詢、被取回的內容、模型輸入輸出與工具參數，因為可能含機密或個資；調查需要時只留必要的、已遮蔽的欄位，放在受限的證據儲存區。官方 也要事先演練 RAG 專屬的事件應變：隔離被投毒的文件、使受影響的快取失效、找出收到受污染回應的使用者。

4.4 情境範例 D：檢索失敗時的客服 agent

情境 D（虛構）：晴川家電的客服助理

虛構 晴川家電是虛構的公司。他們的客服助理以 RAG 檢索保固與退換貨政策，並能呼叫「建立退款」工具。為了「別讓顧客看到錯誤訊息」，工程師設計：若向量資料庫檢索逾時，就讓模型「憑記憶」回答，並照常使用所有工具。

架構：顧客訊息 → 檢索（逾時時略過）→ LLM → 工具層（建立退款、查訂單）→ 客服介面。工具層信任模型送出的參數，沒有再確認使用者身分與權限。

  1. 發生了什麼：某段時間檢索端因容量事件頻繁逾時。逾時的對話中，助理沒有政策可依據，卻憑記憶回答，並在顧客多輪催促下建立了超出政策的退款。稽核發現：退款工具沒有獨立檢查呼叫者的權限，也沒有警示指出檢索失敗率升高。
  2. 哪一環出問題：(1) 檢索失敗時退回「只靠模型記憶回答」；(2) 工具授權依賴模型的決定，而不是由執行層獨立檢查；(3) 高風險動作沒有要求使用者確認；(4) 沒有熔斷器，也沒有把重複失敗視為資安事件。
  3. 對應條目：Cheat Sheet Section 14（失效即拒絕）、Section 10（工具呼叫）、Section 9（輸出驗證）、Section 12（監控）；LLM Top 10 2026 的 LLM03:2026 Excessive Agency（模型輸出到達特權動作的後果）。
  4. 該採什麼控制：
    • 檢索失敗時回傳錯誤，不回退到模型記憶；重複失敗發出警示（見 Section 14）；
    • 退款工具在執行層獨立檢查呼叫者的權限與參數，並以允許清單限制客服情境可用的工具（見 Section 10）；
    • 高風險動作要求明確確認，工具回傳值依 schema 驗證（見 Section 9、10）；
    • 對工具呼叫量與金額加熔斷器，並保留「哪個查詢觸發哪次工具呼叫」的追蹤（見 Section 10、12）。

注意 Cheat Sheet 的一個提醒：攻擊者可能「刻意製造檢索失敗」來迫使模型憑記憶回答。因此這個情境不需要任何高明的注入手法，只需要失敗時的不安全預設。

本章重點與自我檢核

  • 分隔符號與掃描降低機率；真正的邊界是存取控制、輸出驗證與工具層授權（作者整理的讀法）。
  • 輸出是不可信的，直到驗證：用允許清單與 schema 驗證動作，不讓模型落實政策。
  • 工具授權獨立於模型的決定；高風險動作要確認；有允許清單、追蹤與熔斷器。
  • 失效即拒絕：檢索、權限、雜湊、歸屬、快取任一失敗都不退回不安全行為；失敗是資安事件。
  • 可觀測性預設不記錄原始內容；八項最低 CI 測試可當整個主題的驗收清單。
  • 我能說出檢索失敗時為什麼不能退回模型記憶。
  • 我能說明為什麼「模型決定呼叫工具」不等於「使用者有權使用該工具」。
  • 我能對八項最低 CI 測試各說出它檢查的是管線的哪一段。
