第 3 章　LLMSVS：V1–V8 與版本

  • 預估閱讀：約 9 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 1 章；建議先讀 第 2 章 以便對照

LLMSVS (Large Language Model Security Verification Standard) 是另一份驗證標準，範圍比 AISVS 窄：只談使用大型語言模型的應用。它更早出現、篇幅更短（70 條需求），但版本狀態比較容易搞混：現行發布、候選版、草稿在不同地方有不同的標示。本章教你怎麼讀它，以及怎麼在引用時避開陷阱。

看幾條實際的需求（v2.0 原文意旨，標編號）：V5.1 與 V5.2 要求提示由受信任的伺服器端元件發出、且在伺服器端組成，而不是直接接受來自用戶端的完整提示（三級皆適用）；V5.13 要求把 LLM 輸出視為不可信，例如不要把輸出片段串接進 SQL，而是用參數化查詢或同等保護（三級皆適用）；V6.7 要求自訂外掛考慮目前已驗證主體的範圍，外掛不能存取超過該主體被授權的範圍（層級 2 起）；V7.4 要求備有軟體物料清單 (Software Bill of Materials, SBOM)，列出第三方元件、授權與版本（層級 2 起）。這些與前面主題的原則是同一回事：模型的輸入與輸出都不是信任邊界內的東西。

3.3 核心概念：層級標示，以及草稿為什麼要把它寫成「累積式」

v2.0 的勾選表與 v2.1 草稿的累積式定義

是什麼
v2.0 的每條需求有三欄（L1、L2、L3），在適用的層級打勾。LLMSVS 2.0 把三級描述為：層級 1 基本、層級 2 中等（敏感資料，如個人助理、處理客戶資料的 API、處理內部資料的系統）、層級 3 高保證（營運關鍵、金融交易、受特定產業規範如醫療資料）。
從表裡看到什麼（作者計數）
作者數了 v2.0 的勾選：70 條裡，17 條勾在三級、33 條只勾 L2 與 L3、20 條只勾 L3；也就是 L1 欄 17 條、L2 欄 50 條、L3 欄 70 條，沒有「只勾 L1」或「只勾 L2」的列。換句話說，勾選形式上是巢狀的：層級 3 包含全部。作者整理，非官方：這是作者從表格的勾選樣式推出的觀察，v2.0 文件沒有用文字明說「層級是累積的」。
v2.1 草稿改了什麼
草稿的前言明文定義「層級是累積式：層級 2 包含層級 1，層級 3 包含層級 2」，並規定：先選層級再測試；不要因為不方便就拿掉層級 1 的列；功能不存在時，該列標為「不適用 (Not Applicable)」，並寫一行理由。
為什麼這個差別重要
當報告只說「通過層級 2」時，讀者需要知道這代表什麼：是只做了標 L2 的列，還是包含 L1？草稿把它寫清楚，並讓「不適用」成為明確結果，避免「覺得很難所以沒做」被誤標成不適用——草稿也特別區分：「我們沒做檢索，所以 4.3 不適用」成立；「我們有做檢索，但 4.3 很難」是失敗 (Fail)。
常見誤解
「v2.1 已經是現行版本，直接引用它。」不行：README 明說草稿不是發布，要引用 v2.0，直到專案接受新版為止。

未能確認：Releases 標籤與 README 的落差；草稿附屬檔案

(1) 標籤不一致：README 寫「v2.0 是 current release、v2.1 是草稿且不是發布」；但 GitHub Releases 頁把 2.0 標為「v2.0 release candidate」（預發布 prerelease，2026-05-11），把 2.1 標為「V2.1 Draft version」（2026-10-23，未標預發布）。同一天 2026-05-11 還建立了 1.0 release。哪一個標示才是專案的正式狀態，本教材無法判斷。教材依專案自己在 README 與 CHANGELOG 的明文，把 v2.0 當現行發布、v2.1 當草稿。

(2) 附屬資料夾：README 提到草稿附有 mappings/crosswalk.md、profiles/、examples/worked-assessment.md、catalog/llmsvs-draft.json，但本教材在 main 讀取倉庫根目錄只看到檔案（CHANGELOG、CONTRIBUTING、LICENSE、三份標準文件、README、leaders），mappings/crosswalk.md 讀取為 404。所以草稿說的 crosswalk 與範例評估，無法確認它們存在，教材不引用其內容。

3.5 官方對認證與審查方式的明文立場

LLMSVS 2.0 有一整節寫「評估與認證」，這些是官方明載、也是你引用時最容易被誤用的地方：

  • OWASP 目前不認證任何廠商、驗證者或軟體。任何聲稱「LLMSVS 認證」的保證、信任標章或認證，都不是 OWASP 審核、註冊或認證的；信賴這類說法的組織要謹慎。官方也說這不該阻止組織提供保證服務，只要不聲稱是 OWASP 官方認證。
  • 建議「開書 (open book)」審查：讓評估者能接觸架構師、開發者、專案文件、原始碼與已驗證的介面，並每種使用者角色至少一個帳號。
  • 範圍：LLMSVS 只涵蓋與 LLM 使用及整合有關的需求；一般網路服務等非 LLM 特有的控制，要用 ASVS 等標準另外驗證。
  • 報告內容：清楚定義驗證範圍（特別是排除項）、概述通過與未通過的測試，並附上處理失敗的指引。
  • 證據：業界慣例要求詳細記錄驗證過程，包含工作底稿、截圖、重現問題的腳本、與 proxy 日誌等電子測試記錄；只靠自動化工具的結果不夠，文件必須能提供對所有控制都已被徹底測過的確切證據，發生爭議時要能證明每個被驗證的控制確實被測過。

v2.1 草稿保留了同樣的原則：通過需要證據，廠商問卷或掃描報告單獨不構成通過。
