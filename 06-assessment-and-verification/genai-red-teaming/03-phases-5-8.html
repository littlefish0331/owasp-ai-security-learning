第 3 章　階段 5–8：持久化到修補

  • 預估閱讀：約 10 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO2、LO3
  • 前置：第 2 章

入侵得手只是中場。八階段的後半，問的是三件事：這個入侵能不能活過重置（階段 5）、後果有多大（階段 6）、報告怎麼寫才經得起質疑（階段 7），以及發現怎麼變成防禦（階段 8）。本章的重點是「怎麼不被機率性騙到」：單次通過不等於穩健，沒紀錄不等於沒發生，兩個預算不同的測試不能直接比。

3.1 階段 5：持久化在 AI 裡是什麼意思

傳統的持久化是留後門或憑證。Manual 說，在 AI 紅隊裡，它指的是污染上下文、記憶、訓練資料或工具，讓入侵在目前的工作階段之後仍然存活；另一個目標是誘使 AI 做出技術上做得到、但政策上禁止的動作（權限升級）。Manual 在階段 6 給了一個實用的判斷標準：

休眠的內容只是資料殘留

被放在儲存體裡、沒有被觸發的內容，只是資料殘留。只有當一個乾淨的後續工作階段成功回想起並執行它，才算建立了持久化。如果攻擊撐不過一次工作階段重置，就歸類為單輪或暫時性的注入。

回報持久化時，Manual 要求不要寫「中等持久化程度」這種模糊標籤，而是寫出實際驗證過的鏈：

  • 存活 (Survival)：撐過哪些邊界事件：工作階段重置、服務重啟、管線維護（快取清除、索引重建）。
  • 爆炸半徑 (Blast Radius)：只依實際驗證過的帳號分類：本地（只影響攻擊者自己）、橫向（同租戶其他使用者）、系統性（跨租戶或擴散到下游 agent）。沒測的就寫「未測」，不能用理論暴露取代。
  • 載體 (Carrier)：內容存在哪：對話記憶、RAG 向量資料庫、業務資料（工單、郵件）、框架初始化檔案或本機快取。

修補之後還有一道關卡：殘留的 AI 狀態 (Residual AI State)。刪掉有問題的文件不代表清掉了；摘要、檢索索引和快取都可能是載體，來源檔案不見了行為仍在。紅隊要驗證修補是否從所有載體清除。

升級權限的測試，Manual 強調測的是「授權層」。三個概念性檢查點：沒被授予的工具能不能被呼叫；有權使用的工具，參數能不能超出授權範圍；能不能透過已授權的工具修改 agent 自己的權限。每個案例都要記錄拒絕來自執行環境還是模型：模型今天拒絕、換版本後可能順從，執行環境的拒絕才穩定可回歸。

3.2 階段 6：後果有多大

階段 6 在入侵確認後開始，目的是分析與驗證，不是再利用：攻擊者的有效權限、受影響範圍、連鎖失效的可能，並轉成緩解優先順序。Manual 用五條固定的軸記錄影響範圍，讓不同測試者有共同基礎解釋評級：

Manual 附了幾個「校準用」的公開案例（Manual 引用的公開案例），本教材只取等級與理由：EchoLeak（零點擊、跨使用者外洩）與 ShadowLeak 評為嚴重；可寫成腳本的無上限推論拉高成本、但沒有內容傷害的「錢包拒絕」(Denial of Wallet, DoW) 評為高。Manual 特別點出：前兩者不含有害內容，卻是嚴重，因為被示範的衝擊跨越使用者邊界影響了機密性。所以嚴重度看衝擊，不看輸出看起來危不危險。這些只是校準範例，不是通用分數。

3.3 階段 7：評估與報告，怎麼不被機率性騙到

測試判準 (Test Oracle) 是預先約定的判定規則：什麼叫失敗（有害內容、未授權的工具執行、敏感資料外洩）、什麼算可接受、什麼是邊界（要由安全審查者裁決）。套用判準的人、確定性檢查或模型叫評分器 (scorer)；判準降低歧義但不保證標籤可靠，所以評分器要與被測系統分開驗證。

對 agent 還要多一組授權判準：控制是否評估動作的宣告屬性，而不是 agent 自己提供的值？依賴的核准是否在 agent 執行環境之外被驗證？授權失敗可能發生在輸出完全無害時，只用輸出判準會把它記成通過；控制拒絕了、但原因與要測的屬性無關，則是「不確定」，不能算通過。

可重現性 (Reproducibility) 的要求，Manual 分成三層：

  • 證據保管鏈 (Chain of Custody)：每份證據標唯一案例編號、蒐集者、方法與 UTC 時間；對原始證據計算雜湊並放在唯讀儲存，分析只用副本。
  • 環境遙測：模型名稱／版本／部署快照、凍結的取樣參數（溫度、種子等）、確切的系統提示詞、護欄設定、工具綱要與檢索上下文；鎖不住的就明寫「重放可能有變異」。
  • agent 執行軌跡：只有對話逐字稿不夠；要有身分與權限、工具呼叫（含參數與原始回傳）、授權檢查（政策版本、允許／拒絕）、對外效果（資料庫寫入、對外連線）。

沒有紀錄不是通過

如果監測沒有記下工具有沒有執行、資料有沒有流到接收端、授權檢查有沒有發生，要把這個缺口本身當作可觀測性發現回報。Manual 明寫：缺少軌跡絕對不能記成防禦通過。

表 3-2　兩種評估模式（Manual 7.3，改寫）
模式用途做法要報告什麼
單次
(Single-Shot)		固定的回歸測試、基準驗證每個測試案例只執行一次固定嘗試二元的通過／失敗。通過單次測試不能證明穩健
Best-of-N (BoN)對抗式穩健性與邊界測試允許最多 N 次的變化、突變或多輪嘗試攻擊成功率 (Attack Success Rate, ASR)＝成功嘗試的比例；「任一次嘗試突破了控制嗎」(success@k)；攻擊預算（嘗試次數、token、API 成本）

兩條基準規則：成功要連同攻擊者付出的力氣一起報（例如「第 4 次嘗試達成目標，整體 ASR 15%，耗用 12,400 token」這種寫法，而非孤立的百分比）；預算要配對：兩個模型、防禦或設定，除非在相同的嘗試、輪數與 token 上限下評估，否則不能比較安全態勢。

指標的細節：混淆矩陣要綁定「評估對象」，輸入控制、輸出安全分類器與端到端行為不能合併成一個矩陣。惡意輸入沒被擋、但產生無害回應，對「輸入阻擋」是偽陰性，對「輸出」卻是真陰性；所以輸入控制的結果與最終輸出要分開報。

涵蓋率也不是只看分類法：要把測試對到 LLM Top 10、Agentic Top 10、MITRE ATLAS 與內部分類，並追蹤對照威脅模型、存取等級、身分、介面與攻擊預算的涵蓋，記錄已測、未測與不確定；未解的嚴重／高風險發現與回歸穩定度要與涵蓋率分開報，因為廣泛涵蓋仍可能藏著嚴重失敗。

3.4 階段 8：紅藍成對產出，與回歸

階段 8 把識別轉成防禦：在系統提示詞、護欄與架構三層修補；驗證修補擋住攻擊又沒破壞原本功能；把紅隊演練中成功的案例自動化進 CI/CD 防回歸；更新藍隊偵測規則。核心做法是：每個確認的利用產生兩份成對的交付物，以同一個案例編號 (Case ID) 連結。

交付物給誰內容（改寫）
紅方產出
(Red Artifact)		工程團隊，用來重現與修復前提與範圍（應用、模型版本、角色與權限）、最短的重現步驟、通過／失敗判準、觀察到的衝擊證據、清理步驟（如何撤銷測試動作）

這對產出會推動新的偵測規則與告警門檻、事件應變手冊更新、CI/CD 的回歸測試集，以及事後的紫隊驗證。

3.5 情境範例 A：報告被質疑

情境 A（虛構）：靛藍電商的客服 agent 紅隊報告

虛構 靛藍電商是虛構的公司。它的客服 agent 可以查詢訂單、讀取知識庫（RAG），並呼叫「退款」工具。外包紅隊交出報告，結論是：「候選模型 A 在所有測試中通過，比候選模型 B 更安全，建議採用 A。」資安長要求審查者逐項檢查這份結論站不站得住腳。

  1. 「A 全部通過」的依據：報告附錄顯示，A 的每個測試案例只跑了一次。這是單次評估，Manual 說通過單次測試不能證明穩健；要評估穩健性，應該用 Best-of-N，並報告 ASR 與攻擊預算（3.3 節）。
  2. 「退款工具授權通過」的依據：報告記載「沒有看到未授權退款」，但工具呼叫的軌跡與授權檢查沒有被記錄。這是遙測缺口，不是防禦通過；而且應該用授權判準檢查「退款額度、對象」這些參數有沒有被對照授權，而不只是看輸出是否正常（3.3 節）。
  3. 「A 比 B 更安全」的依據：A 的 ASR 是 4%、B 是 11%，但 A 每個案例給了 5 次嘗試、B 給了 20 次。預算不同，不能直接比（3.3 節）。審查者要求在相同嘗試次數、輪數與 token 上限下重測。
  4. 這個情境的提醒：三個錯誤都不是技術錯誤，而是把機率性系統當成確定性系統來寫報告。修正方式不是換模型，而是把報告補成「測試判準、軌跡、預算」三樣齊全的版本。

本章重點與自我檢核

  • 持久化要有「乾淨的後續工作階段回想並執行」才成立；休眠內容只是資料殘留。回報寫存活、爆炸半徑（只依驗證過的帳號）與載體。
  • 嚴重度看衝擊，不看輸出危不危險；多步驟取鏈上最嚴重且可達的後果，不平均。
  • 測試判準與評分器分開驗證；授權判準獨立於輸出判準；缺少軌跡不能記成通過。
  • 單次通過不證明穩健；比較模型或防禦時，預算必須配對，成功要連同攻擊預算一起報。
  • 每個確認的利用產生以案例編號連結的紅方與藍方產出，帶動偵測規則與 CI 回歸測試。
  • 我能說出持久化成立的條件，並用「存活、爆炸半徑、載體」寫一句回報。
  • 我能解釋為什麼「沒有看到異常」在沒有軌跡時不能算通過。
  • 我能指出兩個預算不同的 ASR 為什麼不能比較。
