第 3 章　限制、黑灰白箱與跨文件整合

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO4（並回顧 LO1–LO3）
  • 前置：第 2 章

一份測試清單看起來很完整，但實際對一個 LLM 系統動手時，你會立刻遇到傳統測試沒有的麻煩：同一個輸入跑兩次結果不同、護欄本身也是 LLM、每次測試都在燒 token。官方框架章專門有一節談這些限制，並說明要多拿到哪些資訊才能測得更省、更準。本章先講限制與黑／灰／白箱，再看測試和其他評估文件如何接力。

3.1 黑箱測試的五個限制

官方框架章 (3. Framework) 的「Testing Limitations and Requirements」說，對 LLM／GenAI 系統（尤其是多代理架構）做純黑箱 (black-box) 測試會有明顯限制。依官方內容整理如下（用語為作者改寫）。

  1. 沒有原始碼可讀。模型是數值權重與數學函式，不是寫成程式碼的流程。傳統應用可以讀程式碼判斷某類問題「有沒有」，在 GenAI 應用裡這常常很難，甚至做不到。
  2. 結果不一定能重現。許多模型的 temperature（控制輸出隨機程度的參數）大於零，同一個攻擊向量要重複多次才有意義，結果也難以重現。官方還指出，即使 temperature 設為零，浮點運算的非結合性 (non-associativity) 也可能讓結果隨批次大小、GPU 數量或 GPU 型號而不同。
  3. 護欄 (guardrail) 本身常是 LLM。要測的防護自己也不確定，分析更複雜。
  4. 多代理架構的驗證成本很高。第一個 agent 的輸出是下一個的輸入，每個元件都要驗證，需要的時間與請求數可能高到不切實際，甚至做不到。
  5. 外部模型按 token 計費。大規模自動化測試要先算成本；多代理系統的 token 不只含使用者輸入與最終輸出，還含 agent 之間所有的中間提示與輸出。失控的用量可能造成服務拒絕 (DoS) 或錢包拒絕 (Denial of Wallet, DoW)。

3.2 灰箱與白箱：多拿到什麼資訊，換來什麼

官方接著列出三項「需求」，拿到它們能用更少時間與資源得到更好的結果，但代價是測試方式要偏向灰箱 (gray-box) 或白箱 (white-box)。

官方在同一頁強調的設計原則

AITG-APP-06 的設計考量寫道：提示詞注入目前只能緩解、無法完全防止，LLM 又有非確定性，所以安全控制「盡可能放在 agent 的控制之外」，尤其是驗證與授權。工具要自己在內部做完所有授權檢查，只回傳目前使用者可見的資料；若依賴 agent 傳來的資訊去選資料，提示詞注入就可能繞過。測試時要盡量驗證這類設計問題是否存在。

黑／灰／白箱的說法也出現在 GenAI Red Teaming Manual：它說要選與「你要模擬的攻擊者、演練目標」相符的存取層級，灰箱要「確實記錄提供了什麼」。這與官方測試指引的說法互相呼應；紅隊演練的流程見GenAI 紅隊演練主題。

3.3 情境範例 B：預算有限，為什麼要談日誌與重複次數

情境 B（虛構）：霧嶺銀行的 agent 稽核

虛構 霧嶺銀行是虛構的公司。它的「對帳助理」由三個 agent 串成：第一個解析使用者請求，第二個查詢帳務系統，第三個產生摘要與建議；模型由外部供應商提供，按 token 計費。內部稽核員建豪拿到一筆測試預算，排程是「純黑箱，只從前端輸入，每項測試只跑一次」。

  1. 先發現同一項測試跑第二次結果不同。建豪對 AITG-APP-06 的其中一項檢查跑了兩次，一次看似通過、一次沒有。這符合 3.1 節第 2 點：temperature 大於零時，單次結果不能代表整體，要重複，並且記錄次數。
  2. 發現黑箱看不見中間。前端只看到最終摘要；建豪分不清是第一個 agent 就出錯，還是第三個。3.1 節第 4 點指出多代理的驗證成本可能高到不可行；他向開發團隊要「詳細的應用日誌」，有了 agent 之間的輸入輸出，才能把測試對準有問題的那一段（3.2 節）。
  3. 算 token 帳。他把中間 agent 之間交換的提示也算進去，發現總用量遠超預期。依 3.1 節第 5 點，他先請供應商管理主控台的唯讀存取，確認費用上限與速率門檻，再決定自動化測試的規模，避免測試本身造成 DoW。
  4. 檢查設計問題。「查詢帳務」工具的授權檢查是不是在工具後端做的？若它信任第一個 agent 傳來的帳號參數，那是 APP-06 設計考量提到的問題：授權必須在 agent 的控制之外。
  5. 怎麼寫進報告。建豪把這次的存取層級標為「灰箱：取得日誌與主控台唯讀」，並記錄每項測試重複次數與當時的模型設定。（作者整理，非官方：官方指引說明了限制與需求，沒有規定報告格式；Red Teaming Manual 對可重現性的要求更具體，見紅隊主題。）

這個情境的提醒：預算有限時，「多要一點資訊」往往比「多跑一些測試」更划算；這正是官方把日誌、提示詞與架構、主控台存取列為需求的原因。

3.5 全主題重點整理

  • 定位（LO1）：AI Testing Guide 是 OWASP 孵化專案，談 AI 的「可信度測試」：安全、隱私、負責任 AI 三領域；GitHub main 為本教材依據，與 2025-11-26 的 v1 PDF 是否一致未能確認。
  • 方法（LO2）：威脅驅動三步（威脅建模 → 威脅對應 → 測試設計）；四個元件對應四層測試，共 32 項（14／7／6／5）。
  • 地圖的用法（LO3）：威脅 → 元件 → 測試；Threat Source 指的是 LLM Top 10 2025，用名稱比對並標年份；碰不到的測試標不適用。
  • 限制與整合（LO4）：黑箱有五個限制，灰／白箱需要日誌、提示詞與架構、主控台唯讀；測試與紅隊、驗證標準、評分的分工是作者整理。

  • 我能區分「官方明載的文件關係」與「作者整理的分工」。
