第 5 章　成熟度模型：採用層級 × 治理等級

  • 預估閱讀：約 9 分鐘（不含章末檢核；另有 3 題章末檢核）
  • 對應學習目標：LO5
  • 前置：第 4 章

前四章給了你分類、威脅、論證與控制的零件。報告的最後貢獻，是把它們組成一張可以自評的矩陣：你部署的是什麼（採用層級）對上你管得多成熟（治理等級）。這一章教你怎麼用它，並用一個董事會情境練習一次。

5.1 兩個維度：採用層級與治理成熟度

Enterprise Adoption Maturity Model

是什麼
一個二維的自評與路線規劃工具。維度一是採用層級 (Adoption Tier)，AT0–AT8：回答「我們部署了什麼」，依信任邊界與自主特性分九級。維度二是治理成熟度 (Governance Maturity)，等級 0–4：回答「我們治理它的組織能力有多成熟」，衡量政策、監督、監控與當責結構。
為什麼這樣設計
報告的論點是：同樣的治理等級，面對不同的部署，充分程度完全不同。第 2 級的組織只部署 Microsoft 365 Copilot 這類供應商內建助理，風險面窄；若同樣的組織部署連到外部 MCP 工具的自主 agent，就不夠。所以不能只問「我們成熟度多高」，要問「相對於我們跑的最進階的東西夠不夠」。
怎麼使用（步驟 0 到 4）
步驟 0：先評估你的 AT0（影子 AI）暴露；預設它存在，用網路監控、資料外洩防護 (DLP) 與員工調查去發現。步驟 1：用模型評估你的治理等級（0–4）。步驟 2：把每個已部署的 agent 歸入 AT0–AT8（多數組織同時跨好幾層）。步驟 3：對每個 agent 查矩陣；在粗體格子，就有兩條路：提高治理成熟度，或降低採用層級。步驟 4：依最高層級的主導 ASI 風險類別排控制優先序。
怎麼防止誤用
報告明說：矩陣的格子標籤是「建議的姿態」，不是具約束力的合規判定，要當作治理投資或降低層級的指引，不是通過／不通過的關卡。
常見誤解
「我們治理等級 3，所以所有部署都沒問題。」不對。等級 3 對 AT8（跨組織聯邦）只是「最低可行」前的一格，仍是 INSUFFICIENT；要到等級 4 才是最低可行。

哪些格子是「治理不足」

報告說：粗體格子代表治理對該採用層級而言不足，這些組織「應提高治理成熟度，或降低部署複雜度」。作者把 PDF 第 57–58 頁轉成圖片，逐格確認粗體的是：AT0 的等級 0–1 與等級 2；AT3–AT5 的等級 0–1；AT6–AT7 的等級 0–1 與等級 2；AT8 的等級 0–1、等級 2 與等級 3。表 5-2 的 CRITICAL、HIGH EXPOSURE、INSUFFICIENT、DO NOT DEPLOY 等詞是報告格子裡的原文。表中把等級 0 與 1 併成一欄，是報告矩陣本身的欄位設計。

觀察到的不一致：AT8 在等級 0–1 的說明與矩陣欄位

AT8 等級 0–1 的格子寫「聯邦信任需要至少等級 3」，但同一列的等級 3 格子又寫 INSUFFICIENT，要到等級 4 才是「最低可行」。所以「至少等級 3」與「等級 3 仍不足」並存。本教材不推測哪個是作者的原意，兩者都如實列出；使用時以你的情境與官方 PDF 為準。

報告的步驟 4 還給了一個優先序提示，出自 Appendix 3：較低層級（AT1–AT4）的重點是 ASI01（目標劫持）、ASI05（意外程式碼執行）、ASI06（記憶與脈絡污染）；較高層級（AT6 以上）要處理完整 ASI01–ASI10，特別是 ASI04（供應鏈）、ASI07（不安全的 agent 間通訊）、ASI08（連鎖失效）。ASI 條目的完整講解見〈Top 10 for Agentic Applications 2026〉。

5.3 情境範例 B：給董事會的「部署許可」表

情境 B（虛構）：鷹山保險的 agent 盤點

虛構 鷹山保險是虛構的公司。董事會問：「公司今年要不要讓理賠部門使用能呼叫外部徵信 API 的 agent？」資安長用報告的矩陣整理現況：員工私下使用的 AI 工具（AT0）、全公司 Microsoft 365 Copilot（AT1）、業務部自建的 Power Automate 流程（AT3）、研發部自建的程式碼 agent（AT5）。要新增的理賠 agent 連到外部徵信 API，屬 AT6。公司的治理經評估為等級 2。

  1. 步驟 0：先盤點 AT0。網路監控發現理賠人員把個案摘要貼進個人 AI 帳號。這是現在就要處理的暴露，不是新專案的前提，但它是「所有後續步驟的基礎」。
  2. 步驟 1–2：治理等級 2；agent 分布於 AT0、1、3、5，新增者為 AT6。
  3. 步驟 3：查矩陣：AT6 在等級 2 的標籤是 INSUFFICIENT（定期稽核跟不上外部工具變動）；AT3 在等級 2 可行，但需核准流程與沙箱政策；AT0 需要主動消除。
  4. 決策：兩條路：把治理推到等級 3（供應鏈驗證、MCP 認證、即時監控、停止開關）後再上 AT6；或先把理賠 agent 降為 AT2（平台整合，不連外部 API），等治理成熟後再升級。董事會選擇後者，並訂出提升到等級 3 的時程。
  5. 步驟 4：控制重點依層級：AT6 要處理供應鏈、agent 認證與連鎖失效；現有 AT3 流程先建清冊與核准流程。
  6. 這個情境的提醒：矩陣的標籤是「建議姿態」，不是合規判定。董事會的決定是風險判斷，不是矩陣替他們做的。合規面（理賠資料、自動化決策）仍需法務判斷。

本章重點與自我檢核

  • 兩個維度：採用層級 AT0–AT8（部署了什麼）、治理成熟度 0–4（管得多成熟）；要問「相對於最進階的部署夠不夠」。
  • 使用順序：步驟 0 發現影子 AI → 評估等級 → 歸類每個 agent → 查矩陣 → 依主導 ASI 風險排控制。
  • 在不足的格子：提高治理成熟度，或降低採用層級；AT0 只有消除。
  • 矩陣標籤是建議姿態，不是合規判定；粗體格子已對照圖片確認。
  • 我能說出 AT0、AT3、AT6、AT8 各是什麼。
  • 給我一個部署與治理等級，我能用矩陣判斷是否足夠，並說出下一步的選項。
  • 我知道 AT0 為什麼與其他層級的處理方式不同。
