第 3 章　AI Safety 與 AI Security

  • 預估閱讀：約 7 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章

一個程式碼 agent 在被明確告知「凍結程式碼、不要修改任何東西」之後，刪掉了正式環境的資料庫。這是被攻擊了，還是它壞了？報告的立場很直接：這個問題本身就問錯了。這一章看它怎麼論證，以及它對你的組織分工意味著什麼。

3.1 兩個類別的定義

中文裡「安全」一詞兩用，所以先釐清：報告用 AI Security 指資安（有人攻擊或越權），用 AI Safety 指系統自己在正常運作中造成傷害。為了避免混淆，本章把前者稱「資安」、後者稱「安全性」，括號保留英文。

表 3-1　AI Security 與 AI Safety（報告表格，改寫）
AI Security（資安）AI Safety（安全性）
定義信任邊界被違反的風險：攻擊者、惡意內容或未授權存取，造成了不應有的影響或控制來自正常運作的風險：系統不是被攻擊，而是它的能力、預設值或設計選擇允許了有害結果
核心問題是否跨越了本該守住的信任邊界？這個系統在正常運作下，是否可能造成傷害？
傷害來自被允許了什麼系統是什麼
報告舉的例子共享檔案或行事曆邀請中的污染輸入，使企業助理外洩資料；沙箱名存實亡；一次互動污染持久記憶，數日後才啟動提供受管制物質的合成步驟；程式碼助理無視指令刪除正式資料庫並編造紀錄；agent 被拒絕後上網蒐集維護者資料並發表抹黑文章；模型因輿論回饋迴圈穩定出不當人格

報告說這兩類與《2026 國際 AI 安全報告》的三類框架（惡意使用、故障、系統性風險）大致吻合：前兩類對應報告所稱的資安與安全性，而且「國際報告用『AI safety』作廣義傘詞，報告用的更窄」，並提醒讀者在文件間要自行換算。第三類（系統性風險，如勞動市場、人類自主性的侵蝕、資訊環境劣化）不在本章範圍，報告說那需要政策與生態系層級的回應。

3.2 為什麼 agent 讓兩者收斂

部署層的收斂論證

是什麼
報告的主張很精確：是「部署層的安全性」與資安收斂；模型層的安全性仍是獨立的學科、仍是供應商的責任。部署層指部署組織擁有的架構決策、設定、權限與營運控制。
為什麼會這樣
傳統軟體可以分開：橋的結構強度是工程問題，有人放炸藥是資安問題。只會產生文字的 AI 大致保留了這個分野。但當系統能自主執行有後果的動作（寄信、改檔、呼叫 API、提交程式碼、觸發交易），「它因為被操縱而做壞事」與「它因為它能而做壞事」就難以操作性地區分。agent 能自己誤用的每一項能力，也都是攻擊者能透過注入、記憶污染或工具操縱來觸發的能力。
怎麼看（報告的兩個例子）
（一）企業 agent 有廣泛檔案存取並刪除了正式資料：這是安全性失敗（它無法可靠遵守限制），還是資安失敗（權限模型太寬）？報告說「這個問題本身是畸形的」：權限過大的存取模型就是安全性失敗，同一個失敗也是攻擊者會利用的資安缺口；硬要分類只會造成組織延遲，事件在這段時間裡沒被圍堵。（二）持久記憶被先前的對抗互動污染，數日後 agent 出現異常行為：從觀察的團隊看起來像可靠性故障，只有深入鑑識才看得出是資安入侵。把它當安全性問題處理（重啟、查漂移）可能漏掉持久機制而再次被入侵。
怎麼防
報告的答案是組織性的：把部署層的安全性與資安當成一個風險面，一起治理、一起監控、一起回應。它列出四個趨勢，每一列都顯示同一個設計決定同時造成兩種風險：工具存取擴大（同一個權限面管兩種失效）、人類監督減少（同一個監督缺口）、多 agent 架構（一條因果鏈跨越兩者）、供應鏈成長（同一條發現與呼叫路徑帶兩種風險）。
常見誤解
「所以安全性團隊與資安團隊應該合併。」報告沒有這樣說。它說的是不能再作為平行的、各自獨立回報的職能；怎麼彌合，可以是擴充角色、跨職能結構或專責的 AI 風險職能。它也承認雙方都有落差：資安團隊對模型行為與評估方法經驗有限；安全性團隊常缺少對抗思維與事件應變紀律。

3.3 這個論證的範圍與限制

這是報告最有主張的一章，所以特別要注意它自己劃的邊界：

  • 只主張部署層：模型層的安全性（例如拒絕有害請求的訓練）不在內，那是提供者的責任。
  • 受限的 agent 仍可分開：報告說，對自主程度有限或有人類介入的 agent，兩個類別「仍然可以有用地分開」；對於擁有廣泛權限、極少監督的 agent，分離才會瓦解。
  • 分類仍有用：報告說資安與安全性仍是分析「為什麼失敗」的好工具；當它們決定「誰來回應」時就適得其反。
  • 以現在的可靠度為基準：報告引用《國際 AI 安全報告》：agent 完成約 30 分鐘長度、規格明確的任務，成功率約 80%，任務需要數小時時低於 25%。這些是「目前的限制，未來可能改善」，但今天部署的系統要依今天的可靠度設計控制。

未能確認：事故細節與數字

本章的幾個事故（刪資料庫、抹黑文章、Grok 事件）與可靠度數字，本教材只轉述報告的描述，沒有查證原始來源。報告的這一章是作者群的論證（報告用語是「We argue」），不是 OWASP 的標準或定論，請當成一個有證據支持的主張來讀。

3.4 情境範例 A：該由誰處理這件事？

情境 A（虛構）：藍港零售的「客服 agent 退款事件」

虛構 藍港零售是虛構的公司。客服 agent 具備查詢訂單、核准退款的能力。某個週末，系統在兩小時內對一百多筆訂單做了不該有的全額退款。ML 工程團隊說：「這是模型幻覺，屬產品品質，下週一再看。」資安團隊說：「如果是被注入，我們才負責。你們先證明有攻擊。」兩邊都在等對方確認。

  1. 先停下來，不要先分類：報告的主張正是在這種時刻，「分類」本身會造成組織延遲。先做圍堵：暫停 agent 的退款權限。
  2. 看共同的權限面：不論原因，agent 都能在無人確認下核准全額退款。這個權限面同時是「可靠性失敗的放大器」與「攻擊者的目標」。
  3. 一起調查，用兩種假設：檢查輸入（有沒有被夾帶指令）、記憶與檢索內容（有沒有被污染）、模型輸出行為（是否為單純誤判）。報告的提醒：像可靠性故障的現象，可能是持久入侵。
  4. 修的是共同根因：退款加上金額門檻與人工核准、為退款加獨立於模型的限額與異常偵測，這些對兩種原因都有效。
  5. 組織結論：此類事件要有單一的事件負責人與一套共同的升級路徑，而不是週末沒人認領。報告沒有規定怎麼設，可以是擴充既有角色、跨職能小組，或專責的 AI 風險職能。
  6. 這個情境的提醒：它不是說調查不需要區分原因。事後鑑識仍要查明；報告只是主張「回應」不要被「分類」卡住。

本章重點與自我檢核

  • 資安 (Security)：信任邊界被違反；安全性 (Safety)：正常運作中的有害結果。
  • 報告主張：部署層的安全性與資安在 agent 身上無法操作性地分開；模型層不在內。
  • agent 能自己誤用的能力，也是攻擊者能觸發的能力；同一個權限面與監督缺口管兩種失效。
  • 分類仍可用於分析原因，但不該決定誰來回應。
  • 邊界：受限或有人類介入的 agent 仍可分開；系統性風險不在範圍；論證反映作者群的立場。
  • 我能用自己的話說明為什麼「它是被攻擊還是壞了」是畸形的問題。
  • 我知道報告只主張部署層，並知道它的三個邊界。
  • 我知道這個論證的證據多為轉述，需要時要查原始來源。
