你熟悉 AI 與軟體開發，但可能沒受過資安訓練。這一頁把後面反覆出現的資安詞彙，翻成你已經有的工程直覺。每個概念都用同一個格式：一句話定義、開發者類比、在 AI 系統裡長什麼樣子。

怎麼讀這一頁

標示 官方 的是 OWASP 文件有寫的內容；標示 作者整理，非官方 的是作者為了方便理解而加的類比或分類。類比有其限制，本教材會在該處說明。

1. 資產、威脅、漏洞與風險

資產 (Asset) 是值得保護的東西，例如資料庫、API 金鑰、模型權重、system prompt。威脅 (Threat) 是「可能發生的壞事」加上做這件事的人或手法。漏洞 (Vulnerability) 是系統的弱點。風險 (Risk) 則是威脅真的利用漏洞、造成影響的可能性與大小。

OWASP AI Exchange 用一句話講得很清楚：威脅在利用一個或多個漏洞時，才變成風險。這句話是後面「風險分析」那章的基礎：一份威脅清單不等於一份待辦清單。

  • 開發者類比：資產是 production 資料庫；威脅是有人想把它拖走；漏洞是某支沒有參數化的查詢；風險是這個組合被利用的機率乘上資料外流的代價。
  • 在 AI 系統裡：資產除了傳統的資料與帳號，還多了訓練資料、模型參數、system prompt、檢索用的語料。

2. CIA 三要素 (CIA Triad)

CIA 是三個要保護的性質：機密性 (Confidentiality)，不該看的人看不到；完整性 (Integrity)，資料與行為不被未授權修改；可用性 (Availability)，該能用的時候能用。

CIA 三要素：開發者類比與 AI 版本
要素你熟悉的對應在 AI 系統裡
機密性ACL、加密、金鑰管理訓練資料、system prompt、使用者輸入、模型本身被外洩
完整性checksum、簽章、輸入驗證模型的行為被操縱（資料被投毒、被提示詞注入 (Prompt Injection)）
可用性rate limit、autoscaling、DoS 防護模型被大量請求拖垮，或推論成本被刻意推高

AI Exchange 把攻擊者的目標分成三類：揭露 (disclose)、欺騙 (deceive)、破壞 (disrupt)，剛好對應 C、I、A。這個對應在第 2 章會用到。

3. 攻擊面與信任邊界

攻擊面 (Attack Surface) 是外界能碰到、並能影響系統的所有入口：API、表單、上傳檔、第三方回呼、開發環境、相依套件。OWASP 的攻擊面分析指引把它描述為「盤點系統中哪些部分需要被審查與測試」。

信任邊界 (Trust Boundary) 是一條線：資料或控制權從「較不可信」的一側，跨到「較可信」的一側。跨線的東西必須驗證或授權。OWASP 的威脅建模 (Threat Modeling) 指引把「資料流與信任邊界」列為理解系統時必須掌握的內容。

  • 開發者類比：瀏覽器送到後端的請求、第三方 webhook，都在邊界的另一側。你不會直接把 query string 拼進 SQL，同樣的紀律也適用於「別人寫的文件」。
  • 在 AI 系統裡：AI Exchange 的工程入門說得直接：使用者輸入、被檢索的文件、工具輸出、儲存的記憶，即使工程師原意只當成資料，也可能影響模型行為。官方

4. 威脅建模與攻擊鏈

威脅建模 是在寫程式之前，先系統化地問「這個東西可能怎麼被弄壞」。OWASP 的威脅建模指引引用 Threat Modeling Manifesto，把過程濃縮成四個問題：

  1. 我們在做什麼？（畫出系統與資料流）
  2. 什麼可能出錯？
  3. 我們打算怎麼處理？
  4. 我們做得夠好嗎？

攻擊鏈 (Attack Chain) 指攻擊者把好幾個步驟串起來才達成目的。AI Exchange 自己就舉了兩例：先駭進訓練資料庫放入毒樣本、等模型訓練完再送出特定輸入；或是先闖進開發環境偷走模型，離線研究怎麼騙它，再對線上系統出手。這兩例在第 2 章會畫成圖。

  • 開發者類比：入侵很少一步到位，常見是拿到一個低權限帳號、再往旁邊移動、最後碰到資料庫。這是通用的資安說法，不是 OWASP AI 文件的原話。類比
  • 防禦的含義：鏈上每一環都可以設關卡，鏈斷一環攻擊就失敗。這也是縱深防禦 (Defense in Depth) 的來源（見第 6 節）。

5. 最小權限、預設拒絕與爆炸半徑

最小權限 (Least Privilege)：只給完成工作所需的最小存取。OWASP 的安全產品設計指引把它列為基本原則；授權指引則把「強制最小權限」與「預設拒絕」並列為建議做法。

爆炸半徑 (Blast Radius)：一旦某個元件出錯或被攻破，最壞能壞到哪裡。最小權限就是在縮小爆炸半徑。AI Exchange 稱這類做法為爆炸半徑控制 (blast radius control)，後面會一直出現。官方

混淆代理人 (Confused Deputy)：一個權限高的服務，被權限低的一方誘導，去做它自己本不該做的事。AI Exchange 在 agentic 與 RAG 的說明裡都用到這個詞：agent 以使用者或服務帳號的權限行動，一旦被操縱，就替攻擊者行事。

  • 開發者類比：IAM role 只給單一 bucket 的唯讀，對比給 AdministratorAccess；資料庫帳號用唯讀對比用 root。混淆代理人則像 CSRF：瀏覽器帶著你的 cookie，替別人送出請求。類比

6. 縱深防禦與失效安全

縱深防禦：用多層控制保護資產，其中一層失效時，其他層仍能擋住。OWASP 的安全產品設計指引也提到，目標是讓環境有韌性，並能快速偵測與回應事件。

失效安全：出錯時要落在安全的狀態，而不是把弱點暴露出來。AI Exchange 在 RAG 一節的例子是：檢索或權限檢查失敗時，如果系統退回「不過濾、直接用模型記憶回答」，上游所有控制就被悄悄繞過。第 5 章會再談。

  • 開發者類比：CI 裡多道 gate；熔斷器開啟時預設拒絕，而不是預設放行。類比

7. 預防、偵測、回應類控制

這是一般資安實務的分類

下表的三分法是通用資安用語，由作者整理成表。AI Exchange 本身不是用這三類組織控制（它用 Manage、Have resilient models、Watch、Limit，見第 3 章），但它對少數控制有明確說「這是預防型」或「這是偵測型」。

三類控制的目的與例子（作者整理，非官方）
類型目的開發者熟悉的例子AI 系統的例子
預防型 (Preventive)讓壞事做不到，或不容易發生參數化查詢、輸入驗證、最小權限帳號最小模型權限 (Least Model Privilege)、資料最小化、限制誰能呼叫模型
偵測型 (Detective)發現壞事正在或已經發生日誌、告警、異常偵測使用監控、對輸入與輸出做異常偵測
回應型 (Responsive)發現後止血、復原、留證據撤銷金鑰、回滾、事件應變流程停止 agent 執行、回滾被污染的狀態、交給人處理

三類要搭配使用。只靠預防，一旦被突破就沒有後續計畫；只靠偵測，等你看到告警時傷害可能已經造成。這也是為什麼對提示詞注入這種「很難根治」的威脅，官方建議的是多層並用。

8. SQL Injection 與 Prompt Injection：同源，但解法不同

這是整份教材最重要的一個類比。兩者的共同點是：不可信的資料，被系統當成指令執行了。

  • SQL Injection：OWASP 的防護指引說明，它發生在不可信資料成為查詢「語法」的一部分時。根本的解法是參數化查詢 (parameterized query)：把查詢結構與資料值分開，由資料庫介面把綁定的值當成資料，而不是語法。再搭配固定的查詢結構與最小權限，限縮萬一出事的傷害。
  • Prompt Injection：OWASP LLM Top 10 2026 在 LLM01 開頭就指出，LLM 在架構上不區分「指令」與「資料」，兩者都是同一串 token，因此沒有乾淨等價於參數化查詢的做法。官方
# 傳統資料庫：結構與資料值在介面層分離
cur.execute("SELECT balance FROM accounts WHERE owner = ?", (owner,))

# LLM 應用：規則、檢索到的文件、使用者問題，最後都是同一串文字
prompt = SYSTEM_RULES + "\n" + retrieved_doc + "\n" + user_question

第一行的 ? 與綁定值，是資料庫「保證」資料不會變成語法的機制。第二行沒有這樣的機制：模型只看到一串文字，沒有一條硬性的界線告訴它「這段是資料、那段是指令」。把外部內容用標記或結構化欄位包起來（AI Exchange 稱為輸入隔離）只能降低模型聽從它的機率，不是像參數化查詢那樣由介面保證。

SQL Injection 與 Prompt Injection 對照
面向SQL InjectionPrompt Injection
問題核心不可信資料成為查詢語法不可信內容改變模型行為
為什麼會發生字串拼接，結構與資料混在一起指令與資料在同一個 token 流，模型本質上就是這樣運作
有沒有根治機制有：參數化查詢目前沒有；LLM Top 10 2026 稱沒有可靠的預防機制
實務上怎麼防參數化 + 固定結構 + 最小權限多層並用：降低成功率，並假設會被突破、限縮後果
傷害大小由誰決定資料庫帳號的權限模型能呼叫什麼工具、能碰什麼資料

類比的限制

SQL Injection 一旦用參數化查詢堵住，這個弱點就算解決；Prompt Injection 沒有這種「修好了」的狀態。所以 AI 資安更強調兩件事：假設防線會被突破，以及把模型能做的事限制到最小。這就是第 3 章「七層防線」的邏輯。（作者整理）

9. 共同責任

你用過雲端的 IaaS、PaaS、SaaS，就懂共同責任：供應商顧好底層，你顧好自己放上去的東西。AI 也一樣：用託管模型時，供應商負責模型與服務基礎設施，你仍要負責自己的應用、提示詞、被檢索的資料、身分、工具權限與輸出處理。AI Exchange 的工程入門把這點講得很明確，第 4 章會用到。官方

重點整理與自我檢核清單

  • 威脅清單不等於待辦清單；威脅要碰到漏洞才成為風險。
  • CIA 對應到 AI：機密性是資料與模型外洩，完整性是行為被操縱，可用性是被打爆或成本被推高。
  • LLM 應用的不可信來源不只使用者輸入，還包括檢索結果、工具輸出、記憶。
  • 最小權限縮小爆炸半徑；縱深防禦讓單一防線失效時還有後備。
  • Prompt Injection 沒有等價於參數化查詢的根治法，所以要多層並用，並假設會被突破。
  • 我能用自己的話說出資產、威脅、漏洞、風險的差別。
  • 我能說出一個 LLM 應用裡，至少三個跨越信任邊界的內容來源。
  • 我能解釋為什麼參數化查詢有效，而 LLM 沒有對應物。
  • 我能把一個控制歸類為預防、偵測或回應型，並說明理由。
