第 9 章　情境演練

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3、LO4、LO5
  • 前置：第 2 章至第 8 章

真實事件很少只屬於一個條目。這一章用三個虛構系統練習同一個動作：看到一個事件，先決定它在哪一環出問題，再回頭對應條目，最後挑「先補哪一項」。情境只描述到能理解風險與防禦的概念層級，不含可直接使用的攻擊手法。

9.1 遇到事件時的三個問題

前面八章給了你十個條目的地圖。實務上更有用的是反過來用：從一個事件出發，依序問三個問題。

9.2 情境 A：客服 RAG 助理

情境 A（虛構）：雲杉保險的理賠問答助理

虛構 雲杉保險是虛構的公司。他們為客服人員建了理賠問答助理：知識庫由內部手冊、過去客服工單與合作診所上傳的文件組成，所有客戶的文件放在同一個向量索引。流程是先對整個索引做相似度搜尋，再依客服人員所屬部門在應用層過濾。助理的回覆以 Markdown 渲染，並且有一個「寄送摘要給客戶」的工具，可寄信到任意地址。

架構：知識庫（手冊、工單、診所文件）→ 共用向量索引 → 檢索 → 託管 LLM（系統提示詞內含寄信工具的說明與一組內部 API 金鑰）→ Markdown 渲染的客服介面。

  1. 發生了什麼：某位客服人員在查詢一般理賠流程時，答案裡出現了「僅限理賠審查部」才該看的內部審查標準。事後檢查又發現，某張工單裡有人（來源不明）放了一段文字，其內容會讓助理在回覆中附上一個外部網址的圖片、網址參數帶著對話內容。同時，稽核人員從系統提示詞裡直接看到了那組內部 API 金鑰。
  2. 哪一環出問題（至少四環）：(1) 檢索前沒有授權：先搜尋全索引、後過濾；(2) 工單內容被當成可信，但可由第三方寫入；(3) 輸出的 Markdown 圖片會自動載入；(4) 金鑰放在模型看得到的地方；(5) 寄信工具能寄到任意地址。
  3. 對應條目：(1) LLM09（跨租戶／跨部門的相似度搜尋）與 LLM02（過度分享與檢索前授權）；(2) LLM01（經檢索內容的間接注入，半可信面）；(3) LLM10（用戶端渲染器自動載入）；(4) LLM08 與 LLM02（嵌入的憑證本身就是外洩）；(5) LLM03（過度功能）。
  4. 該採什麼控制（官方控制，優先序為作者建議）：
    • 先授權再檢索：把部門與權限範圍放進索引查詢內，在伺服器端驗證，並以區塊為單位控制（LLM09 #1、LLM02 第 1 層）；
    • 金鑰移出提示詞，外部化到模型碰不到的系統；授權由獨立的決定性機制強制（LLM08）；
    • 預設關閉 Markdown 圖片自動載入，必須渲染時限定來源允許清單（LLM10）；
    • 寄信工具改成只能寄到已核准的收件人，其餘動作要求人工確認；拿掉不必要的功能與權限（LLM03、LLM01 的 Rule of Two）；
    • 第三方可寫入的工單，視為半可信的來源：隔離並標示來源、過濾只當輔助（LLM01 第 6 項）。

注意這個情境沒有一個「單一弱點」。每個控制都是在某一環讓下一環失敗的代價變小。如果只修一項，最該修的是「寄信工具」與「先授權再檢索」：前者限縮注入成功後的外洩路徑，後者去掉資料被取回的前提。這個排序是作者的判斷，不是官方的。

9.3 情境 B：第三方模型上線

情境 B（虛構）：青河銀行的內部問答模型

虛構 青河銀行是虛構的公司。團隊要上線一個內部問答模型：基礎模型取自公開模型中心的第三方模型，另外下載了一個社群釋出的 LoRA adapter 做領域微調；部署時以「作者／模型名稱」取得模型，並在持續整合流程裡自動轉換格式。上線前檢核的結論是「掃描通過、簽署驗證通過」。三個月後，內部評估發現：模型在某類特殊格式的問題下，回覆中會固定出現一個外部網址，而其他一般評估指標都正常。

  1. 發生了什麼：模型只在特定觸發條件下改變行為，標準評估看不出來。
  2. 哪一環出問題：(1) 取得模型只用名稱，沒有固定到不可變的摘要；(2) 社群 adapter 沒有經過來源審查；(3) 自動轉換環節沒有被視為高風險晉升點；(4) 上線前檢核只回答了「來源與載入」，沒有回答「行為」。
  3. 對應條目：LLM04（名稱參照、無簽署的 adapter、轉換流程）與 LLM05（條件觸發的後門，標準評估看不出來）；若網址被渲染成圖片，還牽涉 LLM10。
  4. 該採什麼控制：
    • 以不可變的參照取得成品，維護已簽署的物料清單，納入 adapter 與資料集（LLM04）；
    • 把轉換與合併當作高風險的晉升點嚴密監控，對 chat template、tokenizer 設定、adapter 做 diff 與靜態分析（LLM04、LLM05 #12）；
    • 針對觸發詞與對抗性輸入做後門探測，並且每一輪微調或對齊之後都重做，不要假設對齊會移除後門（LLM05 #10）；
    • 簽署只證明來源與完整性，檢核表要補上行為評估（LLM04 第 5 項）。

9.4 情境 C：客服 agent 的成本暴增

情境 C（虛構）：晨星購物的客服 agent

虛構 晨星購物是虛構的公司。客服 agent 使用擴充思考的推理模型，能查詢訂單、並呼叫社群提供的「物流追蹤」工具。系統每個使用者每分鐘最多 10 個請求，並設了一個「帳單超過預算時寄信通知財務」的警示。某個月，帳單遠超預算，但沒有任何服務中斷，也沒有請求量異常。調查後發現：幾位使用者各自維持一個很長的對話；同時，社群的物流追蹤工具在特定條件下會回傳一串「請再次呼叫自己」的指示。

  1. 發生了什麼：每個請求都在配額內，但成本持續累積，沒有人被擋下。
  2. 哪一環出問題：(1) 只限制請求數，沒有 token 或成本層級的限制；(2) 警示只通知、不中止；(3) 對話上下文累積，每回合重新處理；(4) 工具輸出沒有被視為半可信，agent 沒有步數或遞迴深度上限。
  3. 對應條目：LLM06（大上下文濫用、推理迴圈、工具呼叫迴圈、錢包拒絕）；工具輸出裡的指示也有 LLM01 的間接注入與 LLM04 的第三方工具面向。
  4. 該採什麼控制：
    • 每個使用者、金鑰、團隊與帳號的硬性花費上限，超過即中止推論（LLM06 #2）；
    • token／天與估計成本的限制，加上推論前預估（LLM06 #1）；
    • agent 的步數、遞迴深度、時間與每次執行成本上限，用狀態雜湊偵測遞迴（LLM06 #9）；
    • 第三方工具視為供應鏈面：釘住版本、稽核工具描述與輸出（LLM01 第 10 項、LLM04）。

本章重點與自我檢核

  • 遇到事件先問三題：從哪個入口進來？被放大的是哪個能力？衝擊落在誰身上？再對應條目。
  • 一個事件常同時涉及多個條目；多個控制的價值，是讓下一環失敗的代價變小，不是各自獨立。
  • 優先補的是限縮後果的控制（最小權限、完全仲裁、先授權再檢索、硬性花費上限、驗證後才行動）；降低成功率的控制是輔助。
  • 上線前檢核要分清「來源與載入的檢查」和「行為的評估」。
  • 表 9-1 的「先補哪一項」是作者的優先序判斷，官方並未排序。
  • 給我一個事件描述，我能用三個問題把它對應到至少兩個條目。
  • 我能為每個情境說出「先補哪一項」以及理由。
  • 我知道哪些檢核項目只證明來源，哪些才檢查行為。
