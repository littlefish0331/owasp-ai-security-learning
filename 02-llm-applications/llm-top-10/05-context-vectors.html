放大器層的另外兩項，都與「模型看到什麼」有關。LLM08 談模型看得到、使用者看不到的那部分上下文；LLM09 談決定「模型看得到哪些資料」的相似度搜尋層。兩者的共同教訓是：不要把安全建立在「別人看不到」或「檢索完再過濾」上。

5.1 LLM08：隱藏上下文不是祕密

LLM08:2026 隱藏上下文暴露 (Hidden Context Exposure) 是指：隱藏的、不對使用者顯示的系統指令或營運脈絡，被未經授權地取出、推得或重建。它在「所含內容有安全意義」時才成為問題：裡面有祕密、政策邏輯、工具、信任邊界、工作流程判準或專有行為，且實質提高了攻擊者的能力。

官方列舉的「隱藏上下文」不只是系統提示詞：還包括開發者指示、取回的政策文字（來自 RAG 知識庫、設定儲存或使用者檔案服務）、應用程式暴露給模型的工具與函式 schema，以及其他組進上下文視窗的規則與資料。共同點是：對最終使用者不可見，但模型看得到。

2025 版的對應條目是 LLM07:2025 System Prompt Leakage；官方在 2026 年前言說它「現在是更廣義的 Hidden Context Exposure」，圖 Figure 1 以紅色虛線標為「更名／重新界定範圍」。官方給的設計立場只有一句，卻很重要：設計時就假設隱藏上下文會被發現，它的內容不應被視為祕密；開發者應確保它被揭露時，幾乎沒有直接的安全影響。具體來說，憑證、連線字串、token 不該放進去，也不該把隱藏上下文當成授權、權限分離、政策執行或內容過濾的唯一邊界。

官方明說 LLM08 不涵蓋三件事：受規範的使用者資料或訓練資料外洩（LLM02）；agent 化後的放大（持續記憶、agent 之間的通道、工具設定持久化、多步驟入侵，屬 Agentic Top 10）；以及 LLM 整合系統繼承的一般應用安全問題（伺服器端日誌洩漏、用戶端程式包檢視、基礎設施層側通道）。三項控制都在同一個方向：不放敏感資料進去；關鍵行為用獨立、決定性的機制強制（不靠提示詞）；授權與存取控制獨立於 LLM，需要不同存取層級的任務就按授權脈絡分開，各自只給需要的權限。

5.2 LLM09：相似度搜尋層是自己的信任邊界

LLM09:2026 向量與嵌入弱點 (Vector and Embedding Weaknesses) 涵蓋任何「把文字、圖片、程式碼或音訊轉成數值表示、再用相似度搜尋決定模型看到什麼」的應用。檢索增強生成 (Retrieval-Augmented Generation, RAG) 是最常見的例子，但同一套機制也是向量化的 agent 記憶、語意快取 (Semantic Cache) 與去重管線的基礎。官方的句子是：只要相似度搜尋位於資料來源與提示詞之間，嵌入層就成為應用信任邊界的一部分。

它和提示詞注入不同：這些弱點利用的是嵌入空間的幾何與相似度搜尋的機制，而不是模型的指令遵循行為；很多攻擊即使取回的內容沒有任何惡意指令，也能成立。官方給了一個好記的四字框架：

框架（官方）對應的風險官方控制（編號為官方清單順序）
投毒讓系統「錯」檢索時資料投毒（攻擊者在能寫入語料的管道放內容，使其嵌入落在目標查詢附近）；語意快取與去重投毒；多模態嵌入投毒（一張圖片的嵌入貼近敏感文字查詢，且文字掃描抓不到）#2 資料驗證、來源認證與溯源（嵌入前正規化、為每筆嵌入記來源／時間／信任層級／管線版本）；#3 依信任層級隔離；#4 攝入與檢索時的異常偵測
反推讓系統「洩」嵌入反推 (Embedding Inversion)：從儲存的向量重建原文；成員推論：若回傳原始相似度分數，索引就是直接的成員身分探測器#4 不把原始相似度分數回傳給用戶端、加雜訊與多樣化、對可被當探測器的端點限流；#5 儲存生命週期（備份視同來源文件的敏感等級、嵌入加密、金鑰與應用層分開管理）
干擾讓系統「啞」檢索干擾 (Retrieval Jamming)：塞入一份「阻擋文件」，使 LLM 拒絕回答或宣稱沒有資訊；不含惡意指令，是檢索層的可用性攻擊#4 異常偵測；重排序 (re-ranking) 提高攻擊成本，但取代不了來源與攝入控制
存取控制失敗讓系統「無差別」跨租戶外洩：相似度搜尋跑過整個索引後才在應用層套用存取控制，攻擊者可由結果數、分數分佈、時序推斷他人文件的存在與主題#1 在索引查詢內做租戶範圍限制，並在伺服器端驗證，不是檢索後再過濾；高敏感工作負載用實體分開的索引；以區塊 (chunk) 為單位做存取控制

官方畫的邊界很清楚：經由檢索內容送進來的指令屬 LLM01；嵌入模型的訓練期投毒屬 LLM05；向量資料庫函式庫的序列化缺陷屬 LLM04；不依賴嵌入幾何的 agent 記憶攻擊屬 ASI06 記憶與上下文投毒 (Memory & Context Poisoning)。另外官方指出：無向量的檢索系統（只用 BM25、或由 LLM 瀏覽樹狀結構）繼承了非幾何的風險，但沒有 LLM09 的攻擊面。

5.3 授權放在哪裡：同一個 RAG，兩種設計

5.4 核心概念：「看不到」與「過濾掉」都不是邊界

把保密與授權放在對的層

是什麼
兩個互補的設計原則：（LLM08）不把祕密與關鍵授權放進模型看得到的上下文；（LLM09）授權發生在檢索之前、在索引查詢之內，而不是檢索之後。兩者都在說：安全屬性要由模型之外、決定性、可稽核的機制強制。這個「合為一個原則」的整理是 作者整理，非官方；兩個條目各自的控制是官方的。
為什麼會發生
提示詞看起來像「設定」，所以被當成保險箱；向量庫看起來像資料庫，所以沿用「查完再過濾」的習慣。但模型會被誘導吐出提示詞內容，而相似度搜尋在套用任何過濾之前，就已經讓結果數、分數與時序洩漏了資訊。
怎麼被利用（概念層級）
透過對話探測取出工具清單與參數 schema，再用它設計針對性的注入；或探測共用索引，從結果數與分數分佈推斷他人資料；或從外洩的向量備份反推出原文——官方的情境是「只有嵌入外洩」被歸為低嚴重度，之後被零樣本反推重建出含個資的內容，事件重新定級，通報義務重新評估。
怎麼防
LLM08：憑證與祕密外部化、關鍵行為與授權由獨立的決定性機制強制。LLM09：索引查詢內的租戶範圍限制、區塊層級存取控制、依信任層級隔離、攝入時正規化並記錄來源、不回傳原始分數、儲存生命週期控制（嵌入備份與來源文件同敏感等級）、檢索紀錄與異常監控。
常見誤解
「系統提示詞對使用者不可見，所以可以放 API 金鑰」（官方：假設會被發現，內容不是祕密）。「所有文件都標了租戶、所有 API 都已驗證，就沒有跨租戶風險」（官方：存取控制決定發生在嵌入空間搜尋之後，攻擊仍可成立）。「只外洩嵌入沒關係，沒有原文」（官方：現代嵌入可被反推，「僅嵌入」不是安全港）。「LLM09 就是 RAG 的提示詞注入」（官方：它利用幾何與機制，常不含任何惡意指令）。

本章重點與自我檢核

  • 隱藏上下文包含系統提示詞、開發者指示、取回的政策文字與工具 schema；設計時假設它會被發現，裡面不放憑證，也不靠它當唯一的授權或過濾邊界。
  • LLM08 的嚴重度看「放了什麼、被如何依賴」：資訊性、中、高、嚴重四級；它常放大 LLM01、02、03、10。
  • LLM09 利用嵌入空間的幾何與相似度搜尋機制；框架是：投毒讓系統錯、反推讓系統洩、干擾讓系統啞、存取控制失敗讓系統無差別。
  • 先授權再檢索：租戶範圍限制要在索引查詢內，不能事後過濾；不回傳原始相似度分數；嵌入備份視同來源文件。
  • LLM09 與 LLM01、04、05、ASI06 的邊界由官方寫明；無向量檢索沒有 LLM09 的攻擊面。
  • 我能說出隱藏上下文包含哪些東西，並解釋為什麼不該把它當祕密。
  • 我能用「錯／洩／啞／無差別」四字框架，把一個 RAG 的弱點分類。
  • 我能解釋「檢索後過濾」為什麼不夠，並說出較佳的做法。
  • 我能區分 LLM09 與 LLM01（檢索內容中的指令）、LLM05（嵌入模型被投毒）的差別。
