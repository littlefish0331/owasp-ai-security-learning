第 2 章　LLM01 提示詞注入

  • 預估閱讀：約 10 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO2
  • 前置：第 1 章；前置觀念：SQL Injection 與 Prompt Injection

LLM01 是三層地圖上最外面的入口，也是官方承認「目前沒有可靠預防機制」的一項。這一章要建立的核心判斷是：既然攔不乾淨，防禦的重點就從「擋住輸入」轉到「就算被騙了，後果也有限」。

2.1 輸入怎麼變成指令

官方對 LLM01:2026 提示詞注入 (Prompt Injection) 的定義很寬：任何輸入——使用者直接輸入、取回的內容、工具輸出、圖片／音訊／影片、中間推理，或持久記憶——只要改變了模型行為，而且不是開發者原本想要的，就算。輸入不必是人看得懂的，不必直接來自使用者，也不必顯示在畫面上。

根因官方用一句話交代：LLM 在架構上不區分「指令」與「資料」，兩者都是同一條串流上的 token，所以沒有乾淨的「參數化查詢」對應物（參數化查詢為什麼在 SQL 上有效，見前置觀念頁）。官方進一步指出三個部署時的性質，會讓情況更糟：

  • 官方 上下文池化 (Context-Window Pooling)：系統提示詞、使用者輸入、取回文件、工具輸出、對話歷史與記憶，被模型當成單一 token 串流，沒有被強制執行的信任邊界。
  • 官方 記憶持久化 (memory persistence)：寫進長期記憶、RAG 語料或向量資料庫的一筆注入，會污染之後每一次讀取該儲存體的對話。
  • 官方 代理式執行 (agentic execution)：模型輸出驅動工具呼叫時，爆炸半徑從聊天介面延伸到工具能碰到的一切；工具輸出又回到上下文，可能連鎖甚至自我複製。

官方建議在選擇緩解措施之前，先把一個情境拆成三個軸，這是很實用的威脅建模步驟：

表 2-1　描述一次提示詞注入的三個軸（官方分類）
軸問的是官方列出的取值
投遞面 (delivery surface)它怎麼到達模型直接輸入、取回內容、工具輸出、工具連線通道、持久記憶
傳播行為 (propagation)它如何跨時間與邊界擴散單次、多步驟攻擊鏈、經記憶或 RAG 跨對話、在 agent 之間自我複製

2.2 直接、間接，以及信任面

直接注入是使用者（或掌握使用者存取路徑的攻擊者）輸入改變了模型行為。它可以是蓄意的，也可以是無意的：官方範例是求職者用 LLM 優化履歷，而職缺 PDF 裡埋了一段針對 AI 的偵測指令，模型把它帶了出來——雙方都沒有惡意，仍然是提示詞注入。越獄 (Jailbreak) 是其中的子集：目標是讓模型違反自身的安全規範。

間接注入是模型讀進外部來源的內容，而那份內容含有扮演指令的資料；使用者既沒提供、也沒看到。官方依「來源的信任程度」把投遞面分三類，信任程度決定哪些防禦現實可行：

表 2-2　間接注入的三種信任面（官方分類，例子取自官方說明）
信任面例子防禦上的意義
不可信公開網頁、陌生寄件者的郵件、搜尋結果一律當可疑；多數注入研究集中在這裡
半可信公開 bug tracker 的 issue 標題、套件的 README 與 changelog、第三方 API 回應使用者信任平台，但不見得信任每一位貢獻者
可信開發者自己的程式庫、資料庫、內部文件與郵件開發者可能不知道攻擊者已經透過無關的上游入口（例如公開的問題回報表單）放了內容進來

三類的共同結構是：攻擊者不需要入侵後端，只要把文字放在你的 LLM 會讀到的地方，而 LLM 會用開發者（或使用者）的權限把事做完。官方特別描述了一種模式：攻擊者經由低權限通道（公開表單、客服工單、社群的 pull request）送出文字，等著使用者那個連上 MCP 的 agent 或開發助理，在高權限憑證下讀到它。所以只守聊天介面，會整類漏掉。

2.3 一條注入怎麼走到聊天視窗之外

官方觀察到：多數高衝擊的注入事件之所以嚴重，是因為注入落在一個「工具、權限或輸出渲染能力」能讓被攻陷的模型代替攻擊者行動的系統裡。這就是 LLM01 與 LLM03:2026 過度授權 (Excessive Agency) 的分工：提示詞注入是輸入側的攻陷，過度的功能、權限或自主，才是讓攻陷在聊天視窗之外產生後果的原因（LLM03 在第 4 章）。

2.4 官方的 11 項控制，各自有什麼限制

官方的立場很直接：提示詞注入是目前生成式 AI 的內在性質，再加上模型行為具隨機性，所以沒有可靠的預防機制（與 NIST、NCSC 及相關研究一致）。因此防禦是架構式而非攔截式：假設模型的指令邊界終將被繞過，去限制模型被允許做的事，以及它的輸出被允許到達的地方，讓一次成功的注入不會變成一次成功的利用。

官方列了 11 項，要求當作縱深防禦，因為沒有單一控制足夠。官方也說明：有些控制降低注入的成功率、並預期會在適應性攻擊者面前退化；另一些限縮注入成功後的後果，這些才是面對會探測系統的攻擊者仍能存活的。下表的「官方點出的限制」欄是官方原文的意思；最右欄的歸類是作者的整理。

表 2-3　LLM01:2026 的 11 項緩解措施（官方）與它們的限制
#控制官方點出的限制歸類（作者整理，非官方）
1在系統提示詞用宣告式的允許與拒絕語句限定角色與能力只是部分控制；攻擊者推得出提示詞就能繞過，要搭配 #4降低成功率
2嚴格的輸出結構，並在可信的應用程式碼中驗證（用結構驗證，不是再叫一次 LLM）只抓得到格式違規，抓不到語意操縱：結構正確的回應仍可能帶惡意查詢或外洩格式的郵件內文限縮後果
3在每個模態邊界過濾（文字、圖片、音訊、結構化資料）語意過濾可被改寫或編碼規避；低資源與混語輸入會降低準確度降低成功率
4憑證與狀態變更能力放在應用程式碼，不在模型；每項操作最小權限；特權呼叫經決定性政策引擎在執行當下重新驗證意圖與參數官方稱此為在 agent 部署中「承重」的控制；方便用的寬鬆權限與多 agent 轉手會把風險帶回來限縮後果
5在每個攝入與渲染邊界清除不可見字元（tag-block、變體選擇符、零寬字元）擋不住看得見的文字酬載，也擋不住未來的隱寫類型降低成功率
6用結構上獨立、標明來源的通道傳送外部內容，讓模型分得出資料與指令只在非適應性測試中降低成功率；知道標記方式的攻擊者可以模仿，StruQ 在適應性攻擊下被繞過降低成功率
7特權、不可逆或對外可見的動作，需明確的人工確認，且要呈現實際渲染的動作而非摘要不可見字元可讓顯示的動作與執行的不同；量大時核准疲勞 (Approval Fatigue) 會削弱審核者判斷限縮後果
8用 Rule of Two 當底線，限制 agent 的能力組合（見下）官方稱為「承重」的控制；對自主深度保持沉默限縮後果
9把 agent 記憶寫入視為特權操作：記錄起因、分類是否含指令、含指令的記憶要核准才能跨對話保留事實性內容與指令會漸變；分次寫入可能躲過逐筆分類限縮後果
10釘住、簽署並驗證每個 MCP server 與第三方工具套件；稽核工具描述中的隱藏指令；監控工具組合釘住版本擋不住版本內本身帶的酬載，也擋不住不改版本的工具描述投毒限縮後果
11用「已讀過防禦細節」的適應性攻擊者測試，不接受只有靜態攻擊成功率的宣稱Nasr 等人（2025）發現，12 種近期防禦中，多數在靜態測試下攻擊成功率接近零，適應性攻擊下卻超過 90%驗證

Rule of Two 與致命三要素。Rule of Two（Meta AI，2025）把 agent 同時具備的三項能力視為高風險：(A) 讀取不可信輸入、(B) 存取敏感資料、(C) 變更狀態或對外通訊。官方的底線是：A、B、C 三者齊備的 agent，每個動作都要人工核准；只有 [A, B] 或 [A, C] 的組合，要做明確的殘餘風險評估。官方也引用 Simon Willison 的「致命三要素 (Lethal Trifecta)」（2025）說明同一個結構診斷：可存取私人資料、可讀不可信內容、可對外通訊，三者並存就具備高衝擊利用的條件，拿掉任何一項就拿掉條件。AI Exchange 主題也討論過這兩者：第 5 章。

2.5 核心概念：LLM01 提示詞注入

LLM01:2026 提示詞注入

是什麼
任何輸入（直接輸入、取回內容、工具輸出、多模態、記憶）改變了模型行為，且違背開發者本意。分直接與間接；越獄是以違反安全規範為目標的子集。
為什麼會發生
指令與資料在同一串 token 裡，沒有架構層級的區分，所以沒有「參數化查詢」那樣的根治手法；加上上下文匯集、記憶持久化、代理式執行，讓一筆注入影響更遠。
怎麼被利用（概念層級）
攻擊者把文字放進你的 LLM 會讀的任何地方（網頁、工單、郵件、套件說明、記憶），模型再以使用者或開發者的權限替他行動。常見結果：外洩資訊、被操縱的輸出、未授權的工具呼叫、跨對話的持續污染。
怎麼防
架構式防禦：憑證與狀態變更留在應用程式碼，經決定性政策引擎；最小權限；高風險動作人工確認；用 Rule of Two 限制能力組合；外部內容隔離並標示來源、過濾與清除只當輔助；用適應性攻擊者做測試。
常見誤解
「把禁止事項寫進系統提示詞就安全」（官方：只是部分控制）。「過濾器夠強就能根治」（官方：語意過濾可被改寫與編碼規避）。「只有惡意使用者才會造成注入」（無意注入也算）。「靜態測試的攻擊成功率接近零代表防住了」（適應性攻擊下可能超過 90%）。

本章重點與自我檢核

  • LLM01:2026 的根因是指令與資料同在一條 token 串流，沒有「參數化查詢」的對應物；官方明說目前沒有可靠的預防機制。
  • 描述一次注入用三個軸：投遞面、傳播行為、編碼。間接注入依來源分不可信、半可信、可信三種信任面；可信面也可能被上游入口污染。
  • 攻擊者不必入侵後端，只要讓 LLM 讀到他的文字；所以只守聊天介面會漏掉一整類。
  • 防禦是架構式：降低成功率的控制會在適應性攻擊下退化，限縮後果的控制（權限、決定性政策引擎、人工確認、Rule of Two）才承重。
  • 11 項控制每一項都有官方註明的限制，所以必須疊加；並用知道防禦細節的適應性攻擊者測試。
  • 我能解釋為什麼提示詞注入沒有「參數化查詢」那樣的根治方法。
  • 我能分辨直接、間接注入，並說出間接注入的三種信任面。
  • 給我一個 agent 的能力清單，我能用 Rule of Two 判斷它是否三者齊備。
  • 我能說出至少三項控制各自的限制，並區分「降低成功率」與「限縮後果」。
