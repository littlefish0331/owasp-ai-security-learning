篩查做完了。這個結果要怎麼留下來，讓下一個 agent、下一個系統與事後的監理檢查都能驗證？AML 速查表的後半把答案放在簽署收據 (Signed Compliance Receipt) 上，並且反覆提醒：簽章能證明的東西很有限。本章走過第 6 到第 12 節，重點是「這個簽章證明了什麼、沒證明什麼」。

4.1 速率限制與自建或託管

信任分級的速率限制（第 6 節）。文件的主張是：不是所有 agent 都該被同等對待。速率限制要依密碼學身分（公鑰指紋或護照 ID），不是 IP 位址，因為 IP 可能共用或被偽造；新註冊或低信任的 agent（例：L0／L1）限額較低，驗證過的高信任 agent（例：L3／L4）較高；回應中附上剩餘配額與重設時間，讓 agent 自行調整；偵測到異常（請求突增、異常的實體樣式）就降級配額。要防「女巫攻擊 (Sybil Attack)」，也就是建立多個身分來繞過限制，做法是把 agent 身分綁到已驗證的營運者帳戶。

自建或託管篩查（第 7 節）。兩種架構都可以，但 agent 是呼叫者時安全考量不同。自建時，名單、比對引擎與篩查 API 都在機構自己的基礎設施上，請求不離開機構邊界，名單更新頻率與比對演算法由自己控制，代價是要投資名單攝入與比對品質。託管時，機構呼叫第三方篩查 API，agent 的身分憑證與篩查資料會離開機構邊界，機構必須確保供應商符合適用的法規要求，且要資料最小化：只送篩查所需的最少資料。兩種架構都要用 TLS 加密傳輸；威脅模型需要跨越不受信任的中介來驗證時，才用雙方都支援、經審查的訊息簽章設定檔。不要把 agent 的私鑰或完整身分憑證送給第三方，也不要以為 TLS 在連線終止之後還保護資料。

4.2 收據：序列化、信任與跨 agent 傳遞

序列化 (第 8 節)。兩個系統各自把同一個 JSON 物件序列化來雜湊或驗章時，鍵的順序、空白與數字格式都可能不同，得到的位元組就不同，驗章會失敗。JSON 規範化方案 (JSON Canonicalization Scheme, JCS，RFC 8785) 給出一種確定的表示法。文件同時列了兩個限制：JCS 不是每種簽署格式都需要（JWS 的驗證者檢查的是編碼後的簽署輸入，不會重新序列化酬載）；而且跨系統驗證還需要雙方同意的簽章設定檔與受信任的驗證金鑰，規範化 (Canonicalization) 兩者都不提供。要做的是：若收據設定檔要求各自序列化 JSON，簽署與驗證前都先規範化；不要自行多加一道預先雜湊，除非設定檔要求；記錄用了哪個規範化與簽章設定檔；不要依賴框架預設或美化輸出的序列化。

跨 agent 的問責（第 9 節）。agent 付款可能經過多個 agent。下游依賴簽署的篩查收據時，必須用綁定到受信任發行者的金鑰驗證它。文件說得很精確：數位簽章提供資料來源與完整性的保證，不證明發行者的篩查做得對；收據記錄的是發行者對實體、名單與決定的「主張」，所以驗證者仍需要一份政策，決定信任哪些篩查發行者。收據要綁定到特定交易（簽署的酬載含交易或意圖雜湊）並一路傳遞；每一跳驗證進來的收據，若自己也採取動作，就附加自己的簽署收據，形成可驗證的問責鏈。

4.3 核心概念：名單新鮮度 (Sanctions-List Freshness) 要綁進收據

「已篩查」不是布林值

是什麼
文件第 10 節的第一句：一張寫著「已篩查，無命中」的收據，如果沒說用的是哪個版本的名單、什麼時候篩的，就沒有意義。要把名單版本與時間戳放進簽署收據裡，讓「篩查有多新」本身不可竄改且可稽核。
為什麼
制裁名單更新頻繁，拿過期的名單得到「乾淨」的結果，是合規缺口（文件的陳述）。後面的驗證者無從得知當時用的是哪一版，除非它被寫進收據。
怎麼被忽略（概念層級）
收據只有「screened: true」；或收據有名單時間，卻由發行者自己宣告有效期，驗證者照單全收；或以為簽了時間戳，就等於證明名單真的是最新的。
怎麼防
(a) 簽署範圍內含名單來源、版本或發布日期與篩查時間戳；(b) 把每個結果與名單版本綁到特定交易或付款意圖；(c) 由驗證者強制自己可接受的名單年齡與篩查年齡上限，不讓發行者提供的年齡限制凌駕驗證者的政策；(d) 另外保存使用過的名單版本證據與篩查服務的更新歷史。
常見誤解
「收據有簽章與時間戳，所以那份名單一定是最新的。」文件明說：簽署的時間戳或版本只保護被記錄的主張不被更改，並不獨立證明名單當時是最新的、或真的被使用，所以才要另外保留證據。

第 12 節是全文的 Do／Don't 彙整，文件說這些控制與 AISVS 的驗證要求一致，特別是第 10 章（MCP 安全需求；見AISVS 與 LLMSVS 第 2 章）。其中有一條值得單獨記：身分要在每次篩查請求前驗證，一次檢查不夠長期存取。

本章重點與自我檢核

  • 速率限制依密碼學身分與信任等級，不依 IP；把 agent 身分綁到已驗證的營運者帳戶以防女巫攻擊。託管篩查時，憑證與篩查資料離開機構邊界，要資料最小化。
  • 規範化 (JCS) 只解決「各自序列化得到同樣位元組」，不提供簽章設定檔與受信任金鑰；JWS 不需要它。
  • 收據的簽章證明來源與完整性，不證明發行者篩查做對；驗證者要有信任哪些發行者的政策，並自己強制名單年齡與篩查年齡上限。
  • 「已篩查」不是布林值：名單版本與時間戳要簽進收據並綁定到交易；簽署只保護被記錄的主張，不證明名單當時是最新的。
  • 文件的法規對照表是示意、不是法律意見，且已被收斂得更保守；要與法務確認各管轄區義務。
  • 我能說出一張收據要簽進哪些內容，以及每一跳要驗證哪四件事。
  • 我能對「簽了章就證明篩查正確」這個說法指出錯在哪裡。
  • 我能說明為什麼對照表要和法務一起讀，以及它被改保守的方向。
