第 3 章　AML 與制裁（上）：身分、篩查、稽核軌跡與失效即拒絕

  • 預估閱讀：約 9 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章

一個 AI agent 代客戶發起付款。付款之前，機構要先問四件事：這是哪個 agent？它替誰行事？對手方在不在制裁名單上？這一切做過什麼、有沒有被改？AML 速查表前半就在處理這四個問題，並且守住一條線：篩查沒做完，就不等於放行。本章讀它的關鍵原則與前五節。

3.1 先分清楚：軟體身分不是法律客戶

文件在 12 節控制之前，先用「法規脈絡」與「關鍵原則」劃出一條界線。法規脈絡列了六類（美國銀行保密法與 OFAC 制裁、FinCEN 的客戶識別與盡職調查、英國與歐盟制裁、資金移轉紀錄保存），每一類的意思都一樣：適用哪些要求，取決於機構的受管制角色、交易、客戶關係與管轄區，要由合規負責人去認定。

下面幾句是文件的陳述，不是法律意見，教材不查證現況

  • 文件寫道：OFAC 並未規定一般性的「必須掃描姓名或使用篩查軟體」；篩查是支持制裁義務的手段，結論前仍要完成必要的分析。
  • 文件寫道：為軟體做身分驗證，並不等於辨識法律上的客戶；客戶識別指引區分「帳戶所有人」與「只是代為行事的人」。
  • 文件寫道：歐盟制裁的名單比對本身，不足以證明遵守每一項限制。

關鍵原則把這些收成一句話：法律客戶與對手方的識別，要和軟體的認證與授權分開。記錄「這個 agent 為哪位客戶行事、可以做什麼」，是應用程式安全控制；而篩查、監控、通報與保存的規則，由合規負責人定義。不要把 agent 憑證或「名單比對成功」當成法律義務已完成的證明。下表把文件的四個問題與回答它們的機制對起來。

3.2 三道前置檢查：agent 身分、實體篩查、操作者

先確認身分，再篩查（文件第 1 節）。agent 要存取篩查服務或發起付款之前，身分必須用密碼學驗證；沒有密碼學證明的自我宣告標頭（如 X-Agent-ID）必須拒絕。身分要綁進篩查請求，稽核軌跡才能證明是哪個 agent 做的檢查；每筆日誌記下公鑰指紋或護照 ID。文件建議用分級信任 (Graduated Trust Levels，例：L0 到 L4，文件未定義各級內容) 給不同的存取權；agent 不得自己提升信任等級或修改自己的權限；也不要因為 TLS 在代理處終止，就信任呼叫者自帶的身分標頭。Agent 身分的治理背景見Agentic 安全與治理現況第 4 章。

實體篩查（文件第 2 節）。文件說，agent 是呼叫者時，比對引擎本身「基本上不變」，變的是周邊脈絡。所以：所有對手方在付款前都篩查；把 agent 身分與信任等級放進篩查脈絡，下游才分得出是 agent 還是人發起的；結果回傳機器可讀的結構（比對／不比對／部分比對與分數），因為 agent 讀不懂 PDF；最低比對門檻由機構設定，agent 不得調低。不要讓 agent 繞過篩查直接呼叫付款端點、不要讓快取結果超過可設定的時間窗（名單常更新）、不要把原始名單開放給 agent（它該呼叫篩查 API，而不是下載整份名單）。

操作者篩查（文件第 3 節）。要辨認的是「誰負責營運這個 agent」，再依機構核准的合規計畫決定哪些當事人需要篩查；文件提醒不要假設開發者、部署者或營運者就是法律客戶。做法是：上線時驗證負責的組織；在合規計畫中定義重新篩查的觸發條件與頻率；把操作者的篩查狀態記入 agent 的信任檔案；要求 agent 在憑證中宣告營運者。不要以為驗證過一次就永遠沒事；匿名 agent（沒有宣告營運者）不得存取篩查服務；營運者自述要經營業登記或 KYB（認識你的企業）資料庫獨立驗證。

3.3 簽署稽核軌跡：讓紀錄「被改了看得出來」

Section 4 要的是防竄改的紀錄，把已驗證的 agent 與篩查請求、結果連起來。文件特別聲明：接下來的細節描述的是一種選配的簽署加雜湊鏈設計；相關的 MCPS Internet-Draft 是個人提交的進行中工作，不是已採納的 MCP 標準；需要這層保護時，要選一個經過審查、可互通的設定檔，而且無論選哪種設計，都要套用日誌保護控制。（這與MCP 安全第 5 章講的 MCPS 定位一致。）

它描述的設計是：agent 用私鑰簽署每個篩查請求（含唯一的一次性值 nonce 與時間戳）；伺服器簽署每個回應；每筆稽核項目含前一筆的 SHA-256 雜湊，串成雜湊鏈，並記錄 agent 身分、呼叫的工具、篩查參數的雜湊（不存原始參數，為了隱私）與結果。保存期間依適用法規（文件寫通常 5 年，教材不查證），並可匯出供監理檢查。不要只靠應用程式日誌（它們不防竄改）；不要把稽核紀錄存在 agent 可控的儲存；不要省略 agent 身分；雜湊鏈出現缺口代表遭竄改或遺失，必須觸發告警。

3.4 核心概念：未解決不等於放行

失效即拒絕 (Fail-Closed)：篩查沒做完，付款就不能走

是什麼
Section 5 的第一句：不完整或不可用的篩查結果，要視為未解決，絕不當作放行。結果未解決時，暫緩交易執行；依機構核准的政策，可以有限次重試、人工審查或拒絕。同一節還特別說：服務失敗本身不是確認的制裁命中，要由合規負責人為每種情況定義處置。
為什麼
錢一旦送出通常難以追回，而篩查失敗是最誘人的「先放過去」時機。文件還提醒一個攻擊面：篩查失敗率升高，可能是有人刻意發動阻斷服務，目的就是逼系統退回放行 (fail-open)。
怎麼被繞過（概念層級）
常見的是善意的後備邏輯：「篩查逾時就先放行、事後補查」「回應含糊就當沒問題」「錯誤一律寫『系統忙碌』」。最後一種的隱性代價是：錯誤不區分「服務不可用」與「已完成且命中」，agent 與營運人員就無法決定下一步；無上限的重試還可能被拿來做時間差探測。
怎麼防
見下表；文件另要求長時間不可用時用熔斷器 (Circuit Breaker) 完全停止 agent 發起的付款，並在需要人工核准時，讓核准者看到並確認關鍵交易資料（引用 Transaction Authorization Cheat Sheet）。
常見誤解
「失效即拒絕等於把這筆交易當成命中制裁。」文件明說不是：它是技術閘門，防止必要檢查未完成時就執行；與「確認命中後依法必須封鎖」的法律義務是兩回事，後者怎麼處置要由合規負責人決定。

和你已讀過的「失敗姿態」怎麼接

詞彙表裡的失效安全 (Fail Securely)是廣義原則：出錯時落在安全的狀態。失效即拒絕是它的一種具體形式：當「安全的狀態」就是不執行時，失敗就拒絕。RAG 安全第 4 章在 RAG 管線也講了同一件事；而Agent Control Standard 第 3 章卻說 ACS 預設是放行，用強制力換可用性。作者整理，非官方：兩者並不矛盾，是在不同動作上做不同選擇；AML 文件處理的是涉及錢與法律義務的動作，所以選了拒絕。ACS 章的情境 B 說退款這種不可逆、涉及金錢的動作不適合 fail-open，與這裡的做法一致。需要記得的是：文件沒有把「失效即拒絕」和 ACS 並列，這個連結是教材的讀法。

作者整理，非官方：Section 5 被改過，教材採最新版

2026-06-03 的首次提交，Section 5 開頭是「系統必須拒絕交易」；2026-10-04 的提交（標題為 Distinguish unresolved sanctions screening from confirmed matches）改成現在的寫法：未解決、不是放行，服務失敗不等於確認命中。教材採最新版。這個修訂本身就說明：技術上的「暫緩」和法律上的「封鎖」是不同的東西。

本章重點與自我檢核

  • 軟體的身分驗證與授權，不等於辨識法律客戶；記錄 agent 為誰行事屬應用程式安全控制，義務由合規負責人定義。
  • 先用密碼學確認 agent 身分與營運者，才可以篩查；自我宣告標頭一律拒絕，匿名 agent 不得使用篩查服務。
  • 簽署且雜湊串接的稽核軌跡是選配設計；雜湊鏈缺口要告警；紀錄存放在機構控制的基礎設施，且只存參數的雜湊。
  • 篩查未完成＝未解決，不是放行；失敗要記錄、區分原因、設熔斷器；它是技術閘門，不等於把交易視為制裁命中。
  • 我能說出篩查前要確認哪兩件事（agent 身分與營運者），以及為什麼不能只用自我宣告標頭。
  • 我能解釋「未解決不等於放行」，以及它和「命中」的差別。
  • 我能說出失效即拒絕與失效安全、ACS 預設放行的關係，並標出哪一句是作者整理。
