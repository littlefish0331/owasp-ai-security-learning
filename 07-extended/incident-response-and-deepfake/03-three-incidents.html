第 3 章　三種事件的應變

  • 預估閱讀：約 10 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3

第 2 章回答「這是不是 AI 事件、有多嚴重」。這一章回答下一個問題：接下來做什麼。指南的事件特定章把 AI 事件分成三種：攻擊 AI 系統、攻擊供應鏈、攻擊第三方模型供應商，每種都依 NIST 生命週期寫出偵測與分析、圍堵、根除、復原、事後活動。不同的事件，第一個動作可能完全不同：有的要隔離系統提示詞，有的要輪換 API 金鑰，有的要盤點某個套件的所有版本。

3.2 兩個貫穿的原則

圍堵要「立即而且成比例」

是什麼
供應鏈一節的第一句圍堵建議是：圍堵應立即且與業務衝擊成比例。可行的話下線模型，但要先評估相依關係，以及它的輸出是否餵給關鍵業務流程。如果衝擊小，就隔離受影響模型、關閉服務基礎設施。
為什麼
AI 系統常常被藏在既有應用裡，其輸出被其他系統當作輸入。一刀切下線，可能讓依賴它的流程一起停擺；什麼都不做，則讓受污染的輸出繼續擴散。嚴重度（第 2 章）決定這個權衡往哪邊傾斜：高嚴重度要積極、立即的圍堵（例如下線 AI 系統、切斷 API）。
運作方式
先查資產清單與網路／工作流程圖，找出誰在使用這個模型的輸出；再依事件類型選用手段：自家模型移除容器、停用端點；API 模型切斷與上游的連線並輪換機密；套件問題則盤點所有版本。
在哪個控制層
屬於回應 (response) 類控制。作者整理，非官方：它依賴準備階段的資產盤點與依賴關係圖，沒有這些，成比例的判斷就沒有依據。
常見誤解
「圍堵就是關機。」指南列的圍堵還包括節流查詢量、限縮 IAM、隔離系統提示詞、金絲雀提示詞、通知使用者，不全是關機。另一個誤解：「嚴重度低就不用圍堵。」指南說的是低嚴重度可以採取破壞性較小的圍堵。

3.3 準備階段要先決定的三件事

事件發生時才討論「範圍多大、多快要處理、誰上場」就太晚了。指南在準備階段要求先決定這三件事，並與第 2 章的嚴重度矩陣連動。

表 3-2　三個準備決定（意譯）
決定指南怎麼說要先備好什麼
爆炸半徑不只受損的基礎設施，還包含：受影響的模型版本、資料集（訓練、驗證、測試、生產）、依賴其輸出的應用與服務（即使沒有直接被攻擊）、受其決策影響的使用者與業務決策數量（例如被核准的詐欺交易）、財務與聲譽暴露、下游使用其資料或輸出的其他 AI 系統完整的資產清單與網路／工作流程圖，用來對映相依與傳播路徑；能偵測擴散的 AI 專用監控；為嚴重度矩陣各維度訂好衡量準則
回應時間義務（SLA）SLA 應與嚴重度掛鉤，每個等級都要定義：初步圍堵時間、根除時間、RTO、RPO（對模型較不適用、對資料完整性較適用）、通報頻率。需考慮系統關鍵性、潛在傷害、法規要求、停機成本。官方範例（Critical，嚴重度 4）：初步圍堵 < 15 分鐘、根除 < 4 小時、RTO < 8 小時、立即通知高階主管各嚴重度等級的義務表；適用的資料外洩通報法規；停機成本估算
AI 事件應變團隊（AIRT）傳統 IT 事件應變角色仍然不可或缺（提示詞注入可能仍需要改防火牆規則；外洩資料集仍需要鑑識的證據保管鏈）；在其上疊加 AI 專長角色：AI 安全專家、機器學習工程師、提示詞注入／濫用分析師、資料科學家、模型治理負責人（可決定是否回滾或啟動停用開關）、倫理與風險顧問、AI 紅隊負責人、AI 產品負責人、MLSecOps 負責人。附錄建議分層啟動：核心團隊（一律啟動）、延伸團隊（依事件類型）、專家團隊（特定情境）角色與人選的名單；每個 AI 系統的對口人

SLA 的數字只是指南給的範例，組織應依自己的系統與法規訂定。

3.4 情境範例 A：供應商端的悄悄改變

情境 A（虛構）：艋舺旅遊的客服助理

虛構 艋舺旅遊是虛構的旅行社。它的線上客服助理以 API 呼叫一家外部供應商的基礎模型，回答行程與退改規則。團隊為客服助理設了一組固定的金絲雀輸入，每小時送一次，並記錄回答的分佈。

  1. 偵測：某天，金絲雀輸入的回答分佈明顯偏離歷史基線（預測漂移告警），同時客戶端的 SDK 與包裝層版本沒有變動。（對應表 3-1「第三方」一欄：預測漂移與客戶端相依檢查。）團隊不能直接斷言這是攻擊還是供應商的悄悄更新，指南也要求先區分「對抗攻擊」與「故障」，所以他們把它當作未明原因的異常來處理。
  2. 嚴重度：評分（示範數字，作者設定，非官方）：A 功能 3（回答不一致，影響顧客決策）、B 資料 2、C 營運 2、D 聲譽與財務 3、E 補救 2。取最高分，整體 High。依第 2 章，High 要立即啟動跨職能團隊：資安、AI 工程、客服主管、法務、公關。
  3. 圍堵：輪換與該供應商端點相關的 API 金鑰，暫停或限制與供應商的 API 互動並建立異常使用的監控（指南「隔離與回滾」）；同時在沙箱中用固定輸入對 API 做影子推論，看是否有異常行為（指南「輸出風險重新評估」）。因此自動回覆暫停，退改規則類問題改由人工客服處理，這是作者為情境補的營運安排，不是指南的條文。
  4. 爆炸半徑：依資產清單，團隊找出漂移期間：(1) 受影響的對話與被回答的退改決定數；(2) 另一個把這些回答摘要後寫進客戶紀錄的內部助理（下游的其他 AI 系統）；(3) 已寄出的確認信。範圍因此比「客服助理」大。
  5. 輸出重新驗證：用另一家供應商或內部規則層，把漂移期間的回答重新驗證一遍，標出需要更正並通知的顧客。（這需要事先保存輸入輸出對；保存提示詞有隱私顧慮，第 4 章會回到這個張力。）
  6. 供應商問責與事後：向供應商的安全與信任團隊升級，要求事後報告與根因分析；重新評估供應商的風險分數；在審查通過前不恢復自動回覆（重新核准流程）。法務審查合約中的通知義務、SLA 與稽核權，並決定是否需要通報主管機關與客戶。去識別化後分享給 AI 事件資料庫等社群。
  7. 這個情境的提醒：金絲雀輸入與漂移監控是事前就要做的準備，事件發生後才設已經太晚；而且一組固定輸入偵測得到的，只是「分佈變了」，不能告訴你原因。

本章重點與自我檢核

  • 指南的事件特定章有三種：攻擊 AI 系統、攻擊供應鏈（主要給自己開發模型者）、攻擊第三方模型供應商（以 API 使用基礎模型者），每種都依偵測與分析、圍堵與根除與復原、事後活動展開。
  • 圍堵要立即且與業務衝擊成比例，先看相依再決定要不要下線。
  • 爆炸半徑涵蓋模型、資料集、應用與服務、決策、財務與聲譽、下游其他 AI 系統，不只是被入侵的主機。
  • SLA 與嚴重度掛鉤；Critical 的官方範例是 < 15 分鐘圍堵、< 4 小時根除、< 8 小時 RTO。AI 事件應變團隊是在傳統角色上疊加 AI 專長。
  • 我能依「我是自己開發模型還是以 API 使用」選對該讀的一節。
  • 我能說出爆炸半徑的六個面向。
  • 我知道 SLA 範例數字只是範例，要由組織自己訂定。
