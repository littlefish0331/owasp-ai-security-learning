第 2 章　Guardian、鉤子與五種處置

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO2
  • 前置：第 1 章

這一章打開 ACS 的引擎蓋。你會看到兩個角色怎麼分工、Agent 在哪些時間點停下來問、Guardian 有哪五種回答，以及一個設計上的巧思：Guardian 自己也分成「規則」與「LLM」兩層，而且 LLM 那層看不到規則。

2.1 兩個角色與兩層 Guardian

  • 被觀察的 Agent (Observed Agent)：以 LLM 為核心、受監控的系統。它在每個鉤子點送出請求。
  • 守衛 Agent (Guardian Agent)：政策執行點，決定該怎麼辦。它自己分兩層：
    • 確定性層 (deterministic layer)：用 Cedar 或 Rego 這類政策引擎，永遠先跑。
    • Agent 層 (agent layer)：一個 LLM，只在確定性層的設定把它委派時才被叫用；它看到的只有確定性層交給它的中間輸出，看不到政策原始碼，而且它的答案還要回到確定性層通過一次。

只用確定性層的部署同樣完全符合規格；委派給 LLM 是選項。這個設計的理由，用你熟悉的語言說：規則負責「一定要擋的」，LLM 只負責規則判斷不了的灰色地帶，而且不讓 LLM 知道規則長什麼樣子，以免它被說服去繞過規則。這句解讀是作者整理，非官方；官方寫的是結構，沒有這樣明白講理由。

2.2 鉤子：Agent 在哪裡停下來問

鉤子 (hook) 是 Agent 執行過程中的一個點：到這裡它必須先停下來，把「我打算做什麼」交給 Guardian，等答案再繼續。規格定義了 19 個原生鉤子，外加「包裝後的 MCP」、Inspect 支柱的 AgBOM 方法與一個存活探測，共 22 個方法。下表依作者整理的類別，列出 19 個原生鉤子（類別是作者整理，非官方；官方的圖分成七類，大致相同）。

表 2-1　ACS 19 個原生鉤子（分類為作者整理，非官方）
類別鉤子什麼時候觸發

不是 19 個都必須實作。ACS-Core 的最低要求只有 7 個：sessionStart、userMessage 或 agentTrigger（二擇一）、toolCallRequest、toolCallResult、agentResponse、sessionEnd，以及（能產生子 Agent 的框架必須實作）subagentStart。其餘如記憶、知識查詢、脈絡壓縮與技能生命週期的鉤子，規格寫「應該實作」，條件是框架觀察得到對應的事件。規格對 subagentStart 給了理由：缺了它，Guardian 看不見跨 Agent 的傳播（混淆代理人 (Confused Deputy) 這類攻擊）。技能鉤子則是：若 AgBOM 已列出技能元件，就應該發出技能生命週期鉤子，免得 Guardian 對清單已經暴露的組合面毫無所知。

並非每個鉤子都能被「決定」。官方表格標示：postCompact、subagentStop、skillUnload、turnEnd、sessionEnd 不是決定點，只做稽核與紀錄；其餘多數鉤子可以被 Guardian 決定。另外，toolCallResult 這一個很有意思：它在「工具結果被 Agent 讀進脈絡之前」就觸發，正好是間接提示詞注入進來的路口，Guardian 可以在這裡檢查。這個觀察是作者整理，非官方。

三個細節值得記住。第一，Agent 必須等決定並照做：規格寫道，一個發出鉤子卻不套用判決的框架「不符合規範」；鉤子要成為控制點，Agent 必須真的等。第二，修改的規則很嚴：兩種修改形式（整段替換、結構化編輯）不能混用，目標也不能重疊；Guardian 若送出違反規則的修改，Agent 看不出它的意圖，就必須當成拒絕處理並記稽核。第三，延後過期預設是拒絕，這與下一章的失敗姿態預設剛好相反，原因第 3 章會說明。

2.4 核心概念：三支柱與設定檔

Instrument、Trace、Inspect

是什麼
ACS 把需求組織成三個支柱：Instrument（鉤子與處置，也就是前面三節）、Trace（把每個鉤子與每個決定記成 OpenTelemetry 的 span 與 OCSF 事件，讓既有資安工具讀得懂）、Inspect（產出 AgBOM，即時盤點 Agent 用了哪些模型、工具與相依，可序列化為 CycloneDX、SPDX 或 SWID）。
為什麼這樣切
官方用語是讓 Agent「可檢視、可追蹤、可操控」(inspectable, traceable, instrumentable)：先能看見它是什麼 (Inspect)、再記錄它做了什麼 (Trace)、最後才能在執行期操控它 (Instrument)。這個對應是依官方措辭整理的。
怎麼組裝（概念層級）
ACS-Core 是強制基線：Instrument 加上線路格式與稽核鏈。Trace、Inspect、來源證明 (Provenance)、密碼學簽章、強化稽核等是設定檔 (profile)，部署在握手時各自宣告，可以獨立加上。
怎麼防（它如何限制風險）
ACS-Core 保證兩件事：通道是被認證的，而且被觀察的 Agent 會遵守 Guardian 在四種「必須支援」（ALLOW、DENY、ASK、DEFER）的處置上的決定。規格也說清楚它不保證什麼：不保證政策寫得嚴格，也不保證稽核鏈能防得住被攻破的 Guardian（那是 ACS-Crypto 與 ACS-Audit 設定檔的事，因為基線的 HMAC 是對稱式）。規格的說法是：一個寬鬆的 Guardian 是「符合但寬鬆」的部署，不算違規。另外注意：修改 (MODIFY) 在 0.1.3 版之後從「必須支援」降為「應該支援」，CHANGELOG 的理由是有些框架（例如 shell 鉤子整合、沒有改參數介面的 IDE 外掛）根本做不到。所以「最低限度符合」的部署可以允許或拒絕一個動作，但不能改動它；要做遮蔽之類的內容改寫，就需要支援 MODIFY。
常見誤解
「ACS 的三個支柱都是必須實作的。」不是。只有 ACS-Core 是強制的。其餘是自行宣告的設定檔，而且前一章說過，宣告不經任何人驗證。另一個誤解是：「Guardian 是個 LLM 在判斷。」規格的預設是確定性層先評估，LLM 層是可選的委派。

本章重點與自我檢核

  • 兩個角色：被觀察的 Agent 送請求、Guardian Agent 決定；Guardian 內部確定性層（Cedar／Rego）先跑，LLM 層是選擇性的委派，且看不到政策原始碼。
  • 19 個原生鉤子，涵蓋工作階段、訊息、知識與記憶、工具、脈絡壓縮、子 Agent、技能生命週期；ACS-Core 只強制其中最低限度的 7 個（其餘「應該實作」）；部分鉤子只做稽核，不是決定點。
  • 五種處置：允許、拒絕、修改、詢問、延後。Agent 必須等並照做；修改的規則嚴格；延後過期預設拒絕。
  • 三支柱 Instrument、Trace、Inspect；ACS-Core 是強制基線，其餘是自行宣告的設定檔。
