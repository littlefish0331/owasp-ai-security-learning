第 3 章　失敗姿態與情境

  • 預估閱讀：約 10 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3（並回顧 LO1、LO2）
  • 前置：第 2 章

每一個「檢查站」都要回答一個問題：檢查站壞了的時候，要放行還是攔下？ACS 的答案是：看你怎麼設定，而它的預設是放行。這一章把這個取捨攤開，包括它的理由、它的代價，以及規格與參考實作各自承認的缺口。

3.1 兩個失敗姿態

規格其實定義了兩個，不是一個。兩個都預設為 proceed（放行）。

表 3-1　ACS 的兩個失敗姿態
姿態什麼時候用到選項與預設規格要求的紀錄
啟動姿態 (startup posture)工作階段一開始，握手 (handshake/hello) 就失敗：Guardian 不可達、逾時沒回，或出錯卻沒有回握手回應proceed：讓這個工作階段在沒有守衛的狀況下開始（預設）；refuse：不啟動。設定在帶外 (out of band)沒有 Guardian 可收事件，所以要記在部署自己的稽核日誌
決策失敗姿態 (on_decision_failure)工作階段中，某一步在協商逾時內沒收到可用的決定：Guardian 沉默、傳輸失敗（連線被拒、TLS 失敗、回應格式錯誤），或 Guardian 回錯誤而非決定proceed：該步照常執行，這是預設，稱為失效即放行 (fail-open)；deny：該步阻擋，稱為失效即拒絕 (fail-closed)。在握手時協商每一個沒有決定就放行的步驟，都必須記為稽核事件

兩者的差別在「發生在握手前還是握手後」。決策失敗姿態是握手時協商出來的，所以管不到一次根本沒完成的握手；這就是為什麼需要另一個啟動姿態。還有一條重要規則：只要決定在逾時內到了，Agent 必須照做，不論姿態是什麼。姿態只管「沒收到決定」的情況。

3.2 為什麼預設是放行

規格自己把理由與代價寫得很直接。依其說法：

  • 理由是可用性。預設 proceed 是為了讓一個慢的、出錯的或不可達的 Guardian「不要讓正式環境停擺」。
  • 代價是強制力。規格原話的意思是：fail-open 用強制力換可用性；一個能擾亂通道的對手，可以把「控制」變成「稽核」。換句話說，攻擊者不必說服 Guardian 放行，只要讓它聯絡不上，Agent 就照常執行了。
  • 緩解是留痕。放行時必須記稽核事件，讓繞過「可見而不是無聲」。這是偵測，不是預防。
  • 不能接受這個取捨的部署，改成 deny。這就是 fail-closed。

用你熟悉的類比：這像 CI 裡一個「必要檢查」的服務掛了。你可以選擇「檢查服務掛了就讓合併繼續」（不擋住出貨，但風險自負），或「檢查服務掛了就擋合併」（安全，但服務一掛全公司停擺）。這個類比是作者整理，非官方，好處是它把「安全 vs. 可用性」這個老問題套到 Agent 上；限制是 Agent 的動作可能不可逆（寄出信件、刪除資料），遠比一次合併難回頭。

3.3 一個刻意相反的預設

你在第 2 章看到，DEFER（延後）有一個逾時處置 timeout_decision，預設是 deny。這與決策失敗姿態的預設 proceed 剛好相反，規格明說這是刻意的：

  • 決策失敗是「一個從未回答的 Guardian」，我們不確定它有沒有疑慮。
  • 過期的 DEFER 是「一個已經標記疑慮、卻沒能解決的 Guardian」，疑慮是明確存在的。

所以規格的邏輯是：一個降級但仍能發出 DEFER 的 Guardian，應該失效即拒絕 (fail closed)；一個完全沉默的，才失效即放行 (fail open)。這個區分有道理，但也可以看出一個侷限：它假設「沉默」代表沒有疑慮。如果沉默是因為被攻擊者擾亂造成的，那個假設就不成立，這也是為什麼規格同時承認 fail-open 可以被利用。

3.5 情境範例 A：把判斷全交給 LLM

情境 A（虛構）：昊天證券的 Guardian 設計

虛構 昊天證券是虛構的證券公司。團隊設計一個 Guardian，想把所有判斷交給一個 LLM：「讓 LLM 讀完整份政策文件，再判斷每個工具呼叫該不該放行，這樣最靈活。」一位工程師提出反對。

  1. 看問題：如果 Guardian 本身是 LLM，且它看得到政策文件，那麼它有和被監控的 Agent 一樣的弱點：可以被輸入說服。攻擊者只要讓提示詞影響到 Guardian 的判斷，政策就被繞過。
  2. ACS 的設計怎麼處理：確定性層（Cedar／Rego）永遠先跑，擋下一定要擋的；只有確定性層解不出來的灰色地帶，才委派給 LLM 層；LLM 層看到的只有確定性層給的中間輸出，看不到政策原始碼；它的答案還要回到確定性層通過一次。
  3. 對應的概念：這是縱深防禦與最小暴露的組合：LLM 層只拿它需要的資訊（最小權限的資訊版本），且最終決定權在不會被說服的確定性規則。對應第 2 章 2.1 節。
  4. 該採的控制：把「一定要擋的」寫進確定性政策；LLM 層僅用於政策無法機械化判斷的情況；LLM 層的答案必須過確定性層；對 LLM 層本身的輸入也視為不可信（它同樣可能遇到提示詞注入）。
  5. 這個情境的提醒：「更靈活」與「更安全」常是反方向。ACS 的預設（確定性層先跑）選擇的是後者，並把靈活性做成可選的委派。

3.6 情境範例 B：Guardian 當機的那個週末

情境 B（虛構）：北辰物流的客服 Agent

虛構 北辰物流是虛構的物流公司。客服 Agent 可以查詢訂單，也可以申請退款（需 Guardian 核可）。團隊採用預設設定。某個週末，Guardian 服務因為一次部署失敗而不可達了十二個小時，客服平台照常運作。週一，財務發現期間有一批異常高額的退款，其中有幾筆如果 Guardian 在線，會被 ASK 要求人工核准。

  1. 先看症狀：Guardian 不可達，Agent 還是照常執行，沒有人被通知。這正是預設 on_decision_failure: proceed 的行為。
  2. 哪一環出問題：團隊把「預設值」當成「安全的值」。規格明說預設放行是為了可用性，且「能擾亂通道的對手可把控制變成稽核」。退款這種不可逆、涉及金錢的動作，不適合用這個姿態。
  3. 該採的控制：(1) 對高風險的鉤子（如退款的工具呼叫）把 on_decision_failure 設為 deny (fail-closed)；(2) 規格要求放行的步驟必須記稽核事件，要監看這類事件並設告警，否則留痕沒有人看等於沒有偵測；(3) 規格建議直接監控鉤子路徑上的決策失敗，不要只靠 system/ping 推論健康狀態（因為 Guardian 可能回得了 ping，卻拒絕所有簽章鉤子，例如金鑰解析中斷時）。
  4. 規格可以做到什麼、做不到什麼：規格的姿態是部署層級的（握手協商），本教材讀到的內容並未說明能否對個別工具單獨設定；如果需要只對退款設 fail-closed，要確認所用實作是否支援。這一點教材未能確認。
  5. 這個情境的提醒：fail-open 不是 bug，是明講的取捨；責任在部署者要不要接受它。預設值的意思是「規格作者假設大多數部署更怕停擺」，而不是「這是安全的」。

3.7 與前面主題的整合

  • 與 ML Top 10：ACS 管的是 Agent 的執行期動作，不處理訓練資料、模型參數這類 ML 生命週期風險。
  • 與 Agentic Skills Top 10：ACS 的技能生命週期鉤子（skillRegister、skillLoad、skillUnload）讓 Guardian 在技能進入、啟用時介入，這是 AST10 的 AST09（治理）與 AST03（權限過大）可以被執行期強制的地方。對應是作者整理，非官方：ACS 的文件把這些鉤子描述為「Guardian 不被技能這個組合面蒙蔽」，沒有寫它對應哪個 AST 條目。
  • 與 AI Exchange 控制地圖：ACS 接近 OVERSIGHT 與 LEAST MODEL PRIVILEGE 的執行期實作，但官方沒有把 ACS 放進 AI Exchange 的分類，這是作者整理。

本章重點與自我檢核

  • 兩個失敗姿態都預設為放行：啟動姿態（握手失敗）與決策失敗姿態（鉤子點沒收到決定）。決定在逾時內到了，必須照做。
  • 預設放行是為了可用性；代價是強制力：能擾亂通道的對手可把控制變成稽核。放行必須留痕，但留痕是偵測，不是預防。
  • DEFER 過期的預設是拒絕，與決策失敗的預設刻意相反：已標記疑慮卻沒解決，與完全沉默，不一樣。
  • 參考實作自述缺口：線路未認證、預設放行、只有 2 個鉤子被即時評估、不主張互通性。README 自己限定它的主張範圍很窄，不要把它當成可直接上線的防線。
  • 我能說出兩個失敗姿態各自的預設與適用時機。
  • 我能解釋為什麼 fail-open 可以被利用，以及規格要求的緩解。
