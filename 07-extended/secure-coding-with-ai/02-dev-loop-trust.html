第 2 章　開發迴圈的信任邊界

  • 預估閱讀：約 7 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO2
  • 前置：第 1 章

Secure Coding with AI 的開場很直接：2026 年的 AI 編碼工具已經不只是補完程式碼，而是會執行 shell 指令、安裝套件、改檔案、跑測試、連網、推分支；而且不少開發者開著自動接受，讓它帶著自己的完整權限做事。這一章先畫出文件的威脅模型，再讀前三節：助理給的套件名稱、助理給的版本，以及助理讀進來的文字。

檢查的時點安裝之前（名稱一旦被解析並安裝，惡意程式可能已執行）合併之前與每次 CI

最後一列的「時點」差別是作者整理，非官方：它說明為什麼兩個檢查要放在不同的位置，而不是用同一個閘門解決。

這兩節在 LLM Top 10 2026 裡有對應的官方說法：LLM04:2026 供應鏈 (Supply Chain) 把「過時的套件」與「程式助理編出不存在的套件名稱、被攻擊者預先註冊」都列為風險，並稱後者為幻覺套件名稱搶註 (Slopsquatting)。Cheat Sheet 本身沒有使用這個詞，也沒有引用 LLM04；兩者的對應是作者整理，非官方。

2.4 核心概念：助理讀進來的文字，就是它的輸入

開發迴圈裡的間接提示詞注入

是什麼
文件的說法是：助理讀到的任何內容，都可能含有改變它行為的隱藏指示。這就是LLM01:2026 提示詞注入 (Prompt Injection) 的間接形式，只是發生地點換成你的開發迴圈。
為什麼會發生
兩個原因疊在一起。第一，模型沒有強制區分指令與資料的機制（見 提示詞注入防護第 1 章）。第二，「修好這個議題」這類任務本身就要求助理去讀外部文字，而助理執行時用的是開發者的權限。文字來自低權限的人，動作卻由高權限執行。
怎麼被利用（概念層級）
攻擊者不需要碰開發者的機器，只需要在助理「會去讀」的地方放文字：開一個議題、留一則 PR 意見、在文件或 changelog 裡放內容。之後開發者一句例行的請求，就把文字送進助理。文件列的後果是改動不相干的檔案、削弱安全控制、外洩程式碼。本教材不提供任何具體的注入文字。
怎麼防
文件的五項建議：把所有倉庫內容當成不可信輸入；助理處理完外部內容後，檢查有沒有非預期的變更；用工具先清理或標記疑似注入的樣式；把助理的脈絡限縮到完成任務所需的最少檔案；處理過外部貢獻者或公開倉庫的內容後，稽核助理做了什麼。再補一個作者整理，非官方的檢查角度：看一次工作階段裡，助理是否同時具備三件事，即讀不可信內容、握有敏感存取、能改變狀態或對外連線（見 Rule of Two）。三件事同時成立時，上述「事後檢查」就是唯一的防線，所以第 3 章的沙箱要把其中一件拆掉。
常見誤解
「這是來自 GitHub 議題，所以是熟悉的環境、不用防。」文件明說不要因為內容出現在熟悉的位置就假設它安全。另一個誤解：「清理工具能解決。」清理或標記是降低成功率的一層，依 LLM Prompt Injection Prevention Cheat Sheet 的立場，這類篩選不是安全邊界（見提示詞注入防護第 2 章）；把它對應到本節是作者整理，非官方。

本章重點與自我檢核

  • 文件列五類威脅來源：倉庫內容、MCP 伺服器、規則檔、助理本身、CI/CD 助理；共同點是文字來自低權限的人，動作由高權限執行。
  • 第 1 節管名稱（先確認存在、看年齡與維護者），第 2 節管版本（弱點審計與 CI 失敗）；兩者的檢查時點不同。
  • 第 3 節的六條管道都對應開發者的一句日常請求；處理外部內容後要檢查助理的實際動作。
  • 清理或標記注入樣式只是一層，不是邊界；要靠限縮助理同時握有的能力（第 3 章）。
