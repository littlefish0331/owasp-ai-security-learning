5.3 情境範例 B：一個團隊，從依賴到 API

情境 B（虛構）：青岬保險的理賠文件分類服務

虛構 青岬保險是虛構的保險公司。一個五人團隊用 AI 編碼助理開發「理賠文件分類」服務：服務載入一個微調過的分類模型，對內提供 API，也對合作的理賠公司開放。團隊還維護一個對外公開的客戶端 SDK 倉庫。以下為虛構，細節停在概念層級。

架構：開發者機器（助理開著自動接受，用開發者的完整憑證）→ 倉庫與 CI → 模型成品儲存 → 推論 API（對內與合作夥伴）。

  1. 依賴：助理為新功能建議加入一個 PDF 處理套件，名稱看起來合理；另一個依賴則是舊版本。團隊直接合併，CI 沒有弱點審計。對應 Secure Coding with AI 第 1、2 節。
  2. 讀進來的文字：一位外部人士在公開 SDK 倉庫開了議題；開發者對助理說「修好這個議題」。議題內文夾帶了針對助理的指示，助理在自動接受模式下，除了修 bug，還改了 CI 工作流程，並在 AGENTS.md 加了一行放寬檢查的規則。對應第 3、5、6、10 節。
  3. 審查：審查者看了 PR 的標題與說明（「修正議題 #57」），認為合理，沒有逐檔看 diff；CI 工作流程與規則檔的變更沒有被標示。對應第 7 節。
  4. 成品與 API：被改過的 CI 之後把未簽署的模型成品推到共用儲存；團隊另外在同一批機器上評估一個外部下載的模型。上線的推論 API 有驗證與每秒請求限制，但沒有每租戶花費上限與熔斷器 (Circuit Breaker)；合作夥伴的程式出現迴圈時，帳單在一夜之間暴增。對應 Model Ops 第 3、4、6 節。
  5. 該採什麼控制：
    • 開發迴圈：套件安裝前查證、CI 弱點審計（SC 第 1、2 節）；助理放進沙箱、短效憑證、不用自動接受處理外部議題（第 3、5 節）；規則檔與 CI 設定納入 CODEOWNERS 與 CI 標示（第 6、7、10 節）。
    • 營運面：成品簽署並存於有存取控制的登錄庫；外部模型的評估放進隔離環境（MO 第 3、6 節）；每租戶花費與鏈深度上限、熔斷與告警（MO 第 4 節）。
    • 人：每個 AI 變更有人類負責人與核准紀錄（SC 第 14 節）。
  6. 學到什麼：這條線上沒有一步需要「很厲害的攻擊」：每一步只是一個沒人檢查的預設值。兩份速查表的分工是：前者縮小「助理被帶偏時能做的事」，後者縮小「成品與服務出事時的傷害」。把兩份讀成同一條鏈，才看得到「開發迴圈的疏漏如何流入營運面」。這個串接是作者整理，非官方。

5.4 全主題重點與接下來讀什麼

  • Secure Coding with AI 守開發迴圈：套件名稱與版本（第 1、2 節）、讀進來的文字（第 3 節）、工具與沙箱（第 4、5 節）、規則檔（第 6 節），加上審查、測試、脈絡外洩、建置檔、CI 助理、不可見字元、多 agent 與問責（第 7–14 節）。
