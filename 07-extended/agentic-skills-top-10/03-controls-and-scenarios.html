第 3 章　防禦與情境

  • 預估閱讀：約 7 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章

每個條目檔都有一段 Preventive Mitigations。把十段並排讀，你會發現官方建議的控制反覆圍繞幾個主題。這一章先整理這個規律，再用兩個虛構情境練習「看到症狀、推回條目、選控制」。

3.1 十段緩解建議，其實只有幾個主題

下表「官方的獨立項目」是作者逐條讀官方 Preventive Mitigations 的標題後數的結果；「主題」這個歸類是作者整理，非官方。官方是各條各自列舉，沒有做這樣的跨條目彙整。

表 3-1　官方緩解建議的重複主題（歸類為作者整理，非官方）
主題有獨立項目的條目官方寫到的做法（摘要）
來源與簽章AST01、AST02、AST07以密碼學簽章綁定可撤銷的發佈者身分；來源追溯；透明日誌；每次更新都驗證簽章。官方特別強調：簽章證明作者是誰，不證明內容安全。
內容釘選AST02、AST05、AST07以不可變的雜湊值（例如 sha256）釘選技能與相依性，而不是用版本範圍；外部引用內容要記錄雜湊並每次驗證，或直接內嵌進簽章的技能包。
權限宣告與強制AST03、AST04、AST05（網域允許清單）；AST02 的內部鏡像／允許清單屬類似的來源收斂要求技能宣告權限清單；每個技能使用範圍有限的憑證；網路用網域允許清單而非開關；執行期強制而非只宣告；用沙箱測試比對宣告與實際行為。
隔離AST01、AST04、AST06預設以容器隔離技能執行；每個技能獨立行程；控制介面綁定本機並要求驗證；限制熱重載與工作區覆蓋。
掃描與測試AST01、AST02、AST04、AST05、AST08同時掃描程式碼層與自然語言指令層；用行為分析而非只比對特徵；在沙箱觀察實際行為；掃描整個技能目錄；持續重新掃描；掃描器結果只作參考、不當唯一關卡。
清單、審批與稽核AST01、AST07、AST09集中的技能清單（名稱、版本、雜湊、安裝者、最近掃描狀態）；安裝與更新的審批流程；技能動作的稽核日誌；撤銷程序；整合既有 CMDB、ITSM、CASB。

這張表有兩個用法。第一，面對一個新的 Agent 平台，可以先問「這六類控制我各有沒有」，而不是逐條背十個條目。第二，注意官方自己有一句很重要的警語放在 AST08：掃描器結果只能當參考 (advisory)，而且掃描器自己的 LLM 也可能被注入。也就是說，「有掃描」不等於「安全」。

另外兩點要補充。表中沒列出某個條目，只代表官方在那一條沒有獨立列出該主題，不代表不需要；各條的項目數也不一，不代表風險大小。還有，AST04 的第一項不在這張表的任何一列：它是使用安全的解析器（例如用安全模式載入 YAML、設定允許的鍵清單），因為中繼資料在載入時就會被自動解析，是解析層的獨立控制。

3.2 從症狀推回條目與控制

3.3 情境範例 A：簽章過的技能，行為卻變了

情境 A（虛構）：鳳梨財務的報表技能

虛構 鳳梨財務是虛構的會計軟體公司。團隊在內部登錄庫安裝了一個「匯率換算」技能，已簽章、以雜湊釘選，並通過掃描器。技能的說明文件只有幾行，其中一行指示 Agent「依外部供應商的 API 說明頁格式化查詢」，並給了一個網址。三個月後，財務人員發現 Agent 偶爾會在換算後多做一件沒人要求的事。技能檔案的雜湊與上線時完全一致。

  1. 先看症狀：技能檔案本身沒有變（雜湊一致），但行為變了。對照圖 3-1，指向 AST05：變動的可能是技能執行時才讀取的外部內容。
  2. 哪一環出問題：簽章與釘選只涵蓋技能這包檔案。外部網址在執行時回傳什麼，不在任何一道控制之內。掃描器在審查時看到的可能是當時乾淨的版本（官方的「審查者被騙」形態）。
  3. 對應條目與相近條目：主要是 AST05。若發現外部網址的內容曾被刻意改寫成指令，它也和 AST02 的供應鏈脈絡相關，但依官方決策樹與 AST05 的說明，AST02 的完整性控制管不到這一段。
  4. 該採的控制（取自官方 AST05 的緩解清單）：在審查時為每份外部文件記錄內容雜湊並於每次載入時重新驗證；盡量把外部說明內嵌進簽章過的技能包；用網域允許清單限制可抓取的來源；傳遞性地審查引用鏈；盤點全機隊技能各自抓哪些外部來源；持續重新掃描而不是只在安裝時掃一次。
  5. 這個情境的提醒：「已簽章、已釘選、已掃描」三項都成立，不代表執行時看到的內容沒有變。這正是 AST05 官方所說的「簽章技能對該網址回傳什麼什麼也沒說」。

3.4 情境範例 B：沒人知道裝了什麼

情境 B（虛構）：藍鵲電商的開發者各自安裝

虛構 藍鵲電商是虛構的電商公司。工程師們為了提高效率，各自在自己的開發環境安裝了許多 Agent 技能，安裝只要一行指令。資安團隊在一次內部盤點時發現：沒有人說得出全公司裝了哪些技能、各自什麼版本、誰裝的；這些技能和開發者的雲端憑證放在同一台機器。一週後，外部通報其中一個熱門技能被發現含有不當行為，資安團隊無法回答「我們有沒有裝」。

  1. 先看症狀：最核心的問題是「答不出裝了哪些技能」。對照圖 3-1，指向 AST09 缺乏治理。
  2. 哪一環出問題：技能安裝沒有進入任何組織管控：沒有清單、沒有審批、沒有稽核、沒有撤銷程序。官方描述這是安全團隊「看不見也控制不了」的影子 AI 層。
  3. 相近條目：憑證與技能同機放置，涉及 AST03（權限過大）與 AST06（隔離薄弱）；沒有人重新檢查已裝的技能，涉及 AST07（更新漂移）與 AST08（掃描不足）。AST09 在官方交叉引用裡被描述為讓這些風險得以長期存在的背景條件。
  4. 該採的控制（取自官方 AST09 的緩解清單）：建立集中技能清單（名稱、版本、雜湊、安裝日期、安裝者、最近掃描狀態）；技能安裝的審批流程；給 Agent 非人類身分與範圍有限的憑證並定期輪替；完整稽核日誌；整合既有 CMDB／ITSM／CASB；與離職和事件應變連動的撤銷程序。
  5. 這個情境的提醒：先有清單，才談得上回答「我們有沒有受影響」。清單是所有後續控制的前提，這也是為什麼官方把它列在 AST09 的第一項。

本章重點與自我檢核

  • 官方緩解建議可歸成六類重複主題：來源與簽章、內容釘選、權限宣告與強制、隔離、掃描與測試、清單審批與稽核（歸類為作者整理，非官方）。
  • 簽章證明作者是誰，不證明內容安全；掃描器結果只當參考，不當唯一關卡。
  • 已簽章、已釘選、已掃描，仍擋不住執行時才讀取的外部內容（AST05）。
  • 先有技能清單，才回答得了「我們有沒有受影響」（AST09）。
  • 我能對一個 Agent 平台問出「六類控制各有沒有」。
  • 給我一個症狀，我能說出最先要查的條目與控制。
  • 我能說明為什麼「掃描通過」不是安全的證明。
