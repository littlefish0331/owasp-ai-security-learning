第 4 章　三層控制與情境

  • 預估閱讀：約 6 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO4
  • 前置：第 3 章

官方不是丟給你 50 條控制清單，而是把每個條目的控制分成三層，並標註每項控制是靠買、靠自建，還是兩者並用。這一章先學怎麼讀這個結構，再用兩個虛構情境練習：看到症狀，推回條目，再決定今天能做什麼、下一季要做什麼。

4.1 Tier 與 Buy／Build 怎麼讀

表 4-1　官方的三層成熟度與範圍標註
層級官方定義例子（DSGAI14 遙測外洩）
Tier 1　基礎 (Foundational)團隊用現有工具大概一個 sprint 能上線的控制，用最小摩擦降低最多暴露預設最少日誌（預設關閉內容層級記錄）、強化觀測平台的存取控制、保留期限與來源系統對齊、第三方觀測廠商的管控
Tier 2　強化 (Hardening)可能需要架構調整、新工具或跨團隊協調，影響高、需要中等投入對日誌與追蹤自動掃描個資與機密、分級除錯記錄需核准並自動到期、觀測資料靜態加密
Tier 3　進階 (Advanced)假設已有成熟計畫：紅隊、差分隱私、形式驗證、自訂偵測模型對觀測平台做洩漏紅隊與桌面演練、對觀測平台的存取做行為異常偵測

每項控制後面還標了範圍：Buy（靠廠商能力）、Build（靠自己工程）、Buy and Build（兩者並用）。這個標註回答的是「這件事我能直接採購嗎？」。官方用「爬、走、跑」(crawl, walk, run) 描述這個設計：幫助不同成熟度的組織，而不是丟出一份無差別的檢核表。

三個要小心的地方

  • Tier 不是風險嚴重度。Tier 3 是「成熟度要求高」，不是「風險小」。一個條目的 Tier 3 控制可能對你的系統才是真正的缺口。
  • Tier 1 也沒有保證「一個 sprint 做得完」。官方寫的是「可能」(likely)，要看你的現有工具。
  • 各條的控制數量不一，不代表風險大小。例如 DSGAI01 的 Tier 1 有九項，DSGAI17 的 Tier 1 只有三項。

4.2 從症狀推回條目與第一步

4.3 情境範例 A：刪除請求之後的幽靈資料

情境 A（虛構）：青林電商的客服助理

虛構 青林電商是虛構的網路商店。它的客服助理會檢索歷史訂單與客服對話，這些內容三個月前被轉成嵌入，存在向量資料庫，並用於一次微調。一位客戶依資料主體權利要求刪除個資。法務確認：CRM 與資料湖的紀錄都已刪除，回覆客戶「已完成」。六週後，因為向量庫遷移，團隊做了一次重新索引。再過一週，客戶投訴：客服助理在回答另一位使用者時，提到了他的姓名與訂單。

  1. 先看症狀：已刪除的資料仍從助理被答出。對照圖 4-1，指向 DSGAI01、DSGAI07、DSGAI08。
  2. 哪一環出問題：刪除流程只認得來源系統。嵌入留在向量庫；刪除前的夜間備份仍保有原始紀錄；重新索引把備份還回向量庫；沒有任何血緣紀錄說明這些嵌入來自哪筆來源，也沒有紀錄說明該紀錄是否被用於微調。這與官方 DSGAI07 的情境幾乎同型：「組織以為已履行抹除義務；其實沒有」。
  3. 對應的條目：DSGAI01（外洩：衍生物持續浮現）、DSGAI07（治理：分類與血緣缺失，衍生物活得比來源久）、DSGAI08（合規：違反抹除義務，且微調後的權重難以移除）。
  4. 官方 Tier 控制怎麼分層：Tier 1：分類標籤傳遞到衍生物、管線入口掃描、自動化保留期限、把保留與抹除義務延伸到 ML 管線；Tier 2：抹除驗證測試（確認刪除真的涵蓋嵌入與備份）、帶來源／授權／負責人標籤的資料目錄；Tier 3：資料到模型的血緣登記冊、為資料主體請求準備的衍生物清單、unlearning 就緒架構。
  5. 這個情境的提醒：先做 Tier 1 的「標籤傳遞與保留期限」，才有後面 Tier 2 的「驗證」可驗。至於已經進入微調權重的資料，官方承認 machine unlearning 目前的技術限制；教材不宣稱有現成解法，Tier 3 的做法也只是「就緒架構」。

4.4 情境範例 B：除錯日誌成了最容易偷的地方

情境 B（虛構）：雲杉保險的 Agent 除錯

虛構 雲杉保險是虛構的保險公司。為了找出理賠 Agent 偶發的異常行為，工程師把「除錯模式」打開，記錄完整的請求與回應，包含 OAuth token、內部 system prompt 與客戶貼上的文件。除錯模式後來沒關，資料一直累積在集中的日誌叢集。幾個月後，一位 SOC 分析師的帳號被釣魚，攻擊者匯出了數週的觀測資料。

  1. 先看症狀：日誌系統成為大規模外洩的來源。對照圖 4-1，指向 DSGAI14 遙測外洩。
  2. 哪一環出問題：官方的觀察是：觀測平台往往繞過資料分類，卻彙整了所有最敏感的內容。這裡有三個疊加的失誤：預設記錄過多、除錯模式沒有到期、觀測平台的存取控制不如主系統嚴。
  3. 對應的條目：主要是 DSGAI14；因為日誌含 OAuth token，也牽涉 DSGAI02（Agent 身分與憑證暴露）；若日誌被匯出給第三方分析服務，還有 DSGAI03／06 的味道。
  4. 官方 Tier 控制怎麼分層：Tier 1：預設最少日誌（內容層級記錄預設關閉，高風險欄位寫入前遮蔽或代碼化）、強化觀測平台存取控制（大量匯出與跨工作階段搜尋限制給指定核准人）、日誌保留不得長於其所記錄的資料；Tier 2：自動掃描日誌中的個資與機密、除錯記錄需核准並自動到期；Tier 3：對觀測平台做紅隊與桌面演練。
  5. 這個情境的提醒：注意這裡有一個有趣的對照：GenAI Incident Response Guide（見事件應變與 Deepfake 主題）要求偵測要把 prompts 與模型輸出等訊號串進日誌堆疊，並提醒儲存使用者 prompts 會有隱私問題。這兩份文件的建議存在張力：偵測想要更多資料，資料安全想要更少。兩份文件沒有互相引用，官方也沒有說事件應變時怎麼調和。資料安全 2026 自己的做法是 (DSGAI14 Tier 1)：內容層級記錄預設關閉，提示詞、回應、工具輸出只記中繼資料，除非明確提升；憑證、OAuth 權杖、系統提示詞與個資在寫入前先遮蔽或代碼化；Tier 2 再要求除錯記錄需核准並自動到期。這是官方的折衷；「事件發生時由誰核准提升」則是作者整理，非官方（見事件應變與 Deepfake 第 4 章）。

本章重點與自我檢核

  • 每個條目的控制分三層：Tier 1（約一個 sprint 的基礎）、Tier 2（需架構或跨團隊）、Tier 3（假設成熟計畫）；每項標 Buy、Build 或 Buy and Build。
  • Tier 是成熟度，不是風險嚴重度；各條控制數量不一也不代表風險大小。
  • 刪除請求類事件同時是 DSGAI01／07／08；先做標籤傳遞與保留期限，才能做抹除驗證。
  • 日誌類事件是 DSGAI14；官方 Tier 1 第一步是預設最少日誌。偵測所需的資料與資料安全要求的最小化之間存在張力。
  • 我能說明三層成熟度與 Buy／Build 各代表什麼。
  • 我能由症狀推回條目，並說出官方 Tier 1 的第一步。
  • 我知道為什麼「抹除驗證」要排在「標籤傳遞」之後。
