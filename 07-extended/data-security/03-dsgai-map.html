21 個條目一口氣讀完很難記，但官方在 GenAI Data Risks 一節已經替你分好組：它說這些條目「依資料在 GenAI 系統中流動的順序」排列。這一章照官方的六個群組走一遍，每組挑出代表條目，最後處理最容易混淆的幾組。

3.1 官方的六個群組

官方群組條目一句話（作者改寫）
① 直接暴露DSGAI01 Sensitive Data Leakage

DSGAI05 Data Integrity & Validation Failures
(資料完整性與驗證失敗)		匯入邊界的驗證不足：結構合法但語意惡意，或利用匯入機制本身
DSGAI06 Tool, Plugin & Agent Data Exchange Risks
(工具、外掛與 Agent 的資料交換風險)		每次工具呼叫或 Agent 交接都是外洩邊界，常把整段上下文一併送出
③ 治理基礎DSGAI07 Data Governance, Lifecycle & Classification
(資料治理、生命週期與分類)		治理失誤會向前傳播，嵌入到比來源更長壽的衍生物裡
DSGAI08 Non-Compliance & Regulatory Violations
(不合規與違反法規)		刪除請求只刪了原始資料；嵌入、備份、微調模型仍在
④ GenAI 獨有攻擊面DSGAI09 Multimodal Capture & Cross-Channel Leakage
(多模態擷取與跨通道外洩)		截圖、掃描、語音等經 OCR 或轉錄後，文字與影像一樣敏感，卻常漏掉
DSGAI10 Synthetic Data, Anonymization & Transformation Pitfalls
(合成資料、匿名化與轉換的陷阱)		以為去識別化或合成資料就有隱私保證；準識別欄位仍可重識別
DSGAI11 Cross-Context & Multi-User Conversation Bleed
(跨上下文與多使用者對話滲漏)		共用的記憶、快取或索引讓一位使用者的內容出現在另一位的上下文
DSGAI12 Unsafe Natural-Language Data Gateways
(不安全的自然語言資料閘道，LLM 到 SQL／Graph)		讓 LLM 對寬 schema 直接產生並執行查詢；閘道實際上是強大的服務帳號
DSGAI13 Vector Store Platform Data Security
(向量庫平台資料安全)		未加密的嵌入與寬鬆的向量 API；快照匯入等平台缺陷可升級為資料竊取
⑤ 營運基礎設施DSGAI14 Excessive Telemetry & Monitoring Leakage
(過度遙測與監控外洩)		除錯日誌把完整 prompt、工具輸出與憑證集中存放
DSGAI15 Over-Broad Context Windows & Prompt Over-Sharing
(過寬的上下文與提示詞過度分享)		為了「改善答案」把整份用戶檔案塞進每次請求
DSGAI16 Endpoint & Browser Assistant Overreach
(端點與瀏覽器助理越權)		權限過大的瀏覽器擴充或 IDE 助理，被誘騙把本機資料送出
DSGAI17 Data Availability & Resilience Failures
(資料可用性與韌性失敗)		RAG 的失效模式不是 503，而是安靜的錯誤資訊與復活已刪除的資料
⑥ 模型作為資料產物DSGAI18 Inference & Data Reconstruction
(推論與資料重建)		成員推論、模型反推、嵌入反推
DSGAI19 Human-in-the-Loop & Labeler Overexposure
(人在迴路與標註者過度暴露)		標註者拿到原始 prompt、完成內容與內部文件
DSGAI20 Model Exfiltration & IP Replication
(模型外洩與智財複製)		用合法 API 大量探測，蒸餾出替身模型
DSGAI21 Disinformation & Integrity Attacks via Data Poisoning
(經資料投毒的假資訊與完整性攻擊)		把假資訊餵進 AI 信任的來源（語料、向量庫、工具輸出、即時資料）

官方對群組③的說法值得單獨強調：DSGAI07 與 DSGAI08 被視為「所有其他控制的前提條件」，而不是獨立的風險。換句話說，沒有分類、保留與血緣，其他控制（例如刪除、舉證、投毒溯源）都做不起來。

3.2 容易混淆的條目

下列幾組名稱相近，但官方切分的角度不同。判斷的竅門是問：「資料出問題的環節是什麼？」

表 3-2　容易混淆的條目（辨析為作者整理，非官方）
條目出問題的環節與誰容易混淆
DSGAI01 敏感資料外洩輸出端：模型、RAG 或日誌把敏感字串吐出來與 DSGAI15（過度分享）：DSGAI01 看「吐出來」，DSGAI15 看「一開始就送太多」
DSGAI15 過寬的上下文輸入端：每次請求都附上不必要的資料給外部供應商與 DSGAI06：DSGAI06 看「交給工具或其他 Agent」，DSGAI15 看「交給 LLM 供應商」
DSGAI04 資料／模型／產物投毒訓練期與管線：語料與產物被竄改，載入時執行與 DSGAI21：DSGAI21 看「執行期經由受信來源灌入假資訊」
DSGAI13 向量庫平台平台層：向量庫自己的 API、加密與匯入缺陷與 DSGAI11：DSGAI11 看「租戶範圍沒設好」，DSGAI13 偏平台缺陷與加密
DSGAI18 推論與重建只對模型或向量庫提問、推論訓練資料與 DSGAI20：DSGAI20 要的是「複製整個模型的能力」，不是某筆資料
DSGAI07 治理與 DSGAI08 合規前提條件：分類、血緣、保留；合規義務與 DSGAI01：刪除請求後衍生物仍在，三條都會碰到

最後一列是這份文件的一個核心觀察：同一個事故常橫跨好幾個條目。例如「刪除請求後，客戶資料仍從 RAG 被答出來」，同時是 DSGAI01（外洩）、DSGAI07（衍生物沒被治理）與 DSGAI08（違反抹除義務）。這是第 4 章情境 A 的主軸。

3.3 核心概念：衍生物比來源活得久

資料「刪除」是什麼意思

是什麼
官方在 DSGAI01、DSGAI07、DSGAI08 反覆出現同一個現象：使用者要求刪除，組織刪了 CRM 與資料湖裡的原始紀錄，但那筆資料早已被衍生成嵌入、被備份、被用於微調。
為什麼會發生
衍生物在管線中被複製到別處（向量庫、快取、備份、模型權重），而刪除流程只認得來源。官方在 DSGAI07 寫得更尖銳：一個重新索引工作甚至可能把已刪除的資料從舊備份還原回向量庫。把資料編進模型權重後，要「忘記」它是難的（官方稱為 machine unlearning 的挑戰）。
對安全與合規的含意（概念層級）
刪除請求的「完成」不等於實際移除；若無法證明衍生物也被處理，就會同時產生外洩風險與違反資料主體權利的合規風險。官方因此把 DSGAI07、DSGAI08 放在群組③：它們是其他控制的前提。
怎麼防（官方列於 DSGAI07、DSGAI08）
以 DSGAI07 為例，官方 Tier 1：分類標籤的傳遞 (Classification propagation)、管線入口掃描、自動化保留期限；Tier 2：抹除驗證測試、Agent 上下文的 TTL、帶來源／授權／負責人標籤的資料目錄；Tier 3：資料到模型的血緣登記冊、為資料主體請求準備的衍生物清單。DSGAI08 的 Tier 3 另有「unlearning 就緒架構」，DSGAI01 的 Tier 3 另有「可驗證的抹除／unlearning」。
常見誤解
「刪了來源資料就等於刪除。」官方情境明確指出相反：來源刪除後，嵌入仍會在 RAG 中重新出現。另一個誤解是：「把資料編進模型是匿名的。」DSGAI10 與 DSGAI18 都指出模型可能記住並被取回罕見的紀錄。

本章重點與自我檢核

  • 21 個條目依資料流動順序分六組：直接暴露、管線完整性、治理基礎、GenAI 獨有攻擊面、營運基礎設施、模型作為資料產物。
  • DSGAI07、DSGAI08 被視為其他控制的前提條件，不是獨立風險。
  • 名稱相近的條目靠「出問題的環節」區分：輸出端（01）、輸入端（15）、交給工具（06）、平台層（13）、只提問（18）、複製能力（20）。
  • 衍生物（嵌入、備份、微調權重）比來源活得久；刪除不等於移除。
  • 我能說出六個群組各有哪些條目。
  • 我能用「出問題的環節」區分 DSGAI01 與 DSGAI15、DSGAI18 與 DSGAI20。
  • 我能說明為什麼刪除請求完成不等於資料已移除。
