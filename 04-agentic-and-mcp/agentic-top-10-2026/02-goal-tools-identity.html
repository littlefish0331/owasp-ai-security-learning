第 2 章　目標、工具與身分（ASI01–ASI03）

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO2
  • 前置：第 1 章

十項裡，ASI01、ASI02、ASI03 最常在同一個事件裡一起出現，也最容易被搞混：agent 的目標被改了、工具被用歪了、權限被借走了，這三件事看起來都像「agent 做了不該做的事」。文件為每一條都寫了「跟鄰居有什麼不同」，本章就用這條線把它們分開。

2.1 三個條目怎麼區分

文件反覆強調的區分原則是：看「出問題的是哪一個環節」。目標被改變是 ASI01；目標正常、但工具被用成非預期方式是 ASI02；問題在身分與授權的結構本身，是 ASI03。

表 2-1　ASI01–ASI03 的區分（依各條 Description 改寫；對照 T 編號與 LLM 條目為官方，LLM 編號為 2025 版）
條目出問題的環節文件明寫的邊界對應 T&M／LLM（2025 版）
ASI01 Agent Goal Hijack目標、任務選擇、決策路徑被改變與 ASI06（記憶污染）及 ASI10（rogue agent）不同：攻擊者直接改了目標或指令，不論互動式或預先埋入文件；ASI06 是持久污染儲存的脈絡；ASI10 是無人操控下自行偏離T6 Goal Manipulation、T7 Misaligned & Deceptive；LLM01:2025（單次回應被改）與 LLM06:2025
ASI02 Tool Misuse and Exploitationagent 在被授予的權限內，以不安全或非預期的方式用合法工具若涉及提權或憑證繼承，歸 ASI03；若產生任意或被注入的程式碼執行，歸 ASI05；工具定義經由 MCP 而來，與 ASI04 自然重疊T2；T4 與 T16 是放大因素；LLM06:2025
ASI03 Identity and Privilege Abuse委派鏈、角色繼承、快取憑證等動態信任被利用，導致提權與 ASI02 不同：ASI02 是主體濫用自己已被授予的工具；ASI03 是身分與授權的結構性錯配（agent 沒有自己的受治理身分，落在「歸因缺口」）T3（官方稱一對一）；LLM06:2025 的 agentic 演進，常借助 LLM01:2025；影響可超越 LLM02:2025

要小心的筆誤

PDF 的 ASI10 一處把「Goal Hijack (ASI01)」與「Supply Chain tampering (ASI04)」寫成 AS01、AS04。正確的編號是 ASI01、ASI04。另外，ASI02 的攻擊情境第 4 點標題在 PDF 文字層呈現亂碼（內容是把安全的內部 CRM 工具與外部郵件工具串接以外洩客戶名單），本教材只引用其內容。

2.2 三條各自的核心概念

ASI01：目標被劫持——因為 agent 分不清「指令」與「內容」

是什麼
攻擊者透過提示詞、被竄改的工具輸出、惡意的產出物、偽造的 agent 間訊息或被污染的外部資料，改變 agent 的目標、任務選擇或決策路徑。文件特別區分：LLM01:2025 關心「改變單次模型回應」，ASI01 關心「被改的輸入重導了目標、規劃與多步行為」。
為什麼會發生
agent 依賴「無型別的自然語言輸入」和鬆散治理的編排邏輯，無法可靠分辨合法指令與攻擊者可控的內容。這和 前置觀念 提到的提示詞注入同源，只是後果從錯誤的答案變成錯誤的行動。
怎麼被利用（概念層級）
常見路徑：埋在網頁或 RAG 文件裡的隱藏指示；從公司外寄來的郵件或行事曆邀請，劫持 agent 的內部通訊能力，以受信任的身分發訊息；甚至排程的提示詞每天微調目標權重，讓規劃偏向低摩擦的核准而仍符合政策。
怎麼防
文件列了九項，重點是：所有自然語言輸入一律視為不可信，經過與 LLM01 同等的篩選；對工具套用最小權限，高衝擊或「改變目標」的動作需要人核准；鎖定系統提示詞並納入組態管理；執行前驗證使用者意圖與 agent 意圖；對連接的資料來源做清理；持續記錄並建立目標狀態的基準線，偏離時告警；定期紅隊演練目標覆寫。文件另提到「意圖膠囊 (intent capsule)」這個新興模式，把宣告的目標、限制與脈絡綁在簽章的封包裡。
常見誤解
「ASI01 就是提示詞注入。」ASI01 把提示詞注入視為手段之一；它的核心是「目標被改」這個結果，手法還包括被竄改的工具輸出與偽造的 agent 訊息。

ASI02：工具被濫用——權限都合規，用法卻不安全

是什麼
agent 在被授予的權限內，把合法工具用在不安全或非預期的方式，例如刪掉重要資料、過度呼叫昂貴的 API、外洩資訊。
為什麼會發生
agent 怎麼選工具、怎麼用，受記憶、動態工具選擇與委派影響；工具可能權限過大（郵件摘要工具竟能刪信、寄信）、範圍過寬（只需要一種記錄卻能取全部）、把不可信的模型輸出直接送給 shell，或在迴圈中反覆呼叫昂貴 API。
怎麼被利用（概念層級）
文件的情境：竄改工具介面（描述、結構、中繼資料）讓 agent 依假的能力呼叫；把安全的內部工具與外部寄信工具串接，外洩客戶名單；名稱相近的工具搶先被解析，也就是抄寫相近名稱的攻擊 (typosquatting)；被「核准自動執行」的低風險工具（如 ping）被反覆觸發而經由 DNS 外洩資料；以及每個指令都由受信任的程式在有效憑證下執行，使端點偵測看不到惡意程式。
怎麼防
八項，重點：以「每個工具一份最小權限設定檔」限制範圍、速率與外送允許清單，並寫成 IAM 或授權政策而不是慣例；每次呼叫都驗證，高衝擊或破壞性動作要人確認並顯示預演差異；在隔離沙箱中執行並控制對外連線；執行前用政策執行點檢查意圖與參數，把模型與規劃器輸出視為不可信；設定用量上限；用即時、短效的存取；使用完整限定的工具名稱與版本固定；保存不可竄改的工具呼叫日誌並偵測工具串接的異常。
常見誤解
「工具都有權限檢查，所以沒事。」ASI02 的前提正是 agent 在授權範圍內用歪了工具；單一工具的檢查看不到「讀資料庫後接著外送」這種序列。

ASI03：身分與權限被濫用——結構上的錯配

是什麼
利用 agent 世界裡動態的信任與委派，沿著委派鏈、角色繼承、控制流與 agent 脈絡（含快取憑證與對話歷史）升權。這裡的「身分」同時指 agent 被定義的角色，以及代表它的任何驗證資料（API 金鑰、OAuth 權杖、被委派的使用者 session）。
為什麼會發生
文件指出根因是「以使用者為中心的身分系統」與「agent 的設計」之間的結構錯配：agent 若沒有自己被治理的身分，就落在歸因缺口，無法落實真正的最小權限。
怎麼被利用（概念層級）
文件列了七種：未縮權的權限繼承（高權限管理者把全部存取脈絡丟給窄任務的 worker）、記憶中殘留權限、跨 agent 信任（混淆代理人）、檢查時與使用時不一致 (TOCTOU)（流程開始時驗過，過程中權限已被調降卻仍繼續）、合成身分注入（偽稱「Admin Helper」）、身分共享等。
怎麼防
重點：任務範圍、有時效的權限（短效、窄範圍權杖，每個 agent 有自己的身分）；隔離身分與脈絡，在任務間清除狀態；每個特權動作由集中式政策引擎重新驗證；高權限或不可逆動作需人核准；把 OAuth 權杖綁到簽章的意圖；評估正式的 agentic 身分管理平台；偵測委派中間接取得的權限；偵測跨 agent 的異常升權。
常見誤解
「換成短效權杖就解決了。」短效權杖是重點措施之一，但文件的根因在「agent 沒有自己的受治理身分」；沒有身分與歸因，權杖再短也無法落實最小權限。

2.3 一件事故，怎麼判斷歸哪一條

本章重點與自我檢核

  • ASI01 看「目標是否被改」，ASI02 看「權限內是否被用歪」，ASI03 看「身分與授權的結構錯配」。
  • 三者共通的防線：最小權限、短效且窄範圍的存取、高衝擊動作需人核准、完整日誌與偏離偵測。
  • 提示詞注入是 ASI01 的手段之一，不是 ASI01 本身；單一工具的權限檢查擋不住工具串接。
  • 事故常同時符合多條；歸屬問的是「最主要出問題的環節」。
  • 文件中的 LLM 編號是 2025 版；PDF 內有 AS01 這類筆誤。
  • 給我一段事件描述，我能指出它最主要歸 ASI01、ASI02 還是 ASI03，並說明理由。
  • 我能解釋為什麼「權限都合規」也可能是 ASI02。
  • 我能說出 ASI03 的根因與短效權杖的限制。
