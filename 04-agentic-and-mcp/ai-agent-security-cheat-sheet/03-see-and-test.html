第 3 章　看見、驗證與測試

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章

限制再周全，也會有沒想到的缺口、悄悄失效的控制。看見群的三節就是補這一塊：輸出驗證在動作離開前攔一道、監控讓發生過的事留下紀錄、測試在上線前與每次重大變更後確認限制還有效。本章前兩節用一張表講完，重點放在第 9 節的濫用案例矩陣與發佈閘門。

3.1 三節的要點與示範差別

節官方要點（改寫）示範的差別，或本教材的提醒
5 輸出驗證與護欄
(Guardrails)		輸出在執行或顯示前先驗證；過濾敏感資料外洩；盡量用結構化輸出加結構描述驗證；為輸出動作設邊界（速率、範圍）；套用內容安全過濾示範把一次工具呼叫當成有結構的物件：工具名必須在允許清單內；參數裡出現像金鑰、密碼、權杖這類字樣就拒絕。外層的護欄再檢查速率上限、過濾回應裡的個資，並偵測外洩樣式（例如網址夾帶編碼資料、對外 webhook 送出超大內容）。提醒（作者整理，非官方）：樣式比對只抓得到寫得出樣式的那一類，抓不到語意被操縱的輸出；提示詞注入防護主題也說輸出驗證抓得到格式錯誤，抓不到語意操縱
6 監控與可觀測性
(Observability)		記錄所有決策、工具呼叫與結果；對異常行為做偵測；按 session 與使用者追蹤 token 與成本；安全相關事件要告警；留稽核軌跡供合規與鑑識。高風險動作另記結構化的決策中繼資料：動作分類、風險分數（適用時）、授權結果、批准識別碼、執行結果、政策版本。並監控批准行為的漂移、重複的繞過批准嘗試、特權使用升高、異常的工具呼叫頻率，以及高風險動作的突增示範的事件有類型、嚴重度、agent、session、使用者、時間與細節；記錄前先遮蔽密碼、金鑰、權杖這類欄位；有幾個異常門檻（每分鐘工具呼叫次數、失敗次數、成本）。2026-10-04 的提交修正了時間窗：計算經過時間要用總秒數，不是只取秒數屬性（後者會漏算整天）。這是一個典型的「示範碼的小錯會讓偵測悄悄失準」。若紀錄來自你沒做的元件，文件指向 Verifying（本主題第 4 章）
9 對抗式測試
(Adversarial Validation)		上線前，以及提示、工具、記憶、檢索、政策或模型供應者有實質變更後，做結構化安全測試；同時測應用層的控制與 agent 特有的失敗模式無程式碼示範；見 3.2 的矩陣、3.3 的發佈閘門

「看見」的重點是要看見什麼。只記錄「呼叫了哪個工具」不夠回答事後的問題；官方要求高風險動作連同授權結果、批准識別碼與政策版本一起記，因為事後要查的往往是「是誰、依哪一版規則、用哪一份批准放行的」。

3.3 核心概念：變更觸發重測，測試本身也是攻擊目標

發佈閘門與驗證證據

是什麼
第 9 節的「CI/CD 與發佈閘門」加「驗證證據」。前者：在 CI/CD 對 agent 範本、工具政策與提示的變更跑對抗式測試套件；加入歷史上出現過的注入、記憶污染與工具濫用的回歸測試；當高風險工具政策、批准邏輯或憑證範圍變了、測試卻沒更新時，擋下發佈。後者：正式環境的 agent 要留下可說明「測了什麼」的證據。
為什麼
agent 的行為由提示、工具、記憶、檢索、政策與模型供應者共同決定，任何一個改動都可能讓先前有效的限制失效，所以不是測一次就好。官方還特別提醒：攻擊者可能在改動 agent 行為的同一個合併請求 (pull request) 裡，弱化或刪掉安全測試，因此對測試本身的變更也要仔細審查。
沒做會怎樣（概念層級）
舊問題在換模型供應者或改提示後悄悄回來；測試夾具 (fixture) 裡放了真實的機密或客戶資料；上線時沒人說得出當初測的是哪一版的 agent、哪一份工具政策。
怎麼做
官方列出的做法：紅隊提示與預期的拒絕都放進版本控制，但不放機密與真實客戶資料；驗證證據至少要有四項：受測的 agent 版本、模型供應者、工具政策與檢索設定；執行了哪些濫用案例及其預期結果；觀察到的批准、拒絕、逾時或熔斷器 (Circuit Breaker) 行為；接受的殘餘風險與補償控制。
常見誤解
「測試全過就是安全。」測試只證明在它的條件下看到的行為；本站提示詞注入主題的冒煙測試一節也強調這一點。另一個誤解是：「測過一次，後面改提示不必重測。」官方把提示、工具、記憶、檢索、政策與模型供應者都列為重測的觸發條件。

3.4 兩群怎麼互相檢驗：一個對照

把第 2 章與本章放在一起，可以得到一個實用的檢查（作者整理，非官方）：對任何一項限制，問自己「有沒有對應的測試」與「失效時看不看得見」。

  • 有限制、有測試、有紀錄：你能說出它為什麼有效，失效時也有機會發現。
  • 有限制、沒測試：它可能從一開始就沒生效，或在下次變更後失效而沒人知道。
  • 有限制、有測試、沒紀錄：上線後的漂移（例如批准行為悄悄改變）只能等事故。
  • 只有紀錄、沒有限制：你只是用比較好的方式記錄壞事發生。

Do's and Don'ts 也有呼應：Do 要做結構化對抗式測試、強制 token、成本、重試與工具鏈上限、為高風險動作記錄結構化決策中繼資料；Don't 要略過提示、工具、記憶、檢索或供應者變更後的對抗式測試。

本章重點與自我檢核

  • 看見群的三節：輸出驗證（動作離開前）、監控（發生過的事留紀錄）、對抗式測試（限制是否有效）。
  • 輸出驗證與樣式比對只抓得到寫得出樣式的情況，抓不到語意被操縱的輸出。
  • 高風險動作要記結構化決策中繼資料（分類、授權結果、批准識別碼、政策版本等），並監控批准行為的漂移。
  • 濫用案例矩陣的八列，每列都是某個限制的反面測試；變更提示、工具、記憶、檢索、政策或模型供應者後要重測。
  • 測試本身也可能被弱化或刪除，要審查；驗證證據要說得出「測了哪一版、哪些案例、看到什麼、殘餘風險是什麼」。
  • 我能說出濫用案例矩陣的八列，並指出每列在驗證哪個限制。
  • 我能列出第 9 節要求的驗證證據包含哪四項。
  • 我能說明為什麼測試本身的變更也要審查。
