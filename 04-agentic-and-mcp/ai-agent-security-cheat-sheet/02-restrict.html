第 2 章　限制 agent 能做什麼

限制群的六節看起來像六份清單，其實反覆出現同一個原則：不要靠 agent 或模型自己守規矩，把決定權放在它碰不到的執行元件。本章先用一張表掃過六節的「危險 vs 安全」，再把最關鍵的一組控制——授權放在執行元件、批准綁定確切動作——當作核心概念講透。

2.2 核心概念：授權在執行元件，批准綁定確切動作

agent 只能提議，執行元件才能放行

是什麼
Cheat Sheet 的「Tool Authorization Middleware」與「High-Impact Action Integrity Controls」合起來說一件事：agent 只負責提議動作；放行的是它之外的執行元件（或政策服務），由後者獨立檢查範圍、權限與批准狀態。批准是一份綁定「確切動作」的紀錄，不是一個布林旗標。
為什麼是這樣
模型輸出不可信，Do's and Don'ts 也明寫「不要只靠模型輸出做授權決定」。授權若在 agent 的上下文裡，被注入的 agent 也能自己宣稱「已確認」。官方曾用「使用者已確認」旗標（原文的 user_confirmed）當示範，2026-10-04 被換掉，並明寫旗標不夠。
批准沒綁定會怎樣（概念層級）
同一份批准可套用到不同對象或金額；可被重複使用或並發重複送出；過期仍有效；沒列在表裡的未知工具被預設放行；批准服務或稽核日誌掛了，系統照常執行。
怎麼防
官方列出的做法：(1) 決策與執行分離；(2) 批准紀錄含行動者、工具名、目標資源、正規化後的參數、時間與到期；(3) 短效授權憑證加重放保護 (Replay Protection)；(4) 帳號復原、發起付款、權限變更、批量刪除、正式環境部署這類關鍵動作要升級驗證 (Step-up Authentication)；(5) 高衝擊動作盡量冪等 (Idempotent)，做不到就要明確的重複確認；(6) 風險分級、批准驗證、政策查詢或稽核紀錄任何一個失敗，都失效即拒絕 (Fail-Closed)；(7) 檢查與消耗批准在同一個原子步驟、緊接執行之前，目標或參數一變就要新的批准。官方也點名要搭配 Transaction Authorization Cheat Sheet（本站沒有對應主題）。
常見誤解
「有人按過確認，就算有批准。」批准還要屬於當前行動者與這一次呼叫、未過期、未被用過。另一個誤解是把風險分級表當授權：文件明寫分級「不授予執行工具的權限」。

2.3 風險分級：哪些動作需要人批准

第 4 節要求高衝擊或不可逆動作先經人明確批准，並提供動作預覽、依風險設自主邊界、保留決策與動作的稽核軌跡、讓使用者能中斷與回復。它的分級示範如下（工具名取自原文示範）：

「未知工具預設為高」就是失效即拒絕的實例。分級的好處（作者整理，非官方）是只讓人審真正高風險的動作，避免審查者被淹沒；威脅與緩解文件把這個問題稱為 T10，見壓垮人在迴路。

2.4 多 agent 訊息：簽章不等於權限

第 7 節現行的規則比示範碼更值得記，有兩個細節與 2.2 的原則同源：

  • 有效簽章不授予權限。接收端要認證通訊雙方，並依「寄件者的權限」決定能不能做；簽章要涵蓋寄件者、收件者、訊息類型、內容、建立與到期時間，以及唯一的訊息識別碼。使用簽章時應採用維護中的協定實作；官方連到 RFC 9421 說明為什麼驗證必須要求所有與安全相關的元件都被簽署。
  • 防重放要有共用狀態。時間戳只能限制有效期，窗口內仍可重複執行。接收端要原子地檢查並記下識別碼，記錄要保留整個接受窗口（含時鐘誤差），並讓所有可能接收該訊息的實例共用；狀態不可用時拒絕訊息。官方引用 RFC 9449 的 DPoP 重放指引，說明各伺服器沒有共用狀態時，單次使用的檢查可能做不到。傳輸加密仍要保留，因為簽章不提供機密性。

本章重點與自我檢核

  • 限制群的共同原則：決定權放在 agent 碰不到的執行元件；agent 只提議。
  • 危險 vs 安全的示範差別，多半是「萬用字元與全開」對「限定範圍與預設拒絕」。
  • 批准要綁定行動者、工具、目標、正規化參數與到期，並在緊接執行前原子地檢查與消耗；風險分級不等於授權。
  • 未知工具預設為高風險；風險分級、批准驗證、政策查詢或稽核紀錄失敗時，一律失效即拒絕。
  • 多 agent 訊息的有效簽章不授予權限；防重放要有共用的原子狀態。
  • 我能把一個「危險 vs 安全」的工具、記憶或資料示範，說成限制了什麼。
  • 我能列出批准紀錄至少要綁哪些欄位，並說明為什麼旗標不夠。
  • 我能說明簽章與權限、時間戳與重放保護的差別。
