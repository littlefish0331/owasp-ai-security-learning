第 3 章　伺服器開發者視角

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章

你開發一個 MCP 伺服器，等於把一個用使用者委派權限、能串接多個工具的服務放到 AI 助理旁邊。官方的說法是：它和傳統 API 的差別在於，「任何單一漏洞的衝擊會被放大」。這份 17 頁的指南把控制分成八類，並收尾於一張五大類的「最低標準 (Minimum Bar)」檢查表。本章用兩張表把它們攤開，再用一個虛構情境走一遍。

3.1 官方先列的六種弱點

指南先列出 MCP 伺服器常見的六種風險，後面的八類控制幾乎一一對應：

  • Tool Poisoning：經由提示詞或工具中繼資料中的精心設計輸入操縱 AI。
  • Dynamic Tool Instability（Rug Pulls）：工具描述缺乏嚴格版本控制、又是動態載入，已被信任的定義可能被即時替換。
  • Code Injection & Unsafe Execution：伺服器把模型給的輸入直接送進系統指令、API 或資料庫查詢。
  • Credential Leakage & Token Misuse：金鑰與 OAuth 權杖存放、記錄或快取不當。
  • Excessive Permissions：工具或範圍過寬，一個被攻破的工具就能危及多個系統。
  • Insufficient Isolation（Session、Identity & Compute）：多個並行 session 共用狀態、共用單一身分（如同一個服務帳號服務多位使用者）、或在共享主機執行程式碼，造成跨租戶洩漏、身分偽冒與資源競爭。

3.2 八類控制

1 安全架構本機 vs 遠端：本機優先用 STDIO 或 Unix socket；必須用本機 HTTP 時只綁 127.0.0.1、仍要明確授權並驗證 Origin；在隔離的子程序或容器中執行。遠端：TLS 1.2+，嚴格依 MCP 結構驗證所有 JSON-RPC 訊息。信任連線：已知靜態關係用允許清單、寫死連線或 mTLS；動態環境用 OAuth 2.1 或 OIDC。隔離使用者與 session：禁止用全域變數或單例存使用者資料；每 session 獨立物件或 session 鍵控狀態；結束時確定性清理；每 session 資源配額隔離不足、資源競爭

3 資料驗證與資源管理每 session 的呼叫與資料擷取配額、逾時；所有資料視為不可信，為每個工具的輸入與輸出定義 JSON Schema，不符即拒絕；過濾淨化並設輸出大小上限Code Injection、DoS
4 提示詞注入控制優先結構化 JSON 工具呼叫而非讓模型產生自由文字指令；高風險動作的 HITL（用 MCP 的 elicitation 暫停並要求明確確認）；「LLM 當裁判」：在另一個脈絡的 LLM session 用政策提示審核高風險呼叫；「一任務一 session」：換任務就重設 session，避免隱藏指示在長對話中持續Tool Poisoning、注入
5 驗證與授權遠端伺服器一律驗證，用 OAuth 2.1 或 OIDC，每次請求驗證簽發者、受眾、有效期與簽章；禁止權杖直通 (Token Passthrough)：不可把用戶端權杖轉給下游 API，改用發給該伺服器的權杖或 On-Behalf-Of 流程，直通會破壞稽核並造成混淆代理人風險；短效且窄範圍的權杖；session 是狀態，不是身分：不可只靠 session ID 做授權；集中式政策執行層Credential Leakage、Excessive Permissions
6 安全部署與更新機密放在保管庫，永遠不讓 LLM 接觸機密；最小化強化的容器，非 root；網路分段、預設封鎖進出；版本固定、建置時掃描、簽章映像、維護 AIBOM；CI/CD 安全關卡；安全的錯誤處理（不回傳堆疊、權杖、路徑）Credential Leakage、供應鏈
7 治理密碼學完整性（簽章與版本固定）；任何新工具或重大修改須經安全審查；稽核日誌（含工具呼叫參數、授權事件、組態變更的新舊值；欄位允許清單、遮罩與雜湊，且不可竄改）；非人類身分治理：當作一級身分稽核、NHI
8 工具與持續驗證SAST（含自訂 MCP 規則）與 SCA 進 CI/CD，超出風險容忍度就中斷建置；執行期保護（seccomp、AppArmor 等）；餵給 SIEM 的持續監控；用供應鏈健檢框架評估專案供應鏈、偵測

留意第 5 類的兩個設計：禁止權杖直通與session 不等於身分。它們分別堵住了 MCP 伺服器最常見的兩條「借用使用者權限」的路，也正是第 1 章混淆代理人的實作版。

3.3 最低標準 (Minimum Bar) 檢查表

指南最後收成五大類，是作者認為這份文件最實用的一頁：

  1. 強身分、驗證與政策執行：遠端伺服器全用 OAuth 2.1／OIDC；權杖短效、窄範圍、每次呼叫驗證；無權杖直通、政策集中執行。
  2. 嚴格隔離與生命週期控制：使用者、session、執行脈絡完全隔離；使用者資料無共享狀態；session 有確定性清理與資源配額。
  3. 可信、受控的工具：工具簽章、版本固定、正式核准；描述與執行期行為比對；只給模型最少必要的欄位。
  4. 處處以結構驗證：所有 MCP 訊息與工具輸入輸出都過結構驗證；輸入輸出淨化、限制大小、視為不可信；要求結構化 JSON 呼叫。
  5. 強化的部署與持續監督：容器化、非 root、網路限制；機密在保管庫、不給 LLM；CI/CD 關卡、稽核日誌與持續監控是強制的。

3.4 情境範例 A：多租戶的內部知識 MCP 伺服器

情境 A（虛構）：群峰顧問的知識庫伺服器

虛構 群峰顧問是虛構的公司。平台團隊做了一個內部 MCP 伺服器，讓各專案的 AI 助理查詢知識庫與專案文件，並提供「寄出摘要」功能。為了方便，它用一個服務帳號存取後端 API；同時為了效能，把最近查詢的專案內容快取在伺服器的全域變數裡；使用者驗證則是用連線時拿到的 session ID。以下為虛構，細節停在概念層級。

架構：各專案的 AI 助理（用戶端）→ MCP 伺服器（單一服務帳號、全域快取、session ID）→ 後端 API 與郵件服務。

  1. 發生了什麼：A 專案的助理查詢後，伺服器把結果放進全域快取。幾分鐘後，B 專案的另一位使用者問了一個語意接近的問題，伺服器從快取回傳了 A 專案的內容。另外，稽核時發現所有後端存取都記在同一個服務帳號下，無法分辨是誰做的。
  2. 哪一環出問題：(a) 用全域變數存使用者資料，違反「禁止全域變數與共享單例」與「每 session 獨立」；(b) 單一服務帳號服務多位使用者，造成身分偽冒、無法歸因；(c) 只靠 session ID 授權，違反「session 是狀態，不是身分」；(d) 缺少每 session 配額與確定性清理。
  3. 對應條目：指南第 1 類（隔離）與第 5 類（驗證授權）；MCP Top 10：MCP10 Context Injection & Over-Sharing、MCP07 Insufficient Authentication & Authorization、MCP02（範圍）；T&M：T3 Privilege Compromise；Agentic Top 10：ASI03、ASI06。LLM Top 10 2026：LLM02:2026 Sensitive Information Disclosure。
  4. 該採什麼控制：
    • 隔離：每 session 建獨立物件或用 session 鍵控的狀態庫；結束時清空檔案、快取與權杖；加每 session 配額；
    • 身分：用 OAuth 2.1／OIDC，以 Token Delegation 保留使用者脈絡，同時伺服器仍保有獨立的非人類身分；禁止權杖直通；
    • 授權：不能只靠 session ID，要綁定已驗證的使用者與用戶端身分並重新檢查；
    • 日誌：記錄工具呼叫、參數、授權事件，遮罩敏感內容，並且不可竄改。
  5. 學到什麼：「為了效能與方便」的三個決定（共享快取、共用帳號、只靠 session ID）各自都合理，合在一起就是跨租戶洩漏。官方在弱點清單中專門點名了這三種組合。審查伺服器設計時，最有效的問題是：「這個東西如果被兩個使用者同時用，會發生什麼事？」

本章重點與自我檢核

  • 指南的八類控制：安全架構、安全工具設計、資料驗證與資源管理、提示詞注入控制、驗證與授權、安全部署與更新、治理、工具與持續驗證；最後收成五大類的 Minimum Bar。
  • 禁止權杖直通與session 是狀態、不是身分是防止「借用使用者權限」的兩個關鍵設計。
  • 本機優先 STDIO；遠端用 Streamable HTTP 與 TLS，並嚴格依結構驗證訊息。
  • 永遠不讓 LLM 接觸機密；工具描述要與實際行為相符並簽章固定。
  • 跨租戶洩漏往往來自三個各自合理的方便性決定（共享快取、共用帳號、只靠 session ID）的組合。

  • 我能解釋為什麼權杖直通會造成混淆代理人風險，以及怎麼避免。
  • 我知道多租戶隔離的三個常見破口。
