第 4 章　第三方使用者視角

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO4
  • 前置：第 3 章

多數組織不會自己寫 MCP 伺服器，而是安裝別人做好的。這時你的問題從「怎麼寫得安全」變成「怎麼決定能不能信、怎麼持續管著它」。官方的第三方使用指南用一個「受信任的登錄」為核心，搭配客戶端防護、探索驗證、授權與一條五步驟的治理流程。本章把它和 MCP Security Cheat Sheet 的 12 項實務拼起來。

4.2 客戶端：信任最小化

官方對客戶端的定位很直接：客戶端是抵禦惡意伺服器的第一道防線。它的原則是不假設伺服器可信，包含：驗證 manifest、強制結構描述、使用允許清單；在受限環境（如限制檔案系統與網路的容器）執行客戶端與第三方伺服器；對工具授予即時、窄範圍、自動到期且可立即撤銷的權限；UI 透明（顯示完整的工具描述、權限與資料存取）；防止伺服器外洩客戶端的機密、歷史或快取記憶；偵測異常的工具呼叫（如大量讀檔、過多 API 呼叫）。

探索與連線的做法則是「先驗證來源，再連」：只連受信任登錄上的伺服器；用 IP 允許清單與網路隔離避免連到未知伺服器；開源或本機伺服器要驗證來源、檢查簽章並掃描已知弱點；維持一個核准伺服器的中央登錄。傳輸選擇上，本機伺服器用 STDIO 當子程序（延遲最低、也較容易以沙箱、seccomp 或 AppArmor 強化）；遠端、多租戶或自動擴展的伺服器用 Streamable HTTP，搭配 TLS／mTLS 或 OAuth 2.1、WAF 與速率限制，並定期輪替憑證。

4.3 治理：受信任的登錄與五步驟流程

受信任登錄 (Trusted MCP Registry) 與治理工作流

是什麼
官方的核心主張：建立一個正式的治理策略，確保只有經審查且受監控的 MCP 伺服器被使用；策略的核心是一個受信任登錄。登錄存放每個已核准伺服器的中繼資料並在執行期強制政策，讓主機與 agent 只看得到「經審查、最小權限、持續監控」的伺服器，並有政策即程式碼的關卡與稽核證據。
為什麼需要
沒有登錄，任何開發者都可以自己裝一個 MCP 伺服器，這正是 MCP Top 10 的 MCP09 Shadow MCP Servers。登錄把「能不能用」變成可稽核的決定，並提供漂移偵測的基準。
怎麼被忽略（概念層級）
只在導入時審查一次，之後版本升級、工具描述變更都不再檢查；或審查與批准都由同一個人完成，沒有領域負責人確認「真的需要」。
怎麼做
官方的五步驟：(1) 提交：附文件與工具描述的雜湊；(2) 掃描：自動掃描惡意程式、隱藏指示與其他風險；(3) 審查與簽核：安全與領域專家審查掃描結果，核准的伺服器固定版本並加入登錄；(4) 部署與監控：先在預備環境，經試用期後才升到正式；(5) 定期重新驗證：定期或版本變更時自動重新掃描。角色：提交者（開發者）、安全審查員、領域負責人、核准者（安全與領域負責人必須都簽核才能啟用）、營運者 (SRE)（負責連線上線、監控與緊急關閉開關）。
常見誤解
「審查過就永遠可信。」官方在驗證段落明確要求固定版本、預備環境試用、自動回復，並監控與已核准清單的漂移；這代表信任是有期限、可撤銷的。

4.4 與 MCP Security Cheat Sheet 的 12 項怎麼對

MCP Security Cheat Sheet（最近修改 2026-10-16）有 12 項實務。與第三方指南相比，它多了幾個細節，值得挑出來：

  • 授權不是協定的必選項：Cheat Sheet 指出「授權在協定中是選配」；使用 OAuth 時要依 MCP 的 OAuth 2.1 設定檔，用 resource 參數標明目標伺服器，驗證權杖的受眾，且不要把 MCP 的存取權杖傳給上游 API（與伺服器指南的「禁止直通」一致）。
  • 工具「可用」不等於「已被同意」：Cheat Sheet 在 2026-10-14 的修訂（closes #2761）新增：不要假設一個可用的 MCP 工具就代表使用者同意了某次具體呼叫；工具註記（如唯讀提示）除非來自可信伺服器，否則視為不可信；依風險決定要用使用者確認、窄範圍授權或執行時的政策檢查。
  • 多伺服器隔離 (第 8 項)：把每個伺服器視為不可信的獨立安全域，防止一個伺服器的描述引用或修改另一個的工具行為；監控跨伺服器的資料流（如伺服器 A 的憑證出現在對伺服器 B 的呼叫裡）；用 MCP 代理或閘道執行隔離。
  • 安裝與同意 (第 11 項)：連接新伺服器前顯示明確的同意對話；顯示將執行的完整指令（本機伺服器）；標明來源與發佈者；工具定義改變時重新請求同意；絕不讓網頁內容或不可信資料觸發 MCP 伺服器安裝。
  • 工具回傳值也是注入面 (第 12 項)：每個工具回應都是不可信資料，包含已核准伺服器的回應；標籤化並分離；過濾只能當附加手段；授權與後續工具呼叫要由可信的應用程式碼獨立驗證。

這份 Cheat Sheet 還有一個值得注意的特性：它在 2026-10 內短短兩週修訂了至少三次，說明這個領域變動快。用它當最新實務的來源，但不要把細節抄成永久規則。

4.5 情境範例 B：內部 MCP 登錄的第一次審核

情境 B（虛構）：望海零售的 MCP 導入

虛構 望海零售是虛構的公司。行銷團隊想導入一個第三方 MCP 伺服器，讓助理能讀取行銷素材庫並發佈社群貼文。團隊在公開平台上找到一個下載量不少的套件，並直接用自己的桌面 AI 應用安裝：工具描述顯示「查詢素材、發佈貼文」，安裝過程沒有任何額外確認。以下為虛構，細節停在概念層級。

架構：桌面 AI 應用（行銷人員的帳號）→ 第三方 MCP 伺服器（本機子程序，STDIO）→ 素材庫與社群平台 API。

  1. 發生了什麼：該套件在一次小版本更新後，在工具定義中新增了一個「同步設定」功能，並在描述中夾帶針對模型的額外指示，要求把近期對話內容一併傳送到外部端點。桌面應用沒有重新請求同意，也沒有顯示完整的定義變動。
  2. 哪一環出問題：(a) 沒有登錄與審查流程，直接安裝（MCP09 Shadow MCP Servers，影子部署）；(b) 沒有固定版本與雜湊，小版本更新後工具定義改變了也不知道，這是 MCP03 的抽換 (Rug Pull)；(c) 本機伺服器以使用者的完整權限執行，沒有沙箱；(d) UI 沒有顯示完整描述，也沒有在定義變動時重新請求同意。
  3. 對應條目：第三方指南的 Tool Poisoning 與 Rug Pull、Governance Workflow；Cheat Sheet 第 9（供應鏈）、第 11（同意與安裝）項；MCP Top 10：MCP03、MCP04、MCP09；Agentic Top 10：ASI04（供應鏈與動態載入）；T&M：T17。LLM Top 10 2026：LLM04:2026 Supply Chain。
  4. 該採什麼控制：
    • 治理：所有第三方伺服器走登錄與五步驟：提交（附工具描述雜湊）→ 掃描 → 安全加領域負責人雙簽核 → 預備環境試用 → 定期重新驗證；
    • 版本與完整性：核准時固定版本並雜湊完整的工具定義，定義一變就阻擋並重新審查；
    • 執行環境：本機伺服器在容器或沙箱中執行，限制檔案系統與網路，對工具授予即時、窄範圍權限；
    • UI 與同意：顯示完整描述與將執行的指令，定義變動時重新請求同意，並由 SRE 備好緊急關閉開關；
    • 偵測：監控異常工具呼叫（如大量資料外送）並告警。
  5. 學到什麼：這個情境的核心不是「這個套件是不是惡意的」，而是即使它起初是善意的，沒有登錄、沒有固定版本、沒有重新同意，也無法發現它後來變了。官方的五步驟與雜湊固定，就是把這個「後來變了」變成可偵測、可擋下的事件。

本章重點與自我檢核

  • 使用者視角有四類攻擊模式：Tool Poisoning／Rug Pull、Prompt Injection、Memory Poisoning、Tool Interference。
  • 客戶端原則是信任最小化：驗證 manifest、容器化、即時窄權限、完整透明的 UI、異常偵測。
  • 治理的核心是受信任登錄與五步驟流程（提交、掃描、審查簽核、預備環境試用、定期重新驗證）；安全與領域負責人要都簽核。
  • Cheat Sheet 補充：授權選配、工具可用不等於被同意、多伺服器隔離、安裝同意、工具回傳值也是不可信資料。
  • 信任有期限且可撤銷；Cheat Sheet 近期頻繁修訂，細節別抄成永久規則。
  • 我能說出五步驟流程與五個角色，並解釋為什麼要雙簽核。
  • 我能對一個想安裝的第三方 MCP 伺服器，列出至少五個該先檢查的事項。
  • 我知道「工具可用」不等於「使用者同意這次呼叫」。
