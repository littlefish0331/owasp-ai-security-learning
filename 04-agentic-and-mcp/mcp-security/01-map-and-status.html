MCP (Model Context Protocol) 把 agent 接到工具與資料，所以 OWASP 圍繞它出了好幾份文件。它們的性質差很多：有 PDF 指南、有 Cheat Sheet、有仍在 Beta 的 Top 10，還有只有 README 的儲存庫。這一章先畫地圖，說清楚「誰給誰讀」與「哪一份比較成熟」，再把 MCP 的三個角色講清楚，並處理 MCP Top 10 的版本演進（包括 MCP06 被改名）。

1.2 MCP 的三個角色與兩種傳輸

三份文件都用同樣的術語，先固定下來：

  • MCP Host：承載 AI 的應用程式（如 AI agent 執行環境、桌面應用、IDE 外掛），管理用戶端並路由請求。
  • MCP Client：與一個 MCP 伺服器溝通的連接器；把工具定義交給 LLM。
  • MCP Server：對外提供三種原語：Tools（可被呼叫的函式）、Resources（提供脈絡的資料來源）、Prompts（可重用的提示範本）。
  • 傳輸：本機用 STDIO（或 Unix socket）；遠端用 Streamable HTTP。Cheat Sheet 指出舊的 HTTP+SSE 傳輸已被淘汰。

一個對安全很關鍵的事實，出現在 Cheat Sheet 的架構概觀：LLM 會在脈絡裡看到所有已連線伺服器的所有工具描述。這解釋了為什麼一個壞伺服器能影響別的伺服器的工具（後面第 3 章的 Tool Shadowing）。

1.3 成熟度：為什麼同一個「OWASP MCP」文件不能一視同仁

文件成熟度與引用方式

是什麼
四份文件的「成熟度」不同：兩份是有版本號與發布日期的 PDF 指南，版本都是 1.0；一份是 Cheat Sheet Series 內持續被修訂、沒有版本號的網頁；一份是自我定位為 Beta、條目皆標 2025 的 Top 10。
為什麼重要
引用時的可核對性不同。PDF 可以寫「Version 1.0, Feb 2026」；Cheat Sheet 只能寫「讀取日 2026-10-26，最近修改 2026-10-16」，因為它隨時會再改；MCP Top 10 要寫明是 Beta、條目年份是 2025，且目前可能已有或即將有新版。
沒意識到時會怎樣（概念層級）
把 Beta 清單的編號當作穩定標準寫進規範；或把 Cheat Sheet 的某條當作永遠不變的要求。兩者都可能在下次修訂後失效或改名（MCP06 就是例子，見下表）。
怎麼用
以 PDF 指南當作「相對穩定的基準」，以 Cheat Sheet 當作「最新的實務補充」，以 MCP Top 10 當作「風險語言」，引用時分別寫明版本或讀取日。
常見誤解
「MCP Top 10 在 owasp.org 標 Production，所以是穩定標準。」同一頁的路線圖寫著 Phase 3（Beta），而且 index.md 的下一階段寫「Next Release in October 2026」。層級標籤與實際成熟度的對應沒有官方說明（見參考資料頁）。

本章重點與自我檢核

  • MCP 安全文件有四份主要的：伺服器開發指南（給開發者）、第三方使用 Cheat Sheet（給使用者）、MCP Security Cheat Sheet（持續修訂）、MCP Top 10（Beta）。
  • MCP 有 Host、Client、Server 三個角色，Server 提供 Tools、Resources、Prompts；LLM 會看到所有已連線伺服器的所有工具描述。
  • 成熟度不同，引用方式也不同：PDF 寫版本；Cheat Sheet 寫讀取日與最近修改日；Top 10 寫 Beta 與 2025。
  • MCP06 現名 Intent Flow Subversion（舊名 Prompt Injection via Contextual Payloads）；授權文字自相矛盾，保守標 NC。
  • 我能說出哪份文件是給 MCP 伺服器開發者、哪份是給使用者。
  • 我能說出 MCP 的三個角色與兩種傳輸，並解釋為什麼「所有工具描述進同一個脈絡」是安全問題。
  • 我知道 MCP06 的現名與舊名，以及為什麼引用 MCP Top 10 時要標 Beta。
