第 2 章　生命週期的控制：設計、建置、營運

  • 預估閱讀：約 7 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO2
  • 前置：第 1 章

指南第 3 節把「怎麼做」按軟體生命週期切成三段：設計與開發、建置與部署、營運與執行期。這樣分的用意很實際：有些控制必須在寫第一行程式前就決定（例如記憶要不要跨使用者），有些在上線前才能做，有些只能在系統跑起來後做。本章教你每個階段的重點，以及兩個最容易被漏掉、卻很決定性的設計。

2.1 三個階段的重點

官方在每個階段的開頭有一段總結：agentic 系統除了 LLM Top 10 的風險，還引入新的攻擊面，包含持久記憶、自主規劃與突發行為；這些必須在設計時就考慮，包括定義「安全失敗」狀態、劃出整合邊界、制定記憶存取政策，以及在適用處放入人類把關。

表 2-1　生命週期三階段的控制（指南 3.1–3.3，改寫並分組；細項為官方編號）
階段官方的重點代表性控制（官方列舉的摘要）
3.1 設計與開發在寫程式前決定好邊界與失敗方式3.1.2 系統提示詞強化（明確邊界、預設拒絕未列出的主題、用分隔符與結構化輸入、並以確定性控制限制 agent 能做的事）；3.1.3 安全寫碼（驗證所有輸入而非只驗工具參數、不外洩資訊的錯誤處理、機密管理、最小權限）；3.1.5 HITL 設計（以風險識別需核准的動作、清楚的審查介面、並加強速率限制以免壓垮人類）；3.1.6 記憶安全設計（存取控制、加密、寫入前驗證、PII 處理、人工審核記憶條目）；3.1.7 輸入輸出驗證（對輸入與輸出都套用護欄、結構描述強制、輸出淨化、安全渲染、資料最小化）；3.1.8 授權與驗證（辨識權限邊界、用既有身分與授權伺服器、判斷 agent 是代表使用者還是代表系統）

3.3 營運與執行期持續的行為監控，遠超過效能指標；操作者要保有即時覆寫能力3.3.1 持續監控與異常偵測（輸入輸出掃描、工具呼叫監控、計畫與執行監控、記憶異常偵測、多 agent 行為分析、串接 SIEM、自動異常回應）；3.3.2 執行期護欄（輸入輸出護欄、護欄位置、agent 間內容過濾、記憶 TTL、記憶淨化與 PII 遮罩、輸出淨化、內容安全政策）；3.3.3 日誌、稽核與可追溯性（集中式日誌、session 範圍標記、結構化日誌、trace ID、日誌完整性與最小權限、禁止寫入的敏感內容清單）；3.3.4 執行期弱點掃描；3.3.5 事件應變規劃

三個階段的對應關係很好記：設計定邊界、建置定隔離、營運定觀測（作者整理，非官方）。若你在營運階段才發現沒有日誌或沒有隔離，補救的成本通常最高，所以指南才把這些前移到設計與建置。

2.2 兩個容易漏掉的設計

在指南 3.2 節裡有兩條不起眼、卻針對 agent 特有問題的設計。

控制與資料平面分離，以及特權與隔離 LLM

是什麼
(a) 控制與資料平面分離 (3.2.7)：多 agent 協作時，agent 間的通訊要區分「控制訊息」（任務指派、命令）與「資料訊息」（共享資訊）；控制通道要有更強的驗證、授權與完整性檢查。(b) 特權與隔離 LLM (3.2.6)：把「產生控制流程」的 LLM（特權 LLM，只看到可信的提示詞）與「處理不可信資料」的 LLM（隔離 LLM，沒有工具存取權）明確分開。指南舉 Google 的 CaMeL 為例。
為什麼會需要
agent 處理不可信資料的那個元件，通常也是最容易被指示「做別的事」的元件。若它同時握有工具與控制權，一次污染就能發出惡意命令。指南的說法是：這讓你「不必只依賴模型的對齊」，而是用系統設計強制資料流。
怎麼被利用（概念層級）
沒有分離時：一個處理外部文件的 agent，因文件內夾帶的指示而向同一個多 agent 系統的其他 agent 發出任務指派，這些指派被當成合法的控制訊息；或同一個 LLM 既讀不可信內容、又決定要呼叫哪些工具，使不可信內容直接影響工具參數。
怎麼防
控制與資料走不同通道、控制通道強化驗證；用 API 或自訂直譯器，依細緻的能力與資料流追蹤，在執行工具呼叫前強制安全政策；讓不可信資料不能直接影響 agent 的動作或經未授權的工具參數外洩資訊。
常見誤解
「只要把系統提示詞寫好，就能阻止不可信內容影響行動。」指南的 3.1.2 同時說要「以確定性控制限制 agent 能做的事」，3.2.6 更是明說這類架構是在「即使底層 LLM 對提示詞注入脆弱」時仍提供縱深防禦。提示詞強化是必要但不足夠。

2.3 常見陷阱：護欄放在哪裡

指南在 3.3.2 提醒一件容易被忽略的事：護欄的位置會影響偵測效果。例如放在網路層（API 或 AI 閘道）的護欄，可能錯過多回合的提示詞注入，因為它看不到 session 歷史與脈絡；放在應用程式或 agent 程式碼裡的護欄，則有最完整的視野與脈絡。官方依層級描述：API 閘道（輸入層）負責確定性的輸入與存取控制；LLM（模型）負責對齊與行為規則；agent（推理與工具）負責工具權限、逐步驗證、記憶控制；輸出（後處理）負責最終輸出過濾與修正。多 agent 流程中，還要依 agent 對輸出的影響力放置，例如循序架構裡的最後一個 agent 會決定整個流程的輸出。

這和你在 AI Exchange 的七層防線看到的概念相通：不同層看到的資訊不同，單靠一層容易漏。

本章重點與自我檢核

  • 指南按生命週期分三段：設計與開發、建置與部署、營運與執行期；越早做的決定，越便宜也越有效。
  • 記憶範圍、整合邊界、HITL 與「安全失敗」狀態都是設計階段的決定；系統提示詞強化要搭配確定性控制。
  • 建置階段要隔離（沙箱）、管理機密、做部署前測試，並禁止 agent 存取自己的部署管線。
  • 營運階段要觀測到「決策、計畫演進、記憶存取與工具互動」，日誌本身要有最小權限與不得寫入的敏感內容。
  • 多 agent 要分離控制與資料平面；可把處理不可信資料的 LLM 與握有控制權的 LLM 分開。
  • 給我一個控制措施，我能說出它最適合在生命週期的哪個階段決定。
  • 我能用自己的話解釋控制與資料平面分離，以及為什麼不能只靠提示詞強化。
  • 我知道護欄的位置會影響偵測效果，並能舉一個網路層護欄的盲點。
