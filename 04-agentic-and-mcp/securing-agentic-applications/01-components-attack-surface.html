第 1 章　定位、元件與攻擊面

  • 預估閱讀：約 7 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO1
  • 前置：Agentic 威脅與緩解第 2 章；攻擊面

前兩個主題告訴你「有哪些威脅」。這份指南回答下一個問題：我手上的 agent 該怎麼蓋、怎麼部署、怎麼營運才安全。它的做法是先把 agent 拆成六類關鍵元件，再對每一類標出會被打到的威脅，之後所有建議都可以掛回這張表。本章先看這份指南是什麼，再學會讀這張「元件 × 威脅」的表。

1.2 六類關鍵元件 KC1–KC6

指南用 Key Component (KC) 編號描述 agent 的組成。下表是整理版，細項（例如 KC4 的六種記憶範圍）官方有更細的拆分。

表 1-2　六類關鍵元件（官方定義的改寫；細項為官方子編號）
元件是什麼官方細項（舉例）
KC1 生成式語言模型agent 的「腦」：理解、推理、規劃、產生回應LLM、多模態 LLM、小型語言模型 (SLM)、微調模型
KC2 編排決定 agent 的整體行為、資訊流與決策過程工作流 (workflow)、階層式規劃、多 agent 協作
KC3 推理／規劃範式把大任務拆成多步、每步有子目標結構化規劃、ReAct、思維鏈 (CoT)、思維樹 (ToT)
KC4 記憶模組保存短期與長期資訊；常以向量資料庫加 RAG 實作長期記憶依「範圍」分六種：單 agent 單 session、跨 agent 單 session、單 agent 跨 session、跨 agent 跨 session、單 agent 跨使用者、跨 agent 跨使用者
KC5 工具整合框架管理工具的選擇與使用SDK 或函式庫（如 LangChain、MCP）、受管平台（如 Bedrock Agents）、受管 API
KC6 營運環境 (Agencies)agent 透過工具呼叫碰到的外部環境API 存取、程式碼執行、資料庫執行、網頁使用、PC 操作、關鍵系統操作、IoT 裝置存取

KC4 的六種範圍值得多看一眼。官方的觀察是：共享範圍越廣，一次被攻破能波及的範圍越大。單 agent 單 session 的記憶最保守；跨 agent 跨使用者的記憶最危險，因為一個被攻破的 agent 可能同時影響多個 agent 與多位使用者。KC6 也是同樣邏輯：官方把 API、程式碼執行、資料庫執行分成「有限」與「廣泛」兩級（例如只讓模型產生預先定義的 API 呼叫中的某些參數，或讓模型產生整個 API 呼叫），後者的風險顯著更高。

1.4 核心概念：用「元件」而不是「攻擊手法」來組織防禦

以元件為單位的威脅對照

是什麼
指南把「這個系統由哪些部件組成」放在前面，威脅掛在部件上，再把控制掛在威脅上。這和以攻擊手法為主軸的清單不同：清單問「有哪些攻擊」，這張表問「我的這個部件會被怎麼打」。
為什麼這樣組織
建置者的工作單位是元件：選哪個模型、用哪個框架、給記憶什麼範圍、讓工具碰什麼環境。把威脅掛在元件上，就能在做每個設計決策的當下，看到該決策帶來哪些風險。
沒意識到時會怎樣（概念層級）
只看攻擊清單的團隊容易漏掉「範圍選擇」的風險，例如把記憶設成跨使用者共享，或給工具「廣泛」而非「有限」的執行能力；這些是設計時一個選項的差別，卻直接決定被攻破後的影響範圍。
怎麼用
盤點你的系統在 KC1–KC6 各是什麼選項（尤其 KC4 的記憶範圍與 KC6 的有限／廣泛程度），在表 1-3 找出對應威脅，再進入後續章節找控制。指南的設計思路是：選項越窄，需要的控制越少。
常見誤解
「這張表列出的威脅就是全部。」表是各元件「關聯」的威脅，不是窮盡；也不包含 T16、T17。威脅建模仍要回到具體系統，並可用 MAESTRO 七層補充。

本章重點與自我檢核

  • 採用 Version 1.0、July 28, 2025、Status: Released；資源頁日期 2025-07-27；與 T&M 的分工是「怎麼在技術上實作那些緩解」。
  • agent 被拆成六類關鍵元件 KC1–KC6；KC4 記憶有六種範圍，KC6 營運環境區分「有限」與「廣泛」。
  • 指南 2.2 節的表把每類元件對應到 T&M 的威脅；表中沒有 T16、T17，因為成書早於 T&M 1.1。
  • 共享範圍越廣、能力越廣泛，被攻破後的影響越大。
  • 我能說出這份指南與 T&M 的分工，以及它的範圍內與範圍外。
  • 我能把一個 agent 拆成 KC1–KC6，並指出哪個元件的選項最影響爆炸半徑。
  • 我能用表 1-3 找出一個元件關聯的威脅。
