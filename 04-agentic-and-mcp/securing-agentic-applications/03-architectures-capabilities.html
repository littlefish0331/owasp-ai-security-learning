第 3 章　三種架構與高風險能力

  • 預估閱讀：約 7 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章

指南的第 4、5 節不是按階段，而是按你選了什麼來組織：你的系統是單一 agent、有中央協調者、還是蜂群？它能碰 API、執行程式碼、查資料庫、上網、操作電腦嗎？每個選項都有一份對應的控制清單。本章用兩張表把它們攤開，並說明一個共通的規律：選項越廣，控制越多。

3.1 三種架構的安全重點

指南對每種架構的「強化的安全行動」有一份清單，後者建立在前者之上。差別不在於「要不要」某個控制，而在於信任從哪裡來。

表 3-1　三種架構的安全重點（指南 4.1–4.4，改寫）
架構特徵額外的控制重點（在前者之上）
4.1 單一 agent一個 agent 帶一組工具；基準線驗證與授權：OAuth 2.0／OIDC、授權碼流程加 PKCE、明確的同意畫面、短效存取權杖、受管身分服務、依角色與最小權限、區分讀寫並預設唯讀、即時憑證；資料保護：加密、DLP、資料分類與敏感度標籤、資料最小化；程式碼安全；監控與事件應變（含緊急關閉開關）；提示安全
4.2 多 agent、中央協調者協調者負責任務分派、維持整體工作流或狀態控制平面分離、每個 agent 用不同權限集；強化協調者的 API；防範控制流劫持（驗證 agent 回應、檢查營運中繼資料的完整性）；緩解混淆代理人問題；agent 間通訊用 mTLS、預先定義結構描述、憑證或權杖驗證、安全訊息佇列、政策執行點 (PEP)、速率限制；信任邊界：零信任、網路分段、容器化；探索僅限已知可信伺服器
4.3 多 agent、蜂群沒有中心，agent 自行協作；難以有明確的「正確行動」指引把「誰可信、什麼動作對」的決定放在 agentic 流程之外；限制或禁止蜂群在無人指引下新增 agent；去中心化身分 (DID) 與可驗證憑證 (VC)；去中心化的聲譽系統；點對點通訊用合適的協定（含加密與認證）
4.4 跨架構不論哪種架構都要做安全的 API 設計與速率限制、持續安全測試、監控與威脅偵測、安全的更新與維護

最容易被誤讀的是蜂群：指南並不是說「蜂群需要 DID 才安全」，而是說蜂群缺少中心，所以信任必須由外部的身分與憑證機制提供；若你的蜂群是封閉環境、成員固定，限制它新增成員比導入 DID 更直接。這個解讀是作者整理，非官方；指南只列出做法，沒有給選擇的準則。

3.2 六類高風險能力（KC6）的控制

指南第 5 節針對 KC6 的每種能力列出核心威脅與控制。以下是比較表。重點是它們的共同結構：先縮小能力的形狀（模板、有限級），再隔離，再加人與日誌。

表 3-2　高風險能力與控制（指南 5.1–5.6，改寫；T 編號為指南列出的核心威脅）
能力核心威脅最先要做的控制（官方的第一與第二項）
5.1 API 存取未授權資料存取、API 濫用與成本暴增（T3、T4、T2）、金鑰外洩（T3、T9）以細緻 OAuth scope 或受限 API 金鑰做最小權限；設定允許／拒絕清單（准許的基底 URL）；偏好 API 模板，而不是讓 LLM 產生完整 API 呼叫
5.2 程式碼執行任意程式碼執行 (T11、T3)、程式碼注入 (T11、T2)、資源耗盡 (T4)、機密洩漏 (T6)強制沙箱（OS 層隔離、容器、VM、WebAssembly、雲端沙箱）；對 agent 產生的程式碼做靜態分析；資源與時間上限；允許清單、人工核准高風險操作
5.3 資料庫執行SQL 注入 (T2)、未授權資料暴露或修改 (T3)、RAG 資料污染或敏感資料檢索 (T1、T5、T3)用受管向量資料庫與存取控制（無法保護的資料就不要匯入）；只用參數化或模板查詢、最小權限帳號（只讀、受限資料表、列欄層級安全）；RAG 檢索後的敏感內容過濾
5.4 網頁使用惡意網頁內容 (T11)、機密洩漏 (T6)、釣魚 (T7)、SSRF (T2、T3)、存取使用者瀏覽器資料 (T3)沙箱化瀏覽器元件（避免在使用者自己的瀏覽器或擴充功能中運作）；URL 允許清單、安全網頁閘道、域名信譽檢查；網路分段防 SSRF
5.5 PC 操作未授權檔案存取或修改 (T3)、任意 OS 指令執行 (T11、T3、T2)、橫向移動 (T3)嚴格隔離（OS 層沙箱、受限使用者、專用容器或 VM）；允許／拒絕清單限定 OS 操作與檔案路徑、攔截 OS 指令；沙箱不累積資料與 session
5.6 關鍵系統操作災難性的實體後果 (T2、T3、T6、T7)、惡意控制注入 (T2、T6)、錯誤資料影響決策 (T1、T5)最大程度隔離（實體隔離或高度分段網路）；MFA 走 agent 之外的流程（不用 agent 中介 MFA 或保留特權 session）；每個關鍵動作都強制 HITL，且要精簡到讓人每次都有注意力；預設唯讀監控

官方在 5.6 特別提醒了一件和設計有關的事：過度或低效率的提示會讓人無差別地批准。這和 T&M 的 T10（壓垮 HITL）、Agentic Top 10 的 ASI09 是同一個問題，只是這裡從「怎麼做 HITL 才有效」切入。

3.3 情境範例 A：一個什麼都能做的運維助理

情境 A（虛構）：雲嶼科技的 DevOps 助理

虛構 雲嶼科技是虛構的公司。平台團隊做了一個「運維助理」：工程師用自然語言描述需求，助理可以呼叫雲端 API、在跳板機上執行 shell 指令與腳本、查詢監控資料庫、瀏覽內部 wiki 與外部文件，必要時修改基礎設施組態。為了讓使用者「免打斷」，所有動作預設自動核准。以下為虛構，細節停在概念層級。

架構：單一 agent（4.1）｜KC6.1 廣泛 API 存取、KC6.2 廣泛程式碼執行、KC6.3 資料庫、KC6.4 網頁使用、KC6.5 PC 操作。

  1. 發生了什麼：有人在公開的技術部落格留言區貼了一段看似疑難排解的文字。助理上網查資料時讀到它，這段文字夾帶了給助理的指示。助理把它當成合理的下一步，用 shell 執行了其中一個腳本，並用廣泛的 API 存取查詢了不相關的資源。
  2. 哪一環出問題：(a) KC6.4 網頁使用沒有沙箱，直接把不可信內容帶進決策；(b) KC6.2 與 KC6.5 的能力是「廣泛」而不是「有限」；(c) KC6.1 讓 LLM 產生完整 API 呼叫，沒有模板與允許清單；(d) 所有動作預設自動核准，沒有 HITL。
  3. 對應條目：指南 5.1–5.5 的核心威脅：T2、T3、T11、T6；T&M 的 Playbook 3（工具與供應鏈）；Agentic Top 10：ASI01、ASI02、ASI05。LLM Top 10 2026：LLM01:2026（間接注入入口）、LLM03:2026 Excessive Agency。
  4. 該採什麼控制：
    • 縮小形狀：API 改為預先定義的模板，LLM 只填已定義的參數；shell 改為允許清單中的命令；
    • 隔離：瀏覽用沙箱、與內部網路分段（防 SSRF）；腳本與命令在容器或微型虛擬機中跑、不累積 session；
    • 最小權限與即時存取：助理用範圍有限、短效的憑證；跳板機以受限使用者執行；
    • 人與日誌：會修改基礎設施組態的動作需人核准，且審查介面要精簡；記錄所有工具呼叫與 OS 層動作，串接 SIEM；備妥緊急關閉開關。
  5. 學到什麼：這個助理一次選了所有最廣泛的選項，於是需要所有最重的控制。與其逐一補控制，更有效的是先縮小選項：不是每個任務都需要程式碼執行和 PC 操作；能用模板就不用自由產生。這正是 Least Agency 在建置面的樣子。

本章重點與自我檢核

  • 三種架構的控制是累加的：單 agent 是基準；中央協調者加上協調者本身與 agent 間通訊的控制；蜂群因無中心，信任須由外部機制提供。
  • 高風險能力的控制有共同結構：縮小形狀 → 隔離 → 加人與日誌。
  • 偏好 API 模板，而不是讓 LLM 產生完整呼叫；無法保護的資料就不要匯入向量資料庫；MFA 走 agent 之外。
  • HITL 提示過多或低效，會使人無差別批准。
  • 選項越廣，控制越多；能縮小選項就先縮小。
  • 給我一個系統的架構與能力，我能列出該先看哪幾張控制清單。
  • 我能說出 API 模板為何比讓 LLM 產生完整呼叫安全。
  • 我知道為什麼 MFA 不應該由 agent 來中介。
