1.2 Agent 比一般 LLM 應用多了什麼

文件把 agent 的核心能力分成三塊：規劃與推理（用 LLM 決定控制流程，常見做法是 ReAct：邊推理邊行動）、記憶（單次 session 內的短期記憶，以及跨 session 的長期記憶）、行動與工具使用（內建函式、外部 API，以及透過 MCP 這類協定連接工具）。自主性也不是二分法：從完全寫死的流程、受程式碼或狀態機約束的流程，到完全由對話與模型推理決定的流程，是一條光譜。

文件對兩者關係的說法是：LLM 應用若帶有 agent 行為，在 LLM Top 10 中就是 Excessive Agency（LLM06:2025）；反過來，agent 本身也可以寫成一個有工具的 LLM 應用。差別在於下表這幾件事被放大了：

1.3 參考架構：威脅模型的畫布

文件用一張「單一 agent 架構」當作討論威脅的畫布，並明說這不是要定義標準的 agent 架構。它列出可部署的元件：(1) 代表使用者執行任務的應用；(2) 接收自然語言輸入的 agent，通常建在 LangChain、AutoGen、CrewAI 這類框架上；(3) 一個或多個負責推理的 LLM；(4) 被呼叫的服務與工具（透過框架層的工具呼叫，或由模型回傳要呼叫的內容）；(5) 支援服務：存放長期記憶的外部儲存，以及向量資料庫等資料來源（RAG 內容）。

多 agent 架構的差別，文件寫得很精簡：架構相似，只多了 agent 間通訊與選配的協調 agent；Google 的 Agent2Agent (A2A) 是其中一種通訊協定。文件另列了多種 agentic 模式（如 Reflective、Hierarchical、RAG-Based 等），用意是讓威脅建模的討論有一致用語，並不是安全分類。

1.4 核心概念：混淆代理人與非人類身分

文件在參考威脅模型裡最先提的兩個 agent 專屬問題，都跟「agent 用誰的權限做事」有關。

混淆代理人 (Confused Deputy) 與非人類身分 (Non-Human Identity, NHI)

是什麼
混淆代理人：agent（「代理人」）的權限高於使用者，卻被誘導代替使用者做了使用者本來無權做的事。非人類身分 (NHI)：機器帳號、服務身分與 agent 使用的 API 金鑰；agent 對接雲端服務、資料庫與外部工具時，通常就是用這類身分。
為什麼會發生
agent 若缺乏權限隔離，就分不清「合法使用者的請求」與「被注入的惡意指示」，只看得到自己手上那把權限更大的鑰匙。NHI 則可能沒有 session 層級的監督，一旦被濫用或權杖外洩，比較不容易被察覺。
怎麼被利用（概念層級）
文件舉的例子：agent 被允許執行資料庫查詢，但沒有確實檢查提交提示詞的人與其憑證；攻擊者便能誘使它執行自己直接無權執行的高權限查詢。另外，agent 繼承的權限若過寬（例如整個使用者 session 或服務權杖），即使個別工具 API 各自有限制，agent 也能把多個工具串起來，例如從外部 API 取回敏感資料再放進使用者看得到的回應。
怎麼防
文件的做法：代表使用者行動時，依最小權限縮小 agent 的授權範圍；驗證提交提示詞的使用者是否有權執行該動作；建立清楚的身分流向、嚴格的 RBAC，以及對 agent 存取企業環境採零信任。第 3 章的 Playbook 4 會把這些展開。
常見誤解
「每個工具 API 都有自己的權限檢查，所以 agent 是安全的。」文件明說：即使個別工具 API 有限制，agent 仍可能把多個工具串成非預期的順序來繞過控制。權限要在「agent 能做什麼的總和」這一層檢查，不只是逐一工具。
