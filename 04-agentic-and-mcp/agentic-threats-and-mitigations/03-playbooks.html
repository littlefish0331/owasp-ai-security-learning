第 3 章　緩解策略：六個 Playbooks

  • 預估閱讀：約 8 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO3
  • 前置：第 2 章；預防／偵測／回應

知道有哪些威脅之後，下一步是「怎麼擋」。文件把緩解策略整理成六個 Playbook，每個對應一組威脅，並在內部分成預防 (Proactive)、反應 (Reactive)、偵測 (Detective) 三步。本章教你怎麼選 Playbook，並用一個虛構的企業 Copilot 情境走一遍。

3.1 六個 Playbook 與它們涵蓋的威脅

文件說這些 Playbook 與前章的 Navigator 對齊，每個都分「預防、反應、偵測」三種措施，而且刻意重疊：記憶完整性同時出現在 Playbook 2 與 5，權限管理出現在 Playbook 3 與 4，多 agent 的信任驗證出現在 Playbook 5 與 6。文件也提醒，這些只處理 AI 特有的風險，傳統的軟體安全、LLM 防護與存取控制仍要做，才算縱深防禦。

表 3-1　六個 Playbook 與涵蓋的威脅（依官方 Playbook and Threat Mapping Overview）
Playbook涵蓋的威脅目標（改寫）
1 防止 agent 推理被操縱T6 Intent Breaking & Goal Manipulation；T8 Repudiation & Untraceability；T7 Misaligned & Deceptive Behaviors防止攻擊者操縱意圖、透過欺騙行為繞過安全，並提升行動可追溯性
2 防止記憶污染與知識損毀T1 Memory Poisoning；T5 Cascading Hallucination防止 agent 儲存、檢索或傳播被操縱的資料

3.2 每個 Playbook 的三步結構

六個 Playbook 都長一樣：Step 1 預防、Step 2 反應、Step 3 偵測。下表挑出四個最具代表性的 Playbook，把每一步的重點措施並列（措辭為改寫；完整清單請看原文）。

表 3-2　Playbook 的三步結構（挑選四個；措施為官方列舉的改寫）
PlaybookStep 1　預防Step 2　反應Step 3　偵測
2 記憶記憶內容寫入前驗證；限制記憶只能來自可信來源；以 session 隔離記憶；依任務限制可檢索的記憶；依敏感度限制保留期限；要求記憶更新附來源；跨 session 的變更先經多 agent 或外部驗證對記憶更新日誌做異常偵測；對可疑條目重新驗證；用機率式真偽檢查找出漂移；以快照回復到已驗證狀態；標記異常高的改寫頻率檢查新知識是否與既有事實一致；限制低可信輸入的傳播；追蹤知識血緣；對知識更新做版本控制；持續分析記憶存取模式
3 工具嚴格的工具存取控制；工具的函式層級認證；在隔離的容器沙箱執行並於每次後重置；速率限制；依即時風險分數限制；即時 (JIT) 授權並用後即撤；對 agent card、提示範本與工具定義做數位簽章，搭配 SBOM記錄所有工具互動；偵測繞過政策的指令串接；金融、醫療、管理類操作需使用者明確核准；提升權限的 AI 產生程式碼需人工驗證；標記異常的呼叫頻率監控工作負載並自動暫停超標的處理程序；追蹤多 agent 累計資源；限制併發的修改請求；監控供應鏈相依；用模擬被污染的元件做紅隊
4 身分對 agent 做密碼學身分驗證；細緻的 RBAC 與 ABAC；高權限帳號用多因素；長時 session 持續重新認證；除非預先定義，禁止跨 agent 委派權限；AI 對 AI 互動用雙向認證；AI 產生的憑證短效會自動到期的動態存取控制；用行為剖析找出角色指派異常；高風險的認證變更需雙 agent 或人工驗證；偵測角色繼承異常；對升權設時間上限追蹤 agent 行為是否與身分一致；監控預期外的角色變更；比對認證嘗試與歷史存取；偵測遞迴或串接的工具執行；隔離產生可疑協定流量的 agent
6 多 agent所有 agent 間訊息要驗證與加密；agent 信任分數；高風險操作前做共識驗證；以任務分段防止跨 agent 升權；速率與配額；依功能角色限制 agent 之間的溝通並切分拓撲即時偵測 rogue 行為；隔離被標記的 agent 及其通訊與記憶；撤銷可疑 agent 的權限；自動停用未授權處理程序；追蹤被封鎖後換身分重新加入的 agent監控角色與任務指派的異常變更；記錄 agent 間通訊；偵測信任分數的下滑；追蹤被拒絕後被其他 agent 核准的動作；監控決策一致性

留意文件在 Playbook 3 的一句重要註記：當工具透過 A2A、MCP 這類協定被呼叫時，這些呼叫可能繞過使用者介面、同意流程與人類監督，所以更要在這一層強制沙箱與權限隔離。

3.3 遇到某個情況，先翻哪個 Playbook

3.4 情境範例 A：企業 Copilot 被一封郵件帶偏

情境 A（虛構）：松野製造的 Copilot

虛構 松野製造是虛構的公司。IT 部門導入一個企業 Copilot：它能讀使用者的郵件、檔案與行事曆，查詢內部 CRM，也能代使用者建立行事曆邀請與草擬回信。為了讓使用者「不必重複說明」，Copilot 把偏好與常用資料存進長期記憶。這個架構與文件「Enterprise Co-Pilots」範例威脅模型同型；以下故事為虛構，細節停在概念層級。

架構：外部郵件（不可信）→ Copilot → { 郵件／檔案／行事曆讀取、CRM 查詢與寫入、行事曆邀請、長期記憶 }。

  1. 發生了什麼：有人寄來一封看似普通的信，信中藏著給 Copilot 的指示。使用者請 Copilot「摘要今天的郵件」，Copilot 照指示改去搜尋敏感資料，並把資料夾帶在發出的行事曆邀請裡送到外部信箱；同時，它把一條「之後都這樣做」的偏好寫進長期記憶，往後每次使用都會重演。
  2. 哪一環出問題：(a) 外部郵件的內容被當成指令（目標被改，T6）；(b) Copilot 用手上的工具做了被操縱的事（T2）；(c) 污染被寫進記憶而持續（T1）；(d) 操作寫入 CRM 時是以使用者的身分，歸因給使用者（T9）；(e) 沒有記錄就看不出發生過什麼（T8）。
  3. 對應條目：T&M 1.1：T6、T2、T1、T9、T8（文件的 Enterprise Co-Pilots 範例就列了這幾項及 T3、T7、T11、T15、T16、T17）。LLM Top 10 2026 的對應是 LLM01:2026（間接提示詞注入的入口）與 LLM03:2026 Excessive Agency（權限過寬）。
  4. 該採什麼控制：
    • Playbook 3：行事曆邀請這類「會對外送資料」的工具加上收件人允許清單或使用者核准；以最小權限與 JIT 授權限制 Copilot 能做的寫入（最小權限）；
    • Playbook 2：寫入長期記憶前驗證並附來源，禁止外部郵件內容直接成為持久偏好；異常的記憶改寫要能回復；
    • Playbook 4：以使用者的最小授權執行，並把「代誰行動」記錄下來，避免寫入 CRM 時混淆代理人（第 1 章）；
    • Playbook 1：記錄 Copilot 的決策與工具呼叫，對「摘要任務卻去搜尋敏感資料」這類偏離做偵測。
  5. 學到什麼：一次事件同時點亮好幾組威脅，不是挑一個 Playbook 就好。最先該補的是限縮後果的控制（Playbook 3 的工具與權限）：就算入口被擋不住，資料也送不出去。

本章重點與自我檢核

  • 六個 Playbook 各對應一組威脅，每個分成預防、反應、偵測三步；文件寫「五個」但實際有六個。
  • Playbook 刻意重疊：記憶、權限、多 agent 信任各在兩個 Playbook 出現；選 Playbook 看它列了哪些威脅。
  • Playbook 3 特別提醒：經由 MCP、A2A 呼叫的工具可能繞過使用者介面與同意流程。
  • 這些 Playbook 只處理 AI 特有風險，傳統安全與 LLM 防護仍須疊加以達縱深防禦。
  • 實務上一個事件常需要多個 Playbook；最先補的是限縮後果的控制。
  • 給我一個症狀，我能指出該先翻哪個 Playbook，並說明為什麼還需要疊加其他的。
  • 我能說出預防、反應、偵測三步各自的目的。
  • 我知道文件在「五個 Playbook」與「六個 Playbook」之間的不一致，並以實際列出的六個為準。
