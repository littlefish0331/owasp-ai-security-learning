第 6 章　RAG 系統

  • 預估閱讀：約 9 分鐘（不含章末檢核；另有 4 題章末檢核）
  • 對應學習目標：LO5
  • 前置：第 5 章（致命三要素 (Lethal Trifecta)）；信任邊界 (Trust Boundary)

你已經很熟悉 RAG 怎麼運作，所以這一章不講原理。要看的是：RAG 在資安上多出了哪些攻擊面 (Attack Surface)，以及官方給了哪些「上線前該問的問題」。

官方的定位：RAG 不是另一個威脅領域

AI Exchange 說得很明確：RAG 沒有獨立的威脅圖景，適用同一套資產與影響模型；週期表已列出各威脅的控制，不需要專屬的 RAG 控制類別。這一節只標出 RAG 在哪裡集中既有威脅，以及哪裡帶來了單純聊天機器人沒有的攻擊面。

6.1 五個階段，各有一道信任邊界

官方把典型的 RAG 管線分成五個階段，並指出每個階段都有各自的信任邊界。

為什麼 RAG 讓情況不一樣？官方給了三個原因：

  1. 存取控制與檢索範圍經常脫節。向量資料庫很少強制執行與原始系統相同的逐文件權限，形成「混淆代理人 (Confused Deputy)」：模型（以及使用者）可能取回他本來沒有權限看的片段。
  2. 語料本身成為一項資產，有自己的 CIA 需求：通常比訓練資料更大、更少人審過、更新更頻繁，且由不同信任等級的多位貢獻者組成。
  3. 檢索是第二個、而且幾乎看不見的輸入通道。使用者只看到自己的問題；模型還看到檢索器選出的一切。任何能進入索引的內容，都是潛在攻擊面，不論目前這位使用者能否直接觸及它。

6.2 RAG 集中與新增的威脅，以及上線前要問的問題

官方列出 RAG 的威脅，並把「威脅建模問題」寫成「如果答案讓你不安，就考慮這個威脅」的形式（延伸第 7 章的決策樹）。下表把兩者合併：左欄是威脅，右欄是對應的上線前提問。

輸出含傳統注入檢索內容帶有腳本或惡意連結，被回聲到輸出並在下游渲染（XSS、Markdown 外洩連結等）檢索內容是否能到達渲染環境或下游動作？
供應鏈與可追溯語料、嵌入模型或向量庫由第三方提供；若回應沒有出處，事後無法偵測投毒或過期這些是否由第三方提供？回應是否帶可驗證的來源歸屬（片段、文件、雜湊）？
AI 資源耗盡攝入時過大或刻意製作的文件，或迫使昂貴檢索與重排序的查詢（官方的建模問題未單列）

RAG 常是致命三要素的「Data」那一腳

RAG 通常提供三要素中的 Data（經由檢索片段做間接注入）；語料或同一個檢索器能碰到的其他文件是 Access；輸出中的可點擊連結或 agent 動作則是 Send。官方特別說，RAG 不必是 agentic 才會中招：對敏感語料的讀取，加上使用者可觀察到的輸出通道（如被渲染的連結），就已足夠。

6.3 控制：沒有專屬類別，但有幾個重點

  • 把 AUGMENTATION DATA CONFIDENTIALITY / AUGMENTATION DATA INTEGRITY 與 INPUT SEGREGATION 專門用在檢索通道；語料要以和訓練資料同樣的嚴謹度對待：有存取控制、有版本、可追溯；並在管線每個階段採 fail-closed（失效即拒絕）預設，而不只是在模型邊界。
  • 使用第三方或外部託管的嵌入模型、向量庫服務、攝入連接器時，供應鏈管理要額外留意。官方指出：因為已儲存的向量可以反推原文，向量庫備份要與來源文件同一敏感等級；把嵌入送到第三方嵌入服務，等於轉移底層資料。
  • MONITOR USE：如果 RAG 回應沒有可驗證的出處（哪些片段、來自哪些文件、雜湊值為何），事後就無法偵測被投毒或過期文件是否影響了答案，這會讓原本可偵測的資料投毒事件變成不可偵測。

6.4 核心概念：存取控制繼承 (Access Control vs. Retrieval Scope)

檢索範圍與原始存取控制脫節

是什麼
來源系統（例如文件管理系統）有「誰能看哪份文件」的規則；但把文件切塊、嵌入、放進向量庫之後，這些規則常常沒有跟著走，檢索時只看「相似度」。
為什麼會發生
向量庫的設計目標是找最相近的片段，不是做逐文件授權；而且 RAG 的價值來自於「把大量文件都放進去」。官方在輸入資料外洩的說明裡明講：應該把使用者的存取權套用到檢索，例如 X 部門的使用者提問時，不該取回 X 部門沒有權限的內容。
怎麼被利用（概念層級）
使用者不需要任何特殊技巧，只要問到與受限文件相關的主題；若系統取回並放進提示詞，模型就可能在回答中引用。多租戶時，也可能從結果數量、分數分布等側面推測其他租戶文件的存在。
怎麼防
檢索階段要用提問者的權限過濾；權限檢查失敗時採失效即拒絕，而不是退回不過濾；來源文件刪除或降權時，連鎖清除其片段、嵌入與快取。
常見誤解
「模型不會把它不該說的話說出來。」官方的 GenAI 一節說得很直接：對模型來說，所有資料都是「可及」的，system prompt、對齊或輸出過濾的防護通常不是滴水不漏。

6.5 情境範例 C：保險公司的客服 RAG

情境 C（虛構）：星橋保險的理賠客服助理

虛構 星橋保險是虛構的公司。他們為客服人員建了一個 RAG 助理：知識庫由理賠手冊、內部 wiki、過去的客服工單與合作醫療院所提供的資料組成，員工以自然語言提問，助理回答並附上來源。向量庫使用外部託管服務，攝入管線每晚自動同步 wiki 與工單系統。

架構：來源（手冊、wiki、工單、院所資料）→ 夜間攝入 → 外部託管向量庫 → 檢索 → 託管 LLM → 客服人員介面（會渲染 Markdown 連結）。

  1. 發生了什麼（兩件獨立的事）：(1) 某位客服人員查詢一般理賠流程時，答案中引用了「僅限理賠審查部」才能看的內部審查標準，因為檢索時沒有帶入提問者的權限；(2) 稍早，某份合作院所資料夾中的文件被插入隱藏指示，內容會誘使助理在答案裡附上一個含查詢內容的外部連結（概念層級，不描述具體手法）。
  2. 哪一環出問題：(1) 檢索階段：檢索範圍和來源存取控制脫節；(2) 攝入階段：來源有第三方可編輯，沒有當成不可信輸入；且輸出會被渲染成可點擊連結。
  3. 對應條目：(1) AI Exchange：Disclosure in output／授權不一致造成的增補資料 (augmentation data) 外洩；LLM Top 10 2026 的 LLM02 Sensitive Information Disclosure 一類；(2) AI Exchange：Indirect prompt injection 與 Output contains conventional injection（經由連結）；LLM Top 10 2026 的 LLM01 與 LLM10。
  4. 該採什麼控制：
    • 以提問者的權限過濾檢索結果，失敗即拒絕（AUGMENTATION DATA CONFIDENTIALITY、LEAST MODEL PRIVILEGE）；
    • 將第三方可編輯的文件視為不可信：INPUT SEGREGATION 加上 PROMPT INJECTION I/O HANDLING，並限制輸出中可渲染的連結（ENCODE MODEL OUTPUT）；
    • 回應附上片段與文件的出處與雜湊，供事後追查（MONITOR USE）；
    • 外部託管向量庫與嵌入服務：供應鏈管理，並將向量庫備份視為與來源同一敏感等級。

本章重點與自我檢核

  • RAG 不是獨立威脅領域，但它新增了「檢索」這條看不見的輸入通道，以及「語料／索引」這兩項資產。
  • 五個階段（攝入、索引、檢索、增補、生成）各有信任邊界。
  • 最常被忽略的：檢索範圍和原始存取控制脫節、失效時回退成不過濾、刪除沒有連鎖、回應沒有出處。
  • RAG 常是致命三要素的 Data；不必 agentic 也可能外洩。
  • 我能對自己的 RAG 管線逐階段指出信任邊界。
  • 我能說出至少三個官方 RAG 威脅建模問題，並說明答案讓人不安時該考慮什麼威脅。
  • 我知道「失效時回退成不過濾」為什麼是漏洞。
